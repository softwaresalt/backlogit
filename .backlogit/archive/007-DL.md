<!-- BEGIN:Problem Frame -->
Backlogit lifecycle operations (create, move, archive, ship) have no mechanical enforcement points. Validation rules, cascade behaviors, and hierarchy constraints are documented in compound learnings and agent instructions but not enforced in code. This means: orphaned tasks (level-2 items without parent_id) can be created requiring manual remediation; status transitions can skip required states (e.g. queued to done without passing through active); shipment completion requires manual cleanup of child item statuses; index staleness after mutations requires explicit backlogit sync calls; parent feature status does not auto-update when all children complete. Internal lifecycle hooks would enforce these rules mechanically at the operation boundary, eliminating human and agent error.
<!-- END:Problem Frame -->

<!-- BEGIN:Options -->
Option A: Pre/Post Hook Callbacks in Workspace. Register Go callback functions on the Workspace struct. Each lifecycle method (CreateArtifact, MoveArtifactStatus, ArchiveItem, ShipShipment) calls runner.Fire(pre_event) before mutation and runner.Fire(post_event) after. Hooks are synchronous and in-process. Configuration in hooks.yaml defines which hooks are active. Pro: Simple, testable, no external dependencies. Pro: Leverages existing HooksConfig stub in config/schema.go. Pro: Errors in pre-hooks can reject the operation. Con: Synchronous execution adds latency to every operation. | Option B: Event-Driven Hook Reactor. Extend the existing EventWriter to publish events to an in-process channel. A reactor goroutine consumes events and fires registered handlers asynchronously. Pro: Non-blocking, operations complete immediately. Con: Post-hooks cannot reject operations (already committed). Con: More complex error handling and ordering guarantees. | Option C: Compiled Hook Registry (No Config). Hardcode all enforcement rules as Go functions registered at Workspace init time. No hooks.yaml, no runtime configuration. Pro: Simplest implementation, zero config surface. Con: Adding new hooks requires code changes and recompilation. Con: Users cannot customize enforcement rules.
<!-- END:Options -->

<!-- BEGIN:Chosen Direction -->
Option A: Pre/Post Hook Callbacks for the initial implementation, with the existing HooksConfig stub expanded to support hook definitions in hooks.yaml. This balances simplicity with configurability. Key design decisions: (1) Pre-hooks can reject -- returning an error from a pre-hook prevents the mutation. (2) Post-hooks are fire-and-forget -- failures log warnings but do not roll back. (3) Built-in hooks ship as defaults -- parent enforcement, status transition validation, cascade completion, and index invalidation are registered automatically. (4) hooks.yaml controls activation -- users can disable default hooks or adjust thresholds. (5) Hook context carries mutation details -- item ID, artifact type, old/new values, actor.
<!-- END:Chosen Direction -->

<!-- BEGIN:Open Questions -->

<!-- BEGIN:Notes -->
Existing event infrastructure in internal/events/stream.go provides the append-only logging that post-hooks can leverage. HooksConfig stub exists at internal/config/schema.go line 96-99. The compound learning docs/compound/workflow-issues/orphaned-tasks-without-parent-features-2026-04-10.md documents the parent enforcement gap this would close. Constitution principle I (Type-Safe Go) requires hook registration use typed structs not loosely typed maps. Constitution principle III (Test-First) requires hook tests before implementation. Target hook points: CreateArtifact (pre/post), MoveArtifactStatus (pre/post), ArchiveItem (pre/post), ShipShipment (pre/post), AdoptItem (post), CascadeStatusUpdate (post).
