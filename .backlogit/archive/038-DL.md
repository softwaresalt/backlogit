# Standalone Binary Release — Install Accessibility

## Problem Frame

<!-- BEGIN:problem-frame -->
backlogit currently requires Go toolchain installation (`go install`) to set up. This limits adoption to developers who already have Go configured. The release infrastructure already exists — `.github/workflows/release.yml` cross-compiles for linux/darwin/windows × amd64/arm64 and publishes to GitHub Releases via `softprops/action-gh-release`. The `internal/version` package supports ldflags injection for Version, Commit, and BuildDate.\n\nWhat is missing is the last-mile accessibility: user-facing installation documentation, platform-aware install scripts, SHA256 checksums for download verification, and complete build metadata injection (the release workflow only sets Version, not Commit or BuildDate).
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: Docs + Install Script + Checksums (Recommended)**\nAdd installation documentation with platform-specific download instructions, a curl/PowerShell install script that auto-detects OS/arch, publish SHA256 checksums alongside release binaries, and fix the release workflow to inject all three ldflags (Version, Commit, BuildDate). Low risk, high accessibility gain.\n\n**Option B: Add Package Manager Support (Homebrew, Scoop)**\nEverything in A plus Homebrew formula and Scoop manifest. Higher maintenance burden, requires separate tap/bucket repositories. Premature for current adoption level.\n\n**Option C: Migrate to GoReleaser**\nReplace the hand-rolled release workflow with GoReleaser for automated cross-compilation, checksums, changelogs, and package manager publishing. Powerful but adds a dependency and learning curve. The current workflow already handles the core use case.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option A — Documentation, install scripts, checksums, and build metadata completeness. This delivers the core value (install without Go) with minimal carrying cost. The release workflow already handles cross-compilation and GitHub Releases; we just need to make it discoverable and verifiable. Package managers (Option B) and GoReleaser (Option C) are YAGNI at current adoption levels and can be added later if demand warrants.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Should the install script support a `--version` flag to install specific releases, or only latest?\n2. Should checksums be a separate file per binary or a single SHA256SUMS file?\n3. Should the docs include a verification guide for security-conscious users?
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
Existing infrastructure:\n- `.github/workflows/release.yml`: cross-compile matrix (6 targets), git-cliff changelog, GitHub Release publish\n- `internal/version`: Version, Commit, BuildDate vars with ldflags support\n- `Makefile` / `make.ps1`: local build with ldflags\n- Current version: 1.0.2\n\nScope boundaries:\n- IN: install docs, install script (bash + PowerShell), SHA256 checksums step in release workflow, complete ldflags in release build step\n- OUT: Homebrew formula, Scoop manifest, GoReleaser migration, Docker image, snap/flatpak
