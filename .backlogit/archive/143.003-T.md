# Route the shipped transition fail-closed on the governed path

## Description

<!-- BEGIN:description -->
Unit 3. In `moveShipmentStatusWithHeadGuard` (`internal/core/shipment.go`), gate on `newStatus == ShipmentShipped && !topLevel` and return the append error instead of only warning. The `topLevel` flag is what distinguishes the governed path from the ungoverned one: `ShipShipment` is the only caller passing `topLevel=false` for `ShipmentShipped` (`internal/core/shipment_lifecycle.go:509`), while the exported `MoveShipmentStatus` passes `true` (`internal/core/shipment.go:115-117`). Gating on the status alone would make the exported entry point fail closed WITHOUT any of 143.004-T's classification or compensation, persisting the status and then returning a bare error, which is an uncompensated residue on a path this feature declares ungoverned. Every other transition (claim, abandon) and every top-level caller keeps the existing best-effort call and semantics. Declare the private boundary type `shipmentEventAppendError` HERE, in the unit that constructs it, and wrap the returned failure in it at the call site so the closure in 143.004-T classifies only that error; declaring it a task earlier would leave an unexported type with no constructor, which `staticcheck` reports as unused. Do NOT retry the append: the `AppendEvent` contract is that a partial write or post-write fsync failure is `ErrWriteIndeterminate` and is not safe to retry blindly, and a pre-append lock failure is already tagged not-applied by 143.002-T and compensates; there is no third outcome class. Record in the doc comment that the fail-closed shipped path intentionally suppresses the `HookMoveShipmentStatus` post-hook, which today always fires because the append error is swallowed, and assert the suppression with a recording hook runner rather than leaving it to the comment. Note the platform consequence: `internal/events/item_log_lock_other.go` always errors on unsupported build targets, so on such a platform every ship would refuse; Windows and Unix are the supported targets. Execution posture: implementation, gated behind the 143.001-T red state.
<!-- END:description -->

## Acceptance Criteria

<!-- BEGIN:acceptance-criteria -->
- Only `newStatus == ShipmentShipped && !topLevel` returns the append error; claim, abandon, and every top-level caller keep best-effort semantics.
- The private `shipmentEventAppendError` boundary type is declared here and constructed at the call site.
- No retry loop is introduced at the append site.
- The `HookMoveShipmentStatus` suppression on the fail-closed path is asserted by a recording hook runner.
- 143.001-T scenarios now fail on classification assertions rather than on no-error-returned, and the not-a-snapshot-error guard becomes meaningful from here on.
- `TestClaimShipment_ActivatesIncludedScope`, `TestClaimShipment_RollsBackOnMidFlightActivationFailure`, and `TestClaimShipment_SuccessActivatesAllItems` stay green unchanged.
- The exported-path shipped-transition tests (`internal/core/shipment_test.go:176`, `:960`, `:1214`, `internal/core/queue_test.go:369`) stay green unchanged, proving the gate is path-scoped; `internal/core/shipment_test.go:1068` uses the nested form directly and is the expected behavior boundary, to be checked explicitly rather than edited.
- This task must never merge without 143.004-T and 143.012-T: between them the existing unconditional rollback would compensate over an unproven append.
