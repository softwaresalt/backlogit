* `blocked` shipments (`status == "blocked"` or carrying a blocked-manifest seal) are unconditionally refused (`ErrShipmentBlockedManifestSealed` / `ErrInvalidStatus` / `errors.Is(err, blerrors.ErrShipmentConflict)`) even when `Force: true` — in both live (`DryRun: false`) and preview (`DryRun: true`) modes — requiring governed `UnblockShipment` first; `Force: true` with non-empty `Reason` overrides only `active` (and terminal `shipped`/`abandoned`) non-`queued` shipments, never `blocked`.

* Enforce `queued`-only default and blocked-manifest seal: unconditionally refuse `blocked` shipments (`status == "blocked"` or carrying a blocked-manifest seal) with `ErrShipmentBlockedManifestSealed` / `ErrInvalidStatus` / `blerrors.ErrShipmentConflict` even when `opts.Force == true` (in both live and `DryRun` modes), requiring governed `UnblockShipment` first; for other non-`queued` shipments (`active`, `shipped`, `abandoned`), refuse with `blerrors.ErrShipmentConflict` unless `opts.Force == true`, and require non-empty `opts.Reason` (`blerrors.ErrValidation`) whenever `opts.Force == true`.
* Support governed requeue of eligible unstarted claim-assigned `active` members in `RemoveFromShipment` under a durable `remove_item` recovery journal (`Operation: "remove_item"`, `RecoveryPolicy: "rollback"`, `ShipmentID: shipmentID`, `Target: itemID`, `Preimage.Shipment` + `Preimage.Members` containing the removed item's full preimage including `status` and `custom_fields.scheduler_baseline_claim`): for a `queued` shipment, the member remains in `.backlogit/queue/` with `status: "queued"`; when force-removing an `active` member from an `active` shipment, verify the member is an eligible unstarted claim-assigned member (`custom_fields.scheduler_baseline_claim == shipmentID` and no `WORK_STARTED:` comment in its item log for the current claim epoch; refusing already-started active members or members lacking the claim marker with `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`), and transition the member's `status` from `active` back to `queued` while clearing `custom_fields.scheduler_baseline_claim` (and appending a correlated `status_changed` `active -> queued` event to the member's item log). * Support read-only zero-write preview when `opts.DryRun == true`: do NOT call `lockShipmentLifecycleGlobal`, `GetShipment`, or `loadArtifact`; instead check the shipment lifecycle recovery journal directory read-only (refusing with a pending-recovery error if any unfinished journal exists) and read Markdown files directly via `readArtifactFromDiskReadOnly` with zero SQLite, lock-file, or JSONL writes.
* Update `validateShipmentLifecycleJournalRecord` / `loadShipmentOperationJournals` in `internal/core/shipment_ops.go` to accept both `Operation == "remove_item"` (`RecoveryPolicy == "rollback"`, `ShipmentID == shipmentID`, `Target == itemID`, `Preimage.Shipment` = shipment preimage, `Preimage.Members` = member preimages including the removed item's full preimage with its original `status` and `scheduler_baseline_claim`) and `Operation == "move_item"` (`RecoveryPolicy == "rollback"`, `ShipmentID == source_shipment_id`, `Target == target_shipment_id`, `Preimage.Shipment` = source shipment preimage, `Preimage.Members` = source member preimages including the moved member's full preimage with its original `status` and `scheduler_baseline_claim`, and `Preimage.Related` = target shipment preimage) across both `Phase == "intent"` and `Phase == "committed"`, and update `reconcileShipmentLifecycleIntent` / the recovery evidence reader in `internal/core/shipment_recovery.go` so that a `remove_item` or `move_item` journal with `Phase == "committed"` (or matching `phase: "committed"` `shipment_item_removed` / `shipment_item_moved` event(s) in the shipment log(s)) is finalized/cleaned up without rolling back preimages, whereas an uncommitted `Phase == "intent"` journal restores `Preimage.Shipment` (and `Preimage.Related` for `move_item`) and `Preimage.Members` (including `status` and `scheduler_baseline_claim`) in Markdown and SQLite.
