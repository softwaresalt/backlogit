Root cause (R-C, MEDIUM/P1 2/3): readShipmentOperationJournalFile/writeShipmentOperationJournalFile/removeShipmentOperationJournalTempFile discard the validated directory handle (`_ *os.File`) and re-resolve filepath.Join(opsRoot,name) absolute paths; validateShipmentOpsWindowsFileHandle re-checks only the FINAL path string, so a same-canonical-path directory OBJECT swap (rename a different real dir into opsRoot) between validation and use is not defeated -> directory-replacement TOCTOU. Correct fix (per correctness+security review): object-bound handle-relative ops anchored to the validated directory handle - RootDirectory-relative NtCreateFile/NtOpenFile (no-follow) for read/create-temp/remove, and NtSetInformationFile with the native FileRenameInformation class (RootDirectory-relative) for the atomic rename (Windows renameat) - REPLACING MoveFileEx. This achieves parity with the existing Unix shipment_ops_unix.go (Openat/Renameat/unlinkat, O_NOFOLLOW). Post-hoc re-open+identity-compare is NOT sufficient (still check-after-use).
API-boundary correction (rev16, read-only diagnosis): the Win32 SetFileInformationByHandle(FileRenameInfo, class 3) form rejects a non-null RootDirectory relative rename with ERROR_INVALID_PARAMETER on this platform; use the native golang.org/x/sys/windows.NtSetInformationFile(FileRenameInformation, class 10) with the existing FILE_RENAME_INFORMATION-compatible buffer and live RootDirectory handle, converting NTSTATUS through the existing Windows error path. No new syscall/dependency; no FileRenameInfoEx/Ex class, no POSIX flags/class 65, no MoveFileEx, no absolute-path re-resolution. All other correct pieces (buffer/layout, DELETE access, share flags, dir handle, UTF-16 byte length without terminator, no-follow source open) preserved as-is.
