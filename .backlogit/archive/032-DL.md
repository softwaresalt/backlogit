<!-- BEGIN:Problem Frame -->
Backlogit operates as a local, file-backed system with no outbound communication. When significant events occur (shipment shipped, item blocked, feature completed, CI failed), the only way a human learns about it is by checking the backlog or reading agent session output. This creates a visibility gap for team leads, distributed teams, and async workflows. Three categories of external integration are needed, in priority order: (1) NOTIFICATION PUSH (highest priority, immediately useful) -- outbound webhooks to Slack, Teams, Discord, or generic HTTP endpoints when backlog events fire. This requires no inbound infrastructure, no credential complexity beyond a webhook URL, and delivers immediate value for team awareness. (2) GITHUB WEBHOOK RECEIVER -- listen for GitHub events (PR merged, issue closed) and auto-update linked backlog items. Requires inbound HTTP server or polling. (3) BIDIRECTIONAL SYNC -- full two-way sync with Jira, Azure DevOps, or other enterprise trackers. Requires OAuth2/PAT management, conflict resolution, and field mapping. This is the heaviest lift and should come last.
<!-- END:Problem Frame -->

<!-- BEGIN:Options -->
PHASE 1 -- NOTIFICATION PUSH (build first): Option A: Generic Webhook Dispatcher. Post-hooks emit HTTP POST requests to configured webhook URLs with a JSON payload containing event type, item details, and timestamp. hooks.yaml defines endpoints and which events route to which URLs. Uses Go net/http client with configurable timeout and retry. Pro: Works with any webhook-capable service (Slack, Teams, Discord, Zapier, IFTTT). Pro: No inbound server needed. Pro: Minimal credential surface (just URLs, optionally with bearer tokens). Con: Fire-and-forget delivery, no guaranteed receipt. | Option B: Platform-Specific Notifiers. Dedicated Slack and Teams client packages that format rich messages (cards, blocks) with backlog context. Pro: Better visual presentation in each platform. Con: Requires platform-specific SDKs or API knowledge. Con: Maintenance cost for each platform adapter. | PHASE 2 -- GITHUB INTEGRATION: Option C: GitHub Webhook Polling. Periodically poll GitHub API for PR/issue events linked to backlog items via commit SHAs. Update backlog status when PRs merge. Pro: No inbound server. Con: Polling delay. | Option D: GitHub App Webhook Receiver. Run a lightweight HTTP server that receives GitHub webhook events in real time. Pro: Real-time updates. Con: Requires network accessibility and GitHub App configuration. | PHASE 3 -- BIDIRECTIONAL SYNC (build last): Option E: Field-Mapped Sync Engine. Use the existing external_map schema in config.yaml to translate field values between backlogit and enterprise systems (Jira, ADO). Requires connector adapters, OAuth2 flows, and conflict resolution. Pro: Full enterprise integration. Con: Highest complexity, requires credential management.
<!-- END:Options -->

<!-- BEGIN:Chosen Direction -->
Phased delivery with notification push first. PHASE 1 (immediate): Option A -- Generic Webhook Dispatcher. Build a WebhookNotifier that post-hooks call with event payloads. hooks.yaml gains a notifications section with endpoint URLs, event filters, and optional auth headers. The payload is a stable JSON schema (event_type, item_id, title, status, timestamp, details map). Slack and Teams can consume this via their incoming webhook URLs with no platform-specific code. If richer formatting is desired later, platform adapters (Option B) can be added as a follow-up without changing the core dispatcher. PHASE 2 (later): GitHub integration via API polling (Option C) as the conservative first step, with webhook receiver (Option D) as a stretch. PHASE 3 (deferred): Bidirectional sync (Option E) only after the notification and GitHub layers prove stable. Key design decisions: (1) Notification dispatch is async (goroutine) to avoid blocking mutations. (2) Failed notifications log to telemetry.jsonl but do not fail the operation. (3) Webhook URLs are stored in hooks.yaml, never in .backlogit/ artifacts. (4) A configurable rate limiter prevents webhook storms during bulk operations. (5) Sensitive webhook URLs may reference environment variables rather than plaintext.
<!-- END:Chosen Direction -->

<!-- BEGIN:Open Questions -->

<!-- BEGIN:Notes -->
This feature depends on 007-DL (internal lifecycle hooks) for the hook firing mechanism and 008-DL (agent-automation hooks) for the event type definitions. The existing external_map schema in config.yaml (docs/configuration.md lines 655-665) was designed to support Phase 3 field mapping but is not yet consumed by runtime code. Constitution principle IV (Workspace Containment) requires that webhook URLs and credentials never appear in .backlogit/ artifacts (which are Git-committed). They belong in hooks.yaml or environment variables. Constitution principle VI (Single-Binary Simplicity) means the webhook client should use Go net/http, not a third-party HTTP client library. The notification push (Phase 1) is deliberately scoped to be useful within a single sprint -- it requires only an HTTP POST client, a hooks.yaml section, and integration with the post-hook pipeline from 007-DL.
