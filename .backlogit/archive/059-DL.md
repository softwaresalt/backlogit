# Shipment shipped-event audit-log completeness

## Problem Frame

<!-- BEGIN:problem-frame -->
A shipment can persist archived_status: shipped while its append-only JSONL log omits the shipment_status_changed: shipped event. Verified against the clean origin/main baseline 3ec95ee3: moveShipmentStatusWithHeadGuard (internal/core/shipment.go:205) persists the shipment status through persistArtifactWithGuard (line 200) and then emits the audit event through the BEST-EFFORT appendItemEvent (internal/core/shipment.go:660), which warns and returns on lock or append failure. ShipShipment (internal/core/shipment_lifecycle.go:509 -> 524) then proceeds to archiveItems regardless, yielding archived_status: shipped with no shipped event. Confirmed absent on the same baseline: there is NO shipment-scoped ws.shipmentEventAppend seam and NO shipmentEventAppendError classification anywhere in internal/, cmd/, or tests/. The only error-returning appender that exists is appendItemEventErr (internal/core/gate_evidence.go:40), reached through the gate-evidence-only seam ws.gateEvidenceAppend (gate_evidence.go:81). Observed in the field from autoharness stash 84D8E6AB / shipment 114-S.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A: Wrap the whole status-to-archival path in the existing core.MutationEnvelope (internal/core/mutation_envelope.go). Rejected: very high blast radius across the hardened ShipShipment locked closure, its membership lock, the head-drift guard, and the 133-F covering-feature restore.
B (chosen): Create a shipment-scoped, error-returning append seam and route ONLY the active -> shipped transition through a NEW shipment-scoped helper, appendShipmentEventErr, rather than through the gate-evidence-scoped appendItemEventErr (whose messages say "gate evidence" and whose lock and append failures both return untagged errors). Classify the captured append error conservatively, because EventWriter.AppendEvent exposes only error and the default non-durable appendFast path discards the fmt.Fprintf byte count (internal/events/stream.go:243, :290-291): only a PROVEN not-applied outcome compensates through the existing snapshot rollback (the lock failure raised inside appendShipmentEventErr, and any writer error explicitly tagged ErrWriteNotApplied), while ErrWriteIndeterminate AND every untagged or otherwise unclassified append error never roll back and surface a MutationPartialError. Add a report-only doctor audit that detects historical residue without ever rewriting JSONL.
C: Swap the emission to an error-returning appender and always roll back. Rejected: violates the two-class contract documented in docs/compound/2026-07-28-durable-writes-two-class-contract-commit-then-surface.md, because rolling back an indeterminate write can destroy an applied append.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Take Option B, using the new shipment-scoped helper appendShipmentEventErr and the conservative classification recorded above: only a proven pre-write failure compensates, and every unproven or untagged append outcome is treated as indeterminate rather than compensatable. The event writer API is NOT expanded; internal/events stays out of scope, and no artifact may promise short-write or partial-write detection. Sequencing is test-first and non-negotiable: a RED harness lands FIRST on each track and must be observed failing before any production behavior exists; where the harness needs a declaration to compile (the per-workspace seam field on one track, the two finding-type constants plus the doctor option on the other), that declaration ships INSIDE the harness task, carries no behavior, and is exercised only by the failing test, per .github/skills/harness-architect/SKILL.md Step 4.3. There is no separate scaffold task. Then the production seam and appender, then fail-closed routing, then class-aware rollback; and on the detection track, the two findings in dependency order. The durability guarantee is PATH-SCOPED to the governed ShipShipment archival path: generic update and archive producers are not prevented, only detected. Detection (report-only doctor audit) ships inside this feature because historical residue already exists and cannot be repaired by the forward fix. PREVENTION of non-ShipShipment paths that can also produce the residue is explicitly deferred to stash 47B48DB0 so this release unit keeps the audit-log-completeness bug boundary. The doctor audit reports two DISTINCT and separately named findings rather than one conflated finding: missing_shipped_event (archived with archived_status: shipped and no shipped event in the item JSONL) and shipped_unarchived_residue (status: shipped but not archived, the indeterminate residue), because the two states have different causes and different operator responses.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
- Whether the RED harness can inject an ErrWriteNotApplied-classified failure without a production seam. Resolved at PR review cycle 1: no. Real filesystem injection aborts earlier in snapshotShipArtifacts (internal/core/shipment_lifecycle.go:152-164, called at :478, before the transition at :509), so the harness injects through the per-workspace seam field, and that single declaration-only field ships inside the harness task itself so the test compiles and still fails for the intended reason.
- Whether the caller can distinguish a short or partial write from a pre-write failure. Resolved: no. AppendEvent returns only error and appendFast discards the fmt.Fprintf byte count, so the plan classifies every unproven outcome as indeterminate rather than expanding the writer API.
- Whether the shipped-transition change can regress claim (queued -> active) or abandon semantics. Mitigation: the routing is gated on newStatus == ShipmentShipped and the other transitions keep best-effort semantics, asserted explicitly.
- Whether a doctor finding can fire transiently during an in-flight ship. Mitigation: carry the same verify-actual-history caveat that FindingOverArchivedCoveringFeature already uses (internal/core/doctor.go:545).
<!-- END:open-questions -->
