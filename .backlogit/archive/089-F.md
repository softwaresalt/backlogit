        Git-aware archival: use `git mv` to preserve file history when the workspace is a git repo.

        Problem: backlogit archives work items by physically moving the markdown file into the archive folder (plain filesystem rename in internal/core/archive.go ArchiveItem). That is fine when .backlogit/ files are NOT tracked in git, but when they ARE tracked, a raw move breaks git's rename/history tracking and can lose the file's history on archival.

        Requirement: When archiving a tracked artifact inside a git repository, perform the move with `git mv <src> <dest>` so git records it as a rename and file history is preserved. Fall back to the current os.Rename/atomic move when: the workspace is not a git repo, the file is untracked, or git is unavailable.

        Acceptance criteria:
        - Archival detects whether the workspace is a git repo AND whether the specific artifact file is git-tracked before choosing the move strategy.
        - Tracked + in-git-repo -> `git mv` (rename recorded, history preserved). Verify with `git log --follow` on the archived path.
        - Not a git repo / untracked file / git binary missing -> existing filesystem move path (no behavior regression).
        - Restore/unarchive path is symmetric (git mv back when applicable).
        - Windows-safe (destination-exists handling) and errors wrapped with context; fail closed if git mv fails unexpectedly rather than silently falling back and losing history.
        - Decide + document whether git mv leaves the rename staged or unstaged, and keep it consistent with how other .backlogit mutations are committed.

        Scope hint: internal/core/archive.go (ArchiveItem, and the restore/canonicalRestorePath logic); add unit/integration coverage for both git and non-git workspaces.

        (Re-stashed after being removed from PR #194 to keep that PR single-purpose; original intake ID was B32F01CE.)
