DEFERRED follow-up from spike 120-F (conclusion: proceed). Implement a repo-wide, opt-in fsync durability protocol for backlogit's two shared write primitives — atomicfile.WriteFileAtomic and events.EventWriter.AppendEvent — so the whole write path is durable against OS-crash/power-loss, not just process-crash. This is a SEPARATE later release unit and is explicitly NOT part of v1.7.0. Priority is MEDIUM (not low): beyond durability polish, this feature must close a REAL pre-existing Windows process-crash DATA-LOSS window in the shared atomicfile.WriteFileAtomic itself (see scope #3), which affects every canonical artifact write including the size seam.

Design (from findings): add a repo-wide fsync durability sequence to the two shared primitives. Reuse internal/events/fsutil.go's file-content fsync patterns ONLY where their documented constraints hold; do NOT reuse syncWriteFileAtomic verbatim for canonical artifacts — its Windows path pre-removes the destination before rename (internal/events/fsutil.go:63-68, comment: "acceptable for regenerable files"), so a crash in that removal window could DELETE a canonical file. The SAME remove-before-rename data-loss pattern also lives in the shared atomicfile.WriteFileAtomic (internal/atomicfile/atomicfile.go:52-60): on a Windows os.Rename failure it os.Remove(path) then retries rename, so a crash (or a second rename failure) between the remove and the retry leaves the canonical artifact MISSING. Canonical writes need a real Windows atomic-replace / fail-closed strategy (e.g. ReplaceFile/MoveFileEx semantics or a write-then-swap that never leaves the destination missing), not the regenerable-file pre-remove.

Scope requirements:
1. WriteFileAtomic: sync temp file, then (POSIX) fsync the parent directory AFTER rename so the rename itself is durable; gate directory fsync on runtime.GOOS != "windows" (Windows FlushFileBuffers has no directory-handle support).
2. AppendEvent first-create durability: AppendEvent runs os.MkdirAll(logsDir) and opens each per-item log with O_CREATE (internal/events/stream.go:56-60), so the FIRST append to a new log creates a new directory entry (and possibly the logs/ dir). On POSIX, when a per-item log is first created the protocol MUST fsync the containing logs/ directory (and any parent directory MkdirAll just created) BEFORE reporting success — a file-only fsync does NOT persist the new dirent. Subsequent appends need only the file fsync. Windows first-create dirent durability is explicitly best-effort (file-content durability only).
3. Canonical-write Windows strategy (REAL data-loss fix, not polish): replace the Windows remove-before-rename fallback in the SHARED atomicfile.WriteFileAtomic (internal/atomicfile/atomicfile.go:52-60) — which os.Remove(path) then retries rename and can leave the canonical file MISSING on a crash between the two — with a real Windows atomic replace (ReplaceFile/MoveFileEx-style) or a fail-closed strategy that NEVER deletes the destination before the replacement is in place. Apply the same rule to any other canonical-write path (do NOT use the fsutil pre-remove for canonical artifacts). SetArtifactSizeWithProvenance calls WriteFileAtomic directly, so this fix protects the size seam and all canonical writes.
4. Two-class error contract (fail-closed is NOT achievable once the rename commits, because the canonical file is already visibly replaced): (a) Pre-commit (unchanged) failure — any error BEFORE the rename commits (temp write, temp fsync, rename not yet done) leaves the canonical file untouched → return a fail-closed error that is SAFE TO RETRY (operation definitely did not apply). (b) Post-commit (indeterminate) failure — rename succeeded but a subsequent parent/logs-directory fsync fails → the replacement is already visible, so return a DISTINCT indeterminate/"possibly-applied" error, NOT an ordinary retryable failure. Callers MUST NOT blindly retry (a retry may double-apply a status transition or emit duplicate audit events); the correct recovery is durability re-verification/reconciliation on next open (idempotent re-sync of the already-visible file), and audit-event/status-transition writers must treat the operation as possibly-committed. Apply this distinction on critical single-item mutations (size seam, status transitions); bulk regeneration may stay best-effort.
5. Opt-in `durable_writes` mode (default off) so bulk paths keep current performance.
6. Document the platform-asymmetric guarantee (full POSIX power-loss durability including new-file dirents; Windows file-content durability with best-effort dirent). Add regression harnesses mirroring the 040-F/041-S pattern, including a Windows directory-fsync skip assertion, a first-create dirent-durability test, and a post-commit-fsync-failure test asserting the indeterminate (non-retryable) error class and reconcile-on-next-open recovery.
