# CAP-2 (C5189EAF): Harden WriteToolchainManifest final replacement to reuse internal/atomicfile Windows MoveFileEx retry semantics

## Problem Frame

<!-- BEGIN:problem-frame -->
Deferred scope expansion `C5189EAF` from `213.002-T` (`U12`, `213-F`, `214-S`, PR #649 thread `PRRT_kwDORzozKM63bqzH`): `WriteToolchainManifest` in `internal/toolchain/launcher.go:875` uses raw `os.Rename(tmpAbs, dstAbs)` for final replacement instead of reusing `internal/atomicfile`'s Windows `MoveFileEx` sharing-violation retry semantics and durable replacement.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Option A: Keep raw `os.Rename(tmpAbs, dstAbs)` in `WriteToolchainManifest`. Pros: no change. Cons: lacks Windows `MoveFileEx` `MOVEFILE_WRITE_THROUGH` durability and 6-attempt transient `ERROR_SHARING_VIOLATION` / `ERROR_ACCESS_DENIED` backoff when concurrent readers inspect `.backlogit/toolchain.yaml`.
Option B (Recommended): Export directory-handle-relative `ReplaceTempFileInRoot(root *os.Root, dirAbs, tmpRel, dstRel string, durable bool) error` in `internal/atomicfile` (taking the caller's verified absolute directory path `dirAbs` separately from `root` because nested `*os.Root` handles created via `root.OpenRoot(storageDir)` report a relative `root.Name()` like `".backlogit"`) and call it from `WriteToolchainManifest` (`internal/toolchain/launcher.go`) on `storageHandle` and `filepath.Join(abs, storageDir)` after re-verifying destination identity under `storageHandle`, with an injectable seam for deterministic retry/error, parent-directory-swap, and non-CWD workspace unit testing. Pros: reuses `internal/atomicfile`'s Windows `MoveFileExW` sharing-violation retry semantics, permanent-denial detection, and `MOVEFILE_WRITE_THROUGH` durability while preventing any parent storage-directory swap from redirecting replacement outside the workspace and working when the target workspace differs from process CWD. Cons: touches `internal/atomicfile` and `internal/toolchain/launcher.go` (within a 3-file task budget).
Option C: Duplicate `MoveFileExW` syscall retry loop directly inside `internal/toolchain`. Pros: single package. Cons: violates DRY and diverges from `internal/atomicfile`'s tested retry error boundaries.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option B (Selected): Export `ReplaceTempFileInRoot(root *os.Root, dirAbs, tmpRel, dstRel string, durable bool) error` in `internal/atomicfile/atomicfile.go` (performing directory-handle-relative replacement bound to `root` / `root.Open(".")`, verifying on Windows that the pinned directory handle's `GetFinalPathNameByHandle` still matches the canonical `EvalSymlinks(dirAbs)` of the caller-supplied verified absolute directory path `dirAbs` — never `root.Name()`, which is relative for nested `OpenRoot` handles — before invoking `atomicReplace` with its 6-attempt `MoveFileExW` sharing-violation retry and permanent-denial semantics, and on POSIX renaming relative to the pinned directory fd plus `dirFile.Sync()` when `durable` is true), and update `WriteToolchainManifest` in `internal/toolchain/launcher.go` (line 875) to re-verify under `storageHandle.Lstat("toolchain.yaml")` that any existing destination is a regular non-reparse file and then delegate final replacement to `atomicfile.ReplaceTempFileInRoot(storageHandle, filepath.Join(abs, storageDir), tmpName, "toolchain.yaml", true)` through an injectable package seam `replaceToolchainManifestFile`, with regression coverage that swaps the parent storage directory between validation and replacement and tests a target workspace differing from process CWD.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
None. Reusing `internal/atomicfile` avoids duplicating Windows `MoveFileEx` retry logic and preserves `ErrWriteNotApplied` sentinel wrapping.
<!-- END:open-questions -->
