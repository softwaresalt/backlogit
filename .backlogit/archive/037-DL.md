# MCP Merge Sync: Incremental Cache Refresh for .backlogit Drift

## Problem Frame

<!-- BEGIN:problem-frame -->
During long-running agent sessions, external changes to `.backlogit/` files (git merge, manual edits, concurrent MCP processes) cause the SQLite cache to drift from the Markdown source of truth. The only current recovery is `backlogit_sync_index`, which triggers a full `Rehydrate` — a destructive DELETE-all + WalkDir + batch-insert cycle that is expensive, briefly empties the index, and rebuilds stash and log tables unnecessarily when only a few artifact files changed.

We need a lightweight `backlogit_merge_sync` MCP tool that detects which `.backlogit/` files changed since the last sync and performs targeted cache updates: upsert changed artifacts, delete removed ones, and rebuild stash/log indexes only when their source files actually drifted. Full rehydrate remains the safety fallback for ambiguous or large deltas.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: In-memory manifest with mtime tracking (recommended)**

Build an in-memory manifest on the `mcp.Server` struct (which persists for the stdio session lifetime) keyed by relative path. Each entry stores `{path, fileKind, size, mtime, item_id}`. On `merge_sync`, re-walk `.backlogit/`, compare against the manifest, and produce add/change/delete sets. Apply targeted upserts and deletes. Fall back to full rehydrate when the delta exceeds a threshold.

Pros: Simple, no schema changes, leverages existing `Server` struct lifetime, no disk I/O for manifest persistence. Cons: Manifest lost on process restart (first call after restart does a full baseline walk). Acceptable because the existing `Rehydrate` already runs at startup.

**Option B: SQLite-persisted manifest for cross-restart continuity**

Store the manifest in a `file_manifest` table in `backlogit.db`. Survives process restarts.

Pros: Cross-restart continuity. Cons: Adds schema complexity, writes to ephemeral cache on every sync (contradicts CQRS read-only cache spirit), marginal benefit since startup already runs full rehydrate.

**Option C: Content-hash manifest (SHA256 per file)**

Use content hashes instead of mtime for change detection.

Pros: Immune to filesystem mtime quirks. Cons: Requires reading every file on every sync (defeats the purpose of lightweight detection), significant overhead for large workspaces.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option A: In-memory manifest with mtime tracking.**

Rationale:
1. The `mcp.Server` struct already persists for the stdio session lifetime with a `sync.Mutex` for workspace state — adding a manifest field is natural.
2. Startup already runs `Rehydrate`, which can populate the initial manifest as a side effect. No cold-start penalty.
3. mtime is reliable enough for v1: backlogit writes use atomic temp-file-then-rename, which updates mtime deterministically. Git operations also update mtime.
4. Avoids schema changes to the ephemeral cache, keeping the CQRS architecture clean.
5. Content hashing can be added later if mtime proves unreliable in practice — the manifest structure supports swapping the comparison strategy.

**Resolved open questions:**

1. **Manifest storage**: In-memory only (v1). Populated at startup from the initial `Rehydrate` walk, updated on each `merge_sync` call. Lost on restart, rebuilt on next startup.

2. **Trigger mode**: Explicit-only via `backlogit_merge_sync` tool call (v1). Lazy/automatic triggering adds complexity around stale-detection timing and could interfere with in-flight writes. Agents already call sync explicitly; a lighter sync tool is sufficient.

3. **Fallback threshold**: Fall back to full rehydrate when delta exceeds 50% of known manifest entries OR when more than 50 files changed. This keeps the incremental path for the common case (1-10 files changed after a merge) while ensuring correctness for large rebases.

4. **Dry-run mode**: Yes, include a `dry_run` parameter. Returns the detected drift (added/changed/deleted file lists with item IDs) without applying changes. Low implementation cost, high value for agent diagnostics.

5. **Response payload**: Return structured JSON with `{added: [{id, path}], changed: [{id, path}], deleted: [{id, path}], stash_refreshed: bool, logs_refreshed: bool, fallback_used: bool, fallback_reason: string}`. Agents need touched IDs for context invalidation, and fallback visibility for trust calibration.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. **Stash/log rebuild granularity**: The current `rehydrateStash` and `rehydrateItemLogs` are full-rebuild functions. Should v1 implement narrow stash/log rebuilds, or simply trigger the existing full-rebuild functions when their source files appear in the drift set? Recommendation: use existing full-rebuild functions in v1 (they are fast for small workspaces) and optimize incrementally later.

2. **Relocation detection**: If a file moves from `queue/` to `done/` (status change via another process), the manifest sees a delete + add. Should merge_sync detect this as a relocation (same item_id, different path)? Recommendation: yes, detect by item_id match and treat as an update rather than delete+add to avoid unnecessary index churn.

3. **Concurrent merge_sync calls**: The `Server.workspaceMu` mutex already serializes workspace access. Should `merge_sync` hold the mutex for the entire operation (walk + apply), or only during the apply phase? Recommendation: hold only during apply to avoid blocking reads during the walk phase. Use a separate `manifestMu` for manifest access.
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
**Relevant compound learnings:**
- `database-issues/atomic-rehydration-sqlite-transaction-2026-04-08.md`: Rehydrate must be atomic. merge_sync should use per-item upserts within a transaction, not the clear-and-rebuild pattern.
- `db-reliability/sqlite-locked-missing-from-retry-predicate-2026-04-13.md`: All writes must go through `RetryWrite` wrapper.
- `db-reliability/batch-failure-silent-nil-return-anti-pattern-2026-04-13.md`: Propagate all errors; never log-and-swallow.

**Codebase architecture notes:**
- `mcp.Server` struct (server.go:25-36) holds `Workspace`, `Events`, `Telemetry`, `HookEvents`, and a `workspaceMu` — manifest fits naturally here.
- `Rehydrate` (rehydration.go:48) uses 3-phase collect/clear/batch-insert — merge_sync replaces phases 2-3 with targeted upsert/delete.
- `UpsertStashEntry` (stash.go:37) already supports ON CONFLICT DO UPDATE — compatible with incremental stash sync.
- `upsertItemTx` already exists for transactional single-item writes.
- DB connection: singleton pool of 4, WAL mode, 30s busy_timeout, `_txlock=immediate`.

**Contingency item 21E17BFC (singleton MCP server):**
This deliberation's merge_sync addresses the most common drift scenario (external file changes during a session). The singleton server contingency (21E17BFC) targets a different problem: multi-process SQLite contention from parallel MCP clients. Keep 21E17BFC in stash as a contingency — pursue only if the write-retry + batched rehydration fixes (031-F, already shipped) prove insufficient under real multi-client load.

**Relevant code paths for implementation:**
- `internal/mcp/server.go` — add manifest field to Server struct

- `internal/db/rehydration.go` — extract manifest-building logic from Rehydrate walk
- `internal/db/queries.go` — add targeted delete-by-id query
- `internal/db/stash.go` — existing `UpsertStashEntry` supports incremental use
- `internal/db/logs.go` — existing `rehydrateItemLogs` for full log rebuild when needed
