<!-- BEGIN:Problem Frame -->
Backlogit agents (Stage and Ship) currently discover work through explicit polling: querying the backlog, scanning stash entries, or being invoked by the user. There is no mechanism for backlogit to push structured signals to agents when actionable conditions arise. This means: stash overflow goes unnoticed until a human triggers triage; blocked items can sit indefinitely without escalation; feature completion (all subtasks done) does not automatically trigger the review workflow; post-merge closure requires manual invocation. Agent-automation hooks would emit structured events that MCP-connected agents can subscribe to, enabling reactive agent workflows that respond to backlog state changes without polling.
<!-- END:Problem Frame -->

<!-- BEGIN:Options -->
Option A: JSONL Hook Event Queue. Post-hooks from the internal lifecycle hook engine (007-DL) append structured events to a new hooks_queue.jsonl file. A new MCP tool backlogit_poll_hook_events lets agents consume unprocessed events with cursor-based pagination. Agents poll periodically or at session start. Pro: Simple, file-backed, fits CQRS architecture. Pro: Builds on the internal hooks engine (dependency on 007-DL). Con: Requires polling, not truly push-based. Con: No real-time notification. | Option B: MCP Notifications Channel. Use the MCP protocol notification mechanism to push events to connected agents in real time. When a lifecycle hook fires, the MCP server broadcasts a notification to all connected clients. Pro: True push semantics, agents react immediately. Con: Requires MCP clients to support notifications (not all do). Con: Only works while agents are connected. Con: mcp-go SDK notification support may be limited. | Option C: Agent Task Queue. Hook events create lightweight task artifacts (subtask type) in the backlog automatically. Agents discover actionable work through normal queue polling. Pro: Reuses existing backlog infrastructure. Con: Pollutes the backlog with auto-generated tasks. Con: Blurs the line between human-created and system-created work.
<!-- END:Options -->

<!-- BEGIN:Chosen Direction -->
Option A: JSONL Hook Event Queue as the primary mechanism, with Option B (MCP Notifications) as a stretch goal if the mcp-go SDK supports it. Key design decisions: (1) Hook events are appended to .backlogit/hooks_queue.jsonl with a stable schema (timestamp, event_type, item_id, payload, processed flag). (2) A new MCP tool backlogit_poll_hook_events returns unprocessed events and marks them consumed. (3) Built-in event types: stash_overflow (configurable threshold), blocked_stale (configurable duration), feature_review_ready (all children done), post_merge_closure (merge commit tracked), shipment_ready (all items done). (4) Agents can register interest in specific event types via hooks.yaml agent_subscriptions section. (5) This depends on the internal lifecycle hooks engine from 007-DL being implemented first.
<!-- END:Chosen Direction -->

<!-- BEGIN:Open Questions -->
1. What is the right stash overflow threshold -- count-based or age-based or both? 2. How long should blocked_stale wait before emitting (hours? days?)? 3. Should the hook event queue be bounded (rolling window) or unbounded with explicit cleanup? 4. Should agents acknowledge events to prevent re-delivery, or is at-least-once delivery acceptable? 5. Can this integrate with the MCP protocol sampling or notification features for true push delivery?
<!-- END:Open Questions -->

<!-- BEGIN:Notes -->
This feature has an explicit dependency on 007-DL (internal lifecycle hooks) since the agent event queue is populated by post-hooks from that engine. The existing telemetry.jsonl pattern provides a proven model for the append-only queue file. The Stage and Ship agent definitions in .github/agents/ would need updates to document hook event polling as part of their session start protocol. The stash staleness gap documented in compound learnings (stash-staleness-requires-custom-scripting-2026-04-09.md) would be partially addressed by the stash_overflow event type.
