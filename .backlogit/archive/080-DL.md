# Deliberation: Reconstitution Pre-Journal Creation Crash Window vs Bounded Under-Deletion Trade-Off (D3C8D13B / 210-S)

## Problem Frame

<!-- BEGIN:problem-frame -->
During shipment 210-S (209-F / 209.002-T, PR #638) implementation and local review of internal/core/shipment_reconstitute_exec.go, stash entry D3C8D13B was captured as a DEFERRED SCOPE EXPANSION (kind: bug, priority: low) for the pre-journal creation crash window: ReconstituteShipments (applyReconstitution) calls CreateArtifact (internal/core/shipment_reconstitute_exec.go:673) and CreateShipment (internal/core/shipment_reconstitute_exec.go:761) before recordCreated (internal/core/shipment_reconstitute_exec.go:258) journals the newly created feature/shipment ID in state.CreatedIDs (shifted from ~373-379, 454-460, 184-190 at commit c34de142 to :673,761,258 in the current internal/core/shipment_reconstitute_exec.go). If an OS process crashes between CreateArtifact/CreateShipment writing the new file and recordCreated flushing state.CreatedIDs to the reconstitution journal, subsequent crash recovery (rollbackReconstitute) leaves at most one newly created orphan artifact unremoved rather than risking unverified deletion. Under P-021 C6, Stage deliberation (080-DL) is required for every DEFERRED SCOPE EXPANSION entry regardless of priority or apparent shape to confirm the scope boundary and non-blocking disposition for 210-S (PR #638).
<!-- END:problem-frame -->

## Options

* Option A (Chosen — Bounded Under-Deletion Trade-Off in 210-S + Defer Pre-Creation ID Reservation / Correlation Matching in D3C8D13B): Keep the current 209-F / 210-S fail-closed bounded under-deletion trade-off in internal/core/shipment_reconstitute_exec.go:673,761 (zero Go changes in 210-S), where rollbackReconstitute only deletes created artifacts durably recorded in state.CreatedIDs, and defer pre-reserving/journaling the allocated artifact ID prior to CreateArtifact/CreateShipment (or matching unjournaled creations by operation correlation ID) to a future shipment harvested from D3C8D13B.
* Option B (Rejected for 210-S — Refactor CreateArtifact / CreateShipment ID Allocation and Journal Schema Inside 210-S): Modify core ID allocation (CreateArtifact/CreateShipment) or expand reconstituteJournalState to pre-reserve IDs before file creation inside 210-S. Rejected because P-021 C1 forbids expanding the 209-F contract surface into general CreateArtifact/CreateShipment two-phase ID reservation during 210-S remediation, and bounded under-deletion (at most one unreferenced orphan file on a sub-millisecond crash window between file write and journal flush, detectable by backlogit doctor) is explicitly safer than over-deletion.
