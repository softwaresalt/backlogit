# Agent Session Disaster Recovery

## Problem Frame

<!-- BEGIN:problem-frame -->
## Problem

When an agent session terminates unexpectedly — remote server disconnect, power failure, context window exhaustion, accidental terminal close, or MCP process kill — work in progress is lost. The agent must restart from scratch or hope a human can manually piece together state from memory files and checkpoint JSON blobs.

### Why It Matters

Long Ship sessions (harness → build → review → CI → PR) can run for 30+ minutes. Losing that progress means duplicated effort, wasted tokens, and frustrated operators. The Stage pipeline is less affected (shorter sessions) but still benefits from recovery when deliberation or multi-stash triage is interrupted.

### Current State

**Infrastructure-level crash safety is solid** (shipped in 042-S):
- Atomic file writes (temp-then-rename + fsync + short-write guards)
- Crash-safe delete (rename rollback)
- Stale lock recovery (60s TTL)
- DB-FS reconciliation (`backlogit sync` rebuilds from Markdown)
- Hook event sequence checkpoints (idempotent resumption)

**Application-level recovery orchestration is missing**:
- `backlogit_create_checkpoint` writes state but nothing reads it back
- `backlogit_save_memory` is a flat key-value store with no discovery, filtering, or cleanup
- Agents manually scan `docs/memory/` by filename convention — no MCP tool support
- No checkpoint schema — each agent writes ad-hoc JSON
- No checkpoint cleanup — files accumulate indefinitely
- No mid-task resume — tasks are atomic (if a 5-subtask build loop dies at subtask 3, it restarts from 1)

### Scope

**In scope**: Checkpoint discovery tooling, standardized checkpoint schema, agent resume protocol, checkpoint retention/cleanup policy, mid-session crash recovery for Stage and Ship agents.

**Out of scope**: Automatic resume without operator confirmation, cross-machine session migration, real-time session replication, changes to the MCP transport layer (covered by contingency stash item 21E17BFC).
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
## Approach A: Tooling-First (backlogit MCP tools only)

Add new MCP tools for checkpoint lifecycle — discovery, validation, cleanup — and let agents use them however they see fit.

**New tools**: `backlogit_list_checkpoints`, `backlogit_get_checkpoint`, `backlogit_cleanup_checkpoints`

**Pros**: Clean separation; agents remain flexible; tooling is reusable across any agent.
**Cons**: Without standardized checkpoint schema and agent protocol, each agent will use these tools differently, producing inconsistent recovery behavior. Doesn't solve the "what should recovery look like" question.

---

## Approach B: Harness-First (agent protocol changes only)

Upgrade Stage and Ship agent instructions with a standardized checkpoint schema, a mandatory pre-shutdown checkpoint write, and a session-start recovery scan protocol. No new backlogit tools — agents use existing `create_checkpoint` + `save_memory` + file reads.

**Pros**: No Go code changes; faster to ship; focuses on the behavioral gap.
**Cons**: Agents still manually scan files (fragile, token-expensive); no structured discovery; no cleanup mechanism; checkpoint validation requires agents to re-implement the same logic.

---

## Approach C: Hybrid (recommended)

Add essential MCP tools for checkpoint discovery and cleanup in backlogit, AND upgrade agent harness protocols to use them with a standardized schema.

### Backlogit tooling layer:
1. **`backlogit_list_checkpoints`** — list checkpoint files with optional filters (agent, feature, shipment, recency)
2. **`backlogit_get_checkpoint`** — read and validate a specific checkpoint, returning parsed JSON
3. **`backlogit_cleanup_checkpoints`** — archive checkpoints older than N days or linked to archived shipments
4. **Standardized checkpoint schema** — required fields (agent, session_id, phase, shipment_id/feature_id, timestamp, resumable_state) with validation

### Agent harness layer:
5. **Session-start recovery protocol** — both Stage and Ship call `list_checkpoints` filtered to their context; if a recent unresolved checkpoint exists, present it and ask whether to resume
6. **Mid-session checkpoint cadence** — write checkpoints after each major phase transition (harness-complete, per-task-complete, review-gate, CI-pass, PR-ready)
7. **Graceful shutdown hook** — when context window approaches limit, write a final checkpoint before ending
8. **Checkpoint lifecycle** — mark checkpoints as `resolved` when session completes normally; `cleanup_checkpoints` archives resolved + stale entries

**Pros**: Complete solution; structured discovery reduces token waste; standardized schema enables validation; cleanup prevents accumulation; agent protocol ensures consistent behavior.
**Cons**: Requires both Go code and harness changes; larger scope than A or B alone.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
## Chosen: Approach C — Hybrid

### Rationale

The problem spans two layers — tooling (backlogit doesn't support checkpoint discovery) and protocol (agents don't have a standardized recovery workflow). Solving only one layer leaves the other as a gap. The hybrid approach addresses both with a clean separation of concerns:

- **Backlogit owns**: persistence, discovery, validation, and cleanup of checkpoints (MCP tools)
- **Agent harness owns**: when to write checkpoints, how to present recovery options, and how to resume (instructions)

### Key Design Decisions

1. **Interactive resume, not automatic** — on discovery of an interrupted checkpoint, the agent presents the state and asks the operator. This prevents silent incorrect resumption from stale state.

2. **Phase-based checkpoints, not continuous** — checkpoints at phase boundaries (harness-complete, task-complete, review-gate, etc.) balance recovery granularity against write overhead. Sub-task-level checkpointing is out of scope for V1.

3. **Resolved/stale lifecycle** — checkpoints are marked `resolved` on normal session completion. Unresolved checkpoints older than 7 days are auto-archivable. This prevents indefinite accumulation while keeping recent crash evidence available.

4. **Standardized schema with optional extensions** — required fields ensure discoverability; optional fields let agents store workflow-specific state.

5. **Checkpoint cleanup integrated with shipment closure** — when a shipment is archived, its associated checkpoints are eligible for cleanup.

## Open Questions

<!-- BEGIN:open-questions -->
1. **Checkpoint storage location** — Should checkpoints stay in `.backlogit/checkpoints/` (current) or move to a more structured path like `.backlogit/checkpoints/{agent}/{shipment-id}/`? Structured paths improve discovery but add routing complexity.

2. **Cross-process memory safety** — `memories.json` currently uses a process-level mutex but no file lock. Should this be fixed as part of this feature, or is it a separate concern? (Leaning: separate — memories.json is a different persistence surface.)

3. **Checkpoint size limits** — Should there be a max size for checkpoint JSON blobs? Large checkpoints waste tokens when read back. (Leaning: yes, soft limit of 4KB with a warning, no hard rejection.)

4. **Context window detection** — How does the agent reliably detect it's approaching the context window limit? This is client-dependent (Copilot CLI vs. Claude Code vs. Cursor). The graceful shutdown hook may need to be best-effort rather than guaranteed.

5. **Memory file consolidation** — Should `docs/memory/` files be brought into the checkpoint system, or kept separate? Currently agents write markdown memory files AND JSON checkpoints. (Leaning: keep separate — memory files are human-readable session summaries for the knowledge base; checkpoints are machine-readable resume state.)

6. **Retention policy defaults** — 7-day retention for unresolved checkpoints is a starting point. Should this be configurable in `config.yaml`? (Leaning: yes, with 7d default.)
<!-- END:open-questions -->

### Research Findings

**Current checkpoint tool surface** (from codebase scan):
- `backlogit_create_checkpoint(state_dump: string) → {path: string}` — writes raw JSON, no validation
- `backlogit_save_memory(key: string, summary: string) → {ok: true}` — flat key-value, no discovery
- `.backlogit/checkpoints/checkpoint-{YYYYMMDD-HHMMSS}.json` — timestamped files, no schema
- Hook event checkpoints use a separate mechanism (`runtime/hooks/{consumer}.checkpoint.json`) with atomic writes + stale lock recovery — this is a good pattern to follow
