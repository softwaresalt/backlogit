# Copilot CLI Plugin Distribution with Hybrid Binary Resolver

## Problem Frame

<!-- BEGIN:problem-frame -->
backlogit is a workflow OS designed for cross-project reuse, but today onboarding a new project requires manually copying agents, skills, instructions, and MCP server config — plus building or installing the Go binary. The Copilot CLI plugin system (`/plugin install`) offers one-command distribution of agents, skills, and MCP configs, but has no mechanism for distributing native binaries. The binary distribution gap must be solved for the plugin to be functional.

The existing release.yml already cross-compiles backlogit for linux/darwin/windows × amd64/arm64 and publishes binaries to GitHub Releases with SHA256SUMS. This infrastructure can be extended rather than rebuilt.

Success criteria: `copilot plugin install softwaresalt/backlogit` delivers a working backlogit MCP server, agent harness, and skill surface with zero manual setup beyond having Node.js (which Copilot CLI already requires).
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: npm wrapper only (esbuild pattern)**
Platform-specific npm packages contain pre-compiled Go binaries. Plugin's MCP config uses `npx -y @backlogit/backlogit-mcp mcp`. Zero prerequisites beyond Node.js.
- Pro: Cleanest UX, industry standard (esbuild/turbo/swc/Deno)
- Con: No benefit for users who already have backlogit installed natively

**Option B: GitHub Releases download script only**
Plugin includes a wrapper script that downloads from GitHub Releases on first use.
- Pro: No npm publishing infrastructure
- Con: Fragile cross-platform shell scripting, no version management

**Option C: Hybrid resolver (CHOSEN)**
Three-tier resolution: (1) native binary in PATH, (2) npm optional deps, (3) GitHub Releases download fallback.
- Pro: Fast for Go users, still works for everyone else, graceful degradation
- Con: Slightly more complex resolver logic

**Option D: Documented prerequisite only**
Just document `go install` as a prerequisite.
- Pro: Zero infrastructure
- Con: Excludes non-Go users, poor plugin UX
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option C: Hybrid resolver** — The npm wrapper package (`@backlogit/backlogit-mcp`) implements a three-tier binary resolver:

1. **PATH check**: If `backlogit` is already installed (via `go install` or direct download), use it. Zero overhead for existing users.
2. **npm optional deps**: Resolve from `@backlogit/{platform}-{arch}` packages installed as optionalDependencies. This is the esbuild pattern — npm auto-filters to the correct platform.
3. **GitHub Releases fallback**: If optional deps failed (e.g., `--no-optional` flag), download the binary from the latest GitHub Release matching the package version. Verify SHA256.

**Plugin structure**: Lives in the same repo under a `plugin/` directory. The `plugin.json` references `agents/`, `skills/`, and the `.mcp.json` that uses the npm wrapper. Agents and skills are symlinked or copied from `.github/` during the publish step.

**CI extension**: The existing `release.yml` is extended with jobs to (a) package each cross-compiled binary into its platform-specific npm package, and (b) publish all npm packages. Release tag triggers both GitHub Release and npm publish.

**npm scope**: `@backlogit/` — clean namespace for the main package and platform packages.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. **npm org setup**: The `@backlogit` npm scope needs to be registered. Is `softwaresalt` the fallback scope if `@backlogit` is taken?
2. **Which agents/skills to include**: All agents (stage, ship, go-engineer, etc.) or a curated subset? Supporting agents like `go-engineer` and `go-mcp-expert` are backlogit-repo-specific — may not make sense in the plugin.
3. **Instructions files**: Plugin spec doesn't formally support `.instructions.md` files. Options: embed key instructions into agent system prompts, or include them as skill resources.
4. **Version coupling**: Should the npm package version track the Go binary version exactly (same semver), or version independently?
5. **Windows arm64**: Go cross-compiles for windows/arm64 but it's a niche target. Include or skip?
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
**Existing infrastructure**:
- `release.yml` already builds 6 platform binaries and publishes to GitHub Releases with SHA256SUMS
- Makefile has LDFLAGS for version embedding
- Binary naming: `backlogit-{goos}-{goarch}[.exe]`

**Plugin manifest fields** (from docs research):
- `name`, `description`, `version`, `author`, `license`, `keywords`
- `agents`: path to agent .md files
- `skills`: path to skill directories
- `mcpServers`: path to .mcp.json or inline config
- `hooks`: optional session lifecycle hooks

**Platform targets** (matching existing build matrix):
- linux-x64, linux-arm64, darwin-x64, darwin-arm64, windows-x64, windows-arm64

**Key reference**: esbuild's `install.js` handles three fallback tiers and verifies binary integrity. The backlogit resolver can follow the same pattern but add the PATH-first check.
<!-- END:notes -->
