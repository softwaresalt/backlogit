# Support multiple agents through one singleton MCP runtime with session isolation and channel-gated mutations (ECF33C79)

## Problem Frame

<!-- BEGIN:problem-frame -->
Shipped feature 204-F (shipment 205-S, decision 077-DL) enforced a CLI-only OS advisory lock (<storage_root>/runtime/mcp-daemon.lock) so at most one `backlogit mcp` stdio process can run per workspace, failing additional starts with ErrDaemonAlreadyRunning unless `--replace` terminates the existing holder. While this prevented split-brain SQLite and manifest corruption, it does not allow multiple concurrent agents (e.g., Orchestrator, Stage, Ship, or IDE sessions) to maintain simultaneous isolated MCP sessions against one shared workspace runtime. Additionally, mark3labs/mcp-go v0.27.0's `StdioServer.Listen` binds a single static `stdioSessionInstance`, whereas `MCPServer.RegisterSession` and `MCPServer.HandleMessage` support multiple concurrent `ClientSession` instances if paired with per-session stream adapters and internal operation gating. At 2026-11-04T20:15:01Z, in response to 'Should that independent background daemon be the lifecycle model?', the operator confirmed: 'Yes, I think makes sense, but it also means that it either needs an initial startup via the start.ps1 or that it initializes with the first instantiation for the workspace to which this local binary is pinned. It also suggests, perhaps, that available tools should be contained within the so-called sandbox of the workspace itself.' At 2026-11-04T21:41:00Z, in response to 'Should available tools mean backlogit-managed tooling only, or all agent/MCP tools used in the workspace?', the operator confirmed: 'I mean ALL agent/MCP tools used in a workspace.' At 2026-11-04T22:02:03Z, in response to the final product question on containment strength (workspace-local installation, configuration, and version pinning vs OS/container-enforced process, filesystem, and network sandboxing), the operator confirmed: 'For now, workspace-local installation, configuration, and version pinning is sufficient.'
<!-- END:problem-frame -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Decided direction (Q1 confirmed 2026-11-04T20:15:01Z; Q2 = ALL confirmed 2026-11-04T21:41:00Z; Q3 = workspace-local installation, configuration, and version pinning confirmed 2026-11-04T22:02:03Z) and bounded proposals: (1) Adopt Option A independent per-workspace background daemon paired with thin stdio-compatible MCP client session shims so individual client exits never terminate peer sessions (R13, A1). (2) Support both startup entry routes as explicit requirements: optional/idempotent prewarm via start.ps1 and lazy auto-start/connect on the first `backlogit mcp` invocation when not prewarmed, using the same singleton admission (<storage_root>/runtime/mcp-daemon.lock + mcp-daemon.json) and workspace-pinned bin/backlogit.exe binary, converging concurrent startups to one daemon without stale-sidecar false success or split brain (R14). (3) Resolve workspace from explicit/trusted workspace context and local executable association rather than ambient cwd alone or global PATH; verify canonical workspace/storage identity, pinned binary path, and compatible daemon version/build before attach, explicitly refusing mismatches with no silent active-daemon replacement and no global PATH fallback (R15), while keeping daemon-managed state under workspace storage/runtime paths and distinguishing POSIX Unix Domain Socket filesystem paths from the Windows Named Pipe OS namespace (\\.\pipe\... bound to workspace identity with current-user SID DACL, R16). (4) Gate all backlogit runtime-managed MCP mutations sequentially in FIFO order via an internal Go channel coordinator while allowing bounded concurrent read-only calls (R7-R9, A2), preserving cross-process file lock (.backlogit/.locks/) and SQLite WAL/busy_timeout coexistence (R12) and recognizing external/unmanaged writers as a separate boundary concern rather than claiming a universal cross-process broker. (5) Enforce a workspace-owned agent/MCP tool environment across ALL agent/MCP tools used in a workspace (R19-R23, SC10-SC14, A8 superseding narrow assumption A6) at confirmed Level 1 containment strength ('For now, workspace-local installation, configuration, and version pinning is sufficient.'): workspace-local installation, configuration, and version pinning across backlogit, companion MCP servers (engram, graphtor-docs, etc.), CLI helpers, and launcher/adapter configs (.mcp.json, start.ps1, start.sh) with explicit tool inventory, startup provenance/compatibility verification, zero silent global PATH or cross-workspace fallback, explicit host bootstrap prerequisite declarations, backlogit's own canonical workspace path containment (R17) without overclaiming external tool confinement, and honest unsupported/built-in/remote tool reporting (SC13). Defer OS/container sandboxing (Level 2) and OS-level adversarial escape validation out of this initial release (R18, R20, R23, SC14), keep authorized remote service access as a separate policy question (R21), and structure delivery into Track A (workspace tool-environment contract, settled at requirements level), Track B (backlogit multi-session daemon + Go channel coordinator), and Track C (cross-tool adapters, companion MCP alignment, and local identity/pinning negative verification, R22). (6) Keep tools/call synchronous with standard MCP progress/log notifications as an unbundled conservative implementation proposal/assumption (R10, A3, D8), with no persistent async job-ticket API or arbitrary reverse RPC authorized.
<!-- END:chosen-direction -->
