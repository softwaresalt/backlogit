# Make ShipShipment compensation honest and correct the defer ordering

## Description

<!-- BEGIN:description -->
Unit 12, split out of the original Unit 4 at PR review cycle 1 because the combined unit changed more than five functions and breached the 2-hour rule on the riskiest change in the feature. In `internal/core/shipment_lifecycle.go`. (1) Make compensation honest rather than silently partial: in `restoreShipArtifacts` (`:174-230`) apply a PER-CALL bounded retry budget to the per-item log-lock re-acquisition and, if an item still cannot be restored, promote the outcome to `MutationPartialError` with `Class: not-applied` and `CompensationState: partially-compensated` listing the un-restored IDs. Apply the promotion to EVERY per-item failure the loop already records into `errs`, enumerated by construction from the loop body rather than by anchor list: lock acquisition (`:184-188`), the read (`:194`), concurrent-event identification (`:197`), mutated-path removal (`:201`), the file restore (`:207`), the log restore (`:211`), the event replay (`:216`), the reindex (`:220`), and the DB upsert (`:225`). (2) Do NOT introduce an early `return` inside the per-item loop: `unlockItemLog()` is a plain statement at `:227`, not a defer, so an early return leaks a process-global item-log mutex that has no deadline (`internal/events/stream.go:125`); a blanket `defer unlockItemLog()` is also unsafe because `LockItemLogCrossProcess` returns a NIL unlock on error (`internal/events/stream.go:218`, `:226`). Wrap the per-item body in a closure with a nil-guarded defer, accumulate failures, and assemble the promotion after the loop. (3) Express the retry budget as attempts PLUS a wall-clock bound (at most two `itemLogLockWait` periods) and record in the doc comment that the in-process acquisition inside `LockItemLogCrossProcess` is itself unbounded, so the deadline bounds the retry loop rather than any single acquisition; the loop runs inside the closure rollback defer with the membership lock and all artifact locks held. (4) Track `restoreAttempted` and `restoreSucceeded` separately instead of the single `restored` flag (`:352`), allow the outer fallback exactly one retry when the in-lock attempt failed, and pin the full truth table for the interaction with `shipRollbackAttempted` (`:394`) across the success, not-applied, partially-compensated, and indeterminate outcomes so the non-member restore neither runs twice nor is skipped. (5) SWAP the two defer registrations at `:365` and `:375` so `releaseArtifactLocks` unwinds LAST and the non-member fallback unwinds first with the artifact locks genuinely held and the `ctx` markers truthful (`ctx` is reassigned in place at `:468`); nilling the releaser was evaluated and rejected because it would make the fallback unconditionally dead and delete the 133.004-T guarantee for the `collectArchiveCandidateIDs` (`:515`), `attachCommitToItems` (`:520`), and `archiveItems` (`:524`) failure paths. Execution posture: implementation with colocated tests.
<!-- END:description -->

## Acceptance Criteria

<!-- BEGIN:acceptance-criteria -->
- An un-restorable item yields `CompensationState: partially-compensated` naming the IDs, never a silent skip, for every per-item failure source in the loop.
- No `return` statement exists inside the per-item rollback loop, and the unlock is deferred with a nil guard.
- The retry budget carries both an attempt count and a wall-clock bound, and the doc comment records that the in-process acquisition is unbounded.
- The flag truth table for `restoreAttempted`, `restoreSucceeded`, and `shipRollbackAttempted` is documented and asserted, with regressions for both the double-restore and the never-restore directions.
- The defer registrations are swapped and proven by an ORDERING-DISCRIMINATING regression: a test that only asserts a post-closure `archiveItems` failure still restores the covering feature passes before and after the swap and does not qualify. Observe the order directly, for example by asserting the artifact lock is still held when the fallback runs.
- Both colocated tests were written first and observed failing before their corresponding change; the red output is recorded in the task log.
- All three 143.001-T scenarios are green, including scenario 3, and the four existing ship tests stay green unchanged.
