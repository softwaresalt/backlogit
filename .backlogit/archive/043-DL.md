# Telemetry Attribution & Analytics Enhancement

## Problem Frame

<!-- BEGIN:problem-frame -->
The telemetry subsystem (046-F/047-F) already provides a functioning JSONL datastore with incremental ingestion, session correlation, context window metrics, and a reporter with multiple output formats. However, several gaps remain that limit the system's analytical value:

1. **TokensByServer is a set, not a count map.** `SessionSummary.TokensByServer` is typed `map[string]string` — it records which servers were active in a session but does not attribute token usage to servers. The reporter works around this with `proportionalServerTokens()` which estimates server tokens from call counts, but the underlying data model is lossy.

2. **Attribution registry is hardcoded.** `attribution.go` contains a static `defaultPrefixes` map. Adding new MCP servers (graphtor, new engram tools) requires code changes. Plan Review F12 from 046-F explicitly deferred YAML config override.

3. **No cross-session trending.** The reporter shows point-in-time snapshots (one harvest run). There is no way to compare token efficiency across sessions, branches, or time periods — a key value proposition for the telemetry system.

4. **Per-tool token attribution is absent.** Tokens are tracked per model call. Tool calls are tracked separately. There is no linking between the two. Proportional allocation (based on timing proximity or turn-based heuristics) would enable answering "which tools consume the most tokens?"

5. **Session end timestamps are not tracked.** `started_at` exists from `session-store.db` but end time is not captured, making session duration calculations unreliable.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: Fix TokensByServer + expand registry only (minimal)**
- Change `TokensByServer` from `map[string]string` to `map[string]int`
- Move attribution prefixes to YAML config
- Low risk, narrow scope, ~2-3 tasks
- Does not address trending or per-tool attribution

**Option B: Fix data model + add trending views (balanced)**
- Option A scope plus cross-session comparison queries
- Add `--compare` flag or `telemetry trend` subcommand
- Moderate scope, ~4-5 tasks
- Delivers meaningful analytical value without the complexity of per-tool token attribution

**Option C: Full attribution + trending (comprehensive)**
- Option B scope plus per-tool proportional token allocation
- Requires heuristic design (turn-based or timing-based allocation)
- Higher complexity, ~6-7 tasks, some tasks may exceed the 2-hour rule
- Risk: proportional attribution heuristics may be unreliable without request-level correlation data
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option B: Fix data model + add trending views.**

Rationale:
- Fixes the lossy `TokensByServer` data model, which is a real defect
- Attribution registry YAML config was explicitly deferred (F12) and is overdue
- Cross-session trending delivers the analytical value that makes the telemetry system useful for optimization decisions
- Per-tool token attribution (Option C) is deferred: the heuristics are complex and the value is uncertain without request-level correlation data in the log format. If the trending views reveal that server-level attribution is insufficient, per-tool attribution can be added as a follow-up.

The spike entry (2F295E2B) will be folded into this feature as a verification/design task rather than a standalone spike, since the existing code provides enough foundation to plan concretely.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. **JSONL schema migration**: Changing `TokensByServer` from `map[string]string` to `map[string]int` changes the JSONL record schema. Existing records need migration or dual-read support. Which approach?
2. **Trending time dimension**: Should trending compare sessions by date, by branch, or by configurable grouping? Branch-based comparison may be most actionable (compare feature branch token use to main).
3. **Attribution config location**: Should the YAML config live in `.backlogit/config.yaml` (workspace-scoped) or a separate `attribution.yaml`? Leaning toward a new section in `config.yaml` for simplicity.
<!-- END:open-questions -->
