Behavior RED harness pinning the **flat-manifest rollback/snapshot scope contract** (spec §0.5 / SBLK-R28; plan §0.4). It closes the gap that the rev4 cycle mis-scoped as "flatten transitively": the ship/closure **rollback lock + snapshot + restore** set is NOT derived from the `releaseScope` parameter — the closure builds it **independently** at `internal/core/shipment_lifecycle.go:603-612`, appending the covering-feature ancestors (`featureIDs`) **and every descendant** of each (`descendantItems`, BFS on `ParentID`, `IncludeArchived:true`) on top of `{shipmentID} ∪ releaseScope`. That set is what `lockArtifactMutations` locks and `snapshotShipArtifacts` snapshots (and `restoreShipArtifacts` restores on failure). Flattening `releaseScopeItemIDs` alone (`174.057-T`) does NOT flatten this independent expansion. This harness asserts BEHAVIOR only and introduces no production change.

The harness compiles against current code and is RED because today the rollback/lock/snapshot set includes unlisted ancestors and descendants; it turns GREEN only when SCOPE-IMPL-1 (`174.057-T`) neutralizes the `603-612` expansion so the set equals `{shipmentID} ∪ flat explicit manifest` only. Covering-feature status-rollup is a SEPARATE mechanism (the `nonMemberFeatureSnapshots`/`restoreRolledUpNonMemberFeatures` status-revert path), not the artifact snapshot/lock set; this harness scopes ONLY the artifact snapshot/lock/restore set, targeting unlisted **descendant tasks** and the **unlisted ancestor feature** being absent from it. The non-member status-rollup path itself is eliminated by `174.062-T` (SCOPE-IMPL-3) and its concurrency safety is pinned separately by `174.061-T` (SCOPE-RED-E); this harness must not assert over that path.

Scenarios (<4, exactly 3):
1. **Lock/snapshot scope == flat manifest** — for a manifest listing a feature + one child, the artifact-mutation lock set and the `snapshotShipArtifacts` snapshot set equal exactly `{shipmentID, feature, listed-child}`; an unlisted sibling descendant of the listed feature is absent from both. Membership of the lock/snapshot set is by explicit listing, not hierarchy.
2. **Unlisted ancestor feature absent from the snapshot/lock set** — a covering-feature ancestor that is upstream of a listed item but is NOT itself in the manifest is absent from the artifact snapshot/lock set (its status-rollup protection, if any, comes from the separate non-member feature snapshot, not this set).
3. **Restore restores only `{shipment} ∪ manifest` IDs; unlisted descendants cannot be restored** — on a forced closure failure that triggers `restoreShipArtifacts`, only the shipment control record plus the flat manifest IDs (`{shipmentID} ∪ flat manifest`) are restored; an unlisted descendant, never snapshotted, is left untouched and cannot be restored. No unlisted ancestor/descendant is locked, snapshotted, or restored. The shipment control record is the sole non-manifest ID in the transactional set (it must transition); asserting the set is "manifest only" would be incorrect.

Observation seam: the harness may pin the contract via the recorded snapshot set returned by `snapshotShipArtifacts` for the closure, or via a forced-rollback restore assertion — whichever the implementer wires **without introducing a new exported symbol**.

AC: (1) the harness FAILS against the current `603-612` independent expansion and PASSES after `174.057-T`; (2) asserts the rollback lock/snapshot/restore set **set-equals** `{shipmentID} ∪ flat explicit manifest`; (3) asserts an unlisted ancestor feature and an unlisted descendant are absent from the set and cannot be restored; (4) scopes only the artifact snapshot/lock/restore set and does not assert over the separate non-member feature status-rollup path (eliminated by `174.062-T`; concurrency-safety pinned by `174.061-T`). Domain: tests. <4 scenarios.
