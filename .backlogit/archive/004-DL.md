# Data Quality & Tool Efficiency Feature Set

## Problem Frame

<!-- BEGIN:problem-frame -->
MCP tools return oversized payloads (fetch_stash: 34KB, get_queue: 1.2MB) that consume agent context windows. Rehydration creates ghost index entries from JSONL logs when no markdown artifact exists, polluting queue views. No dedicated tool identifies orphaned items or duplicate artifacts across legacy and current ID formats. Stash harvest lacks dedup guards, risking duplicate work item creation.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
Option A: Single feature grouping all 5 items — cohesive "data quality" theme, single shipment, shared test infrastructure. Option B: Separate features per concern — more granular shipping but more overhead. Option C: Prioritize only the two high items (pagination + orphan detection) and defer the rest.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option A: Single feature grouping. All 5 items share the theme of making backlogit's tool surface more reliable and token-efficient. Pagination (64CFF524) and orphan detection (40BB859A) are high priority. Ghost entry fix (B9AD4DFF) and duplicate detection (0CBEE7D8) are medium priority but directly related. Stash harvest hardening (44E3C9D4) rounds out the reliability story. A single feature with 5-7 tasks keeps shipment scope manageable.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. Should pagination be implemented as tool-level limit/offset parameters, cursor-based pagination, or server-side projection (field filtering)? The stash entry suggests limit/offset + field projection. 2. Should ghost entry cleanup be a one-time migration script, a rehydration fix, or both? 3. Should orphan and duplicate detection be MCP tools, CLI commands, or SQL views exposed through query_sql?
<!-- END:open-questions -->
