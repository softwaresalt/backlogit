## Objective

Reorder `db.Open` DSN pragmas in `internal/db/connection.go` (`_pragma=busy_timeout(30000)` first) AND separately diagnose, reproduce, and harden database identity, WAL header persistence, and pooled-connection schema initialization across `internal/db/connection.go` and `internal/db/schema.go` (`F448AA52` / `098-DL` / Unit U4) so pooled SQLite connections (`SetMaxOpenConns(4)`) never open in `delete` journal mode on an uncheckpointed 0-byte main `.db` file or fail with `no such table: commit_links` under concurrent `-race` load.

## Scope and Affected Files

* **Domain**: `code` (`internal/db`)
* **Execution posture**: `test-first`
* **Affected files (3)**:
  * `internal/db/connection.go`
  * `internal/db/schema.go`
  * `internal/db/connection_test.go`

## Implementation Details

1. **Separate Concern A — `busy_timeout` DSN pragma ordering (`internal/db/connection.go`, lines 58-68)**:
   * Place `_pragma=busy_timeout(30000)` FIRST in `q["_pragma"]` before `_pragma=journal_mode(WAL)` and `_pragma=foreign_keys(1)` so every newly opened physical connection in `database/sql`'s pool (`SetMaxOpenConns(4)`) sets its 30-second busy timeout before executing `PRAGMA journal_mode(WAL)`.
2. **Separate Concern B — Database identity, WAL-mode verification, and pooled-connection schema initialization (`internal/db/connection.go` & `internal/db/schema.go`)**:
   * **Root cause of `no such table: commit_links` (distinct from committed WAL visibility)**: Committed WAL frames are already visible to fresh SQLite connections *provided* those connections open in WAL mode (`journal_mode = wal`). However, when `db.Open` creates a brand-new `backlogit.db`, `PRAGMA journal_mode(WAL)` on the empty (0-byte) file sets WAL mode in memory on Connection #1 without writing the 100-byte SQLite header (bytes 18–19 = `0x02, 0x02`) to `backlogit.db` on disk, and `EnsureSchema` writes schema pages to `backlogit.db-wal` while `backlogit.db` on disk can remain 0 bytes. When a second pooled connection (`Conn #2`) opens against a 0-byte main `.db` file while `Conn #1` holds an active lock (or when `PRAGMA journal_mode(WAL)` cannot acquire the lock), SQLite's `PRAGMA journal_mode(WAL)` does **not** return `SQLITE_BUSY` — it returns a single result row `"delete"` with `SQLITE_OK`, which `modernc.org/sqlite`'s `c.exec("pragma journal_mode(WAL)")` ignores! `Conn #2` is then handed to the pool in `journal_mode = delete` (or with an empty cached `pSchema` loaded from the 0-byte main file during `PRAGMA journal_mode(WAL)` before WAL mode took effect), causing its query against `commit_links` to fail with `no such table: commit_links`.
   * In `internal/db/connection.go` (`Open`): verify on initial open that `PRAGMA journal_mode` equals `"wal"` (returning an error if WAL mode was not established), and when the newly opened database file on disk is 0 bytes (empty), materialize the 100-byte WAL database header on disk (via `PRAGMA user_version` / `PRAGMA wal_checkpoint(TRUNCATE)`) before returning `db` so every subsequent pooled connection (`Conn #2`..`Conn #4`) reads `hdr[18]==2 && hdr[19]==2` directly from Page 1 of `dbPath` on open and never starts in `delete` mode on a 0-byte file.
   * In `internal/db/schema.go` (`EnsureSchema` and `EnsureSchemaWithExtensions`): execute schema DDL and `migrations` atomically/deterministically and verify schema readiness (`commit_links` present in `sqlite_schema` and `PRAGMA journal_mode == "wal"`) before returning (do not rely on a best-effort `PRAGMA wal_checkpoint(PASSIVE)` or a main-file byte-size heuristic).
