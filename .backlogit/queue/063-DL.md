        Add a supported, audited, operator-invoked forward repair operation that reconciles ONLY a shipment record whose status is still `queued` although its manifest work items have already advanced consistently beyond queued state.

        Problem: a shipment can end up in a split state where the shipment artifact still reads `queued` while its manifest members (covering feature and tasks) are already `active` or further along. This arises when work legitimately started but the shipment-record transition did not land or was not applied through the claim path (for example an interrupted, externally-mutated, or partially applied activation). There is currently no supported, non-destructive way to correct just the shipment record. The safe report-only behavior already exists upstream: autoharness feature 112-F / shipment 118-S delivered report-only detection and operator guidance for exactly this split state, so an operator can already see and understand the condition but has no sanctioned operation to resolve it. That is why this is low priority - it closes a capability gap rather than an active correctness or data-loss risk.

        Requested behavior contract (the safety boundaries are the requirement; internal design is deliberately left open for deliberation):
        - Target-specific and inspection-gated. The operator names one specific shipment. The operation first inspects actual current state and proceeds only when it matches the narrow, unambiguous split shape it is designed to repair. Ambiguous, mixed, or incompatible states are rejected with a clear explanation rather than repaired on a guess.
        - Forward-only reconciliation. The sole correction is advancing the shipment record to `active` (or the semantically equivalent sanctioned state correction for the observed shape). There is explicitly NO backward `active -> queued` repair.
        - Shipment-record-only. It must update the shipment artifact and nothing else. It must NOT replay the manifest-wide activation that ClaimShipment performs, must NOT mutate member task or feature statuses, and must NOT cascade parent state. Members being already correct is the PRECONDITION for the repair, not something the repair re-establishes.
        - Atomic and concurrency-safe, consistent with existing shipment mutation and rollback handling, so a failed or concurrent invocation can never leave a new torn state.
        - Auditable, emitting structured before / after / result evidence capturing what was inspected, what changed, and the operator justification.
        - Never silent, never automatic. No background or implicit self-healing; explicit operator invocation remains required in all cases.

        Explicit non-goals:
        - Not a generic repair, state-override, or force-transition framework, and not a general stale-evidence repair path.
        - Specifically EXCLUDES the separate DD957688 issue (shipment ship-time gate blocked by an archived task whose recorded gate evidence points at a dangling commit). That is a different problem with a different shape and must not be folded into this operation.
        - Adjacent shipment-lifecycle audit and prevention work in features 143-F and 144-F is related in area but does not provide this operation; neither repairs an under-advanced shipment record.

        Provenance: upstream prerequisite for autoharness tracker 936C68F3, which stays unresolved until backlogit exposes this operation.

        Needs Stage deliberation before planning. Open questions include: the exact surface (CLI, MCP, or both) and whether it should be a governed operation; how the acceptable pre-state is defined precisely (which member statuses beyond queued count as "advanced consistently", and how gaps or descoped members are treated); what justification the operator must supply; and where and how the before/after/result evidence is recorded.
