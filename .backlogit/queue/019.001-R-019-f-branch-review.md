## P2 Findings

### F-1 (P2/manual): QueryItems LIMIT/OFFSET without ORDER BY

**File**: `internal/db/queries.go`
**Issue**: `QueryItems()` appends LIMIT/OFFSET clauses to the query without a preceding ORDER BY clause. SQLite does not guarantee row ordering without ORDER BY, so paginated results are non-deterministic. Callers using `limit=5, offset=5` may see different or repeated rows across pages.
**Recommendation**: Add a default `ORDER BY id ASC` clause before LIMIT/OFFSET when `filters.Limit > 0`. The id column is indexed and provides stable pagination.

---

### F-2 (P2/manual): No stale .lock file detection after crash

**File**: `internal/core/stash_lock.go`
**Issue**: `lockStashFile` creates a `stash.jsonl.lock` sidecar using `O_CREATE|O_EXCL`. If the process crashes while the lock is held, the sidecar file persists and all subsequent stash writes fail with "stash locked by another process" until the sidecar is manually removed.
**Recommendation**: In `lockStashFile`, check the sidecar file's `mtime` before failing. If it is older than a configurable threshold (e.g., 60 seconds), log a warning and remove it as stale before retrying.

---

### F-3 (P2/advisory): Non-atomic rehydration window

**File**: `internal/db/rehydration.go`
**Issue**: `DELETE FROM items` and `DELETE FROM item_deps` run before the WalkDir rebuild begins. If the process crashes between the deletes and the completion of WalkDir, the index is empty. Any query during or after a partial rehydration will return no results.
**Recommendation**: Wrap the full rehydration cycle (DELETE + WalkDir + Upsert) in a single SQLite transaction. This ensures the index is either fully rebuilt or fully rolled back. Per f015 compound learnings, Rehydrate counts are user-visible behavior.

## P3 Findings

### F-4 (P3/advisory): Global stashMu serializes all workspaces

**File**: `internal/core/stash_lock.go`
**Issue**: `stashMu` is a package-level `sync.Mutex`. When multiple `Workspace` instances exist in the same process, all stash mutations across all workspaces serialize on the same lock. In the common single-workspace scenario this is correct and harmless. In multi-workspace server scenarios (e.g., a future MCP server managing multiple projects), this unnecessarily reduces concurrency.
**Recommendation**: No immediate action required. If multi-workspace scenarios arise, replace the global mutex with a per-path mutex map using `sync.Map`.

---

### F-5 (P3/advisory): Offset=0 silently omitted from SQL

**File**: `internal/db/queries.go`
**Issue**: The OFFSET clause is only appended when `filters.Offset > 0`. Callers passing `limit=5, offset=0` get correct behavior (OFFSET 0 = start from row 0 = no effect), but the explicit `OFFSET 0` clause is never emitted. This is semantically correct and SQLite-standard, but may surprise callers reading the generated SQL for debugging.
**Recommendation**: Add a comment near the Offset condition explaining that `OFFSET 0` is intentionally skipped as it is a no-op.
