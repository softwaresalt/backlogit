# Token and context window efficiency telemetry

## Problem Frame

<!-- BEGIN:problem-frame -->
AI agents operating through MCP tool servers (backlogit, autoharness, engram, graphtor-docs) consume tokens and context window capacity with every interaction. Today there is no way to measure the relative efficiency of different tool combinations, harness configurations, or agent workflows within a project workspace. Without quantitative measurement, users cannot tune their setups to reduce cost or improve throughput.

The core tension: the MCP protocol does not expose token usage to tool servers. When Copilot calls `backlogit_create_item`, backlogit sees the tool arguments and returns a result but never receives `prompt_tokens`, `completion_tokens`, the model name, or the session ID. That data flows from the model API response to the Copilot client, not to the MCP server.

However, Copilot CLI's `COPILOT_HOME` environment variable (set via `cpstart.ps1` at each workspace root) scopes all Copilot data to `.copilot/` within the workspace. This means process logs with full token counts, session event JSONL with per-turn output tokens and compaction metrics, and a SQLite session store with session metadata all reside inside the workspace. This data is already being captured automatically with zero additional instrumentation.

The missing piece is a harvester that reads this workspace-scoped Copilot telemetry, correlates it with backlogit task completions, attributes tool calls to their originating MCP servers, and exposes the resulting metrics through backlogit's existing SQL query surface. The headline metric, tokens-per-completed-task, requires task normalization that only backlogit can provide, making this a backlogit-native feature rather than a standalone tool.

## Options

<!-- BEGIN:options -->
### Option A: Rely on raw Copilot CLI telemetry

Read `.copilot/logs/process-*.log` files directly without processing.

Advantages:
* Data is already captured automatically
* Token counts are real API response values
* Per-model-call and per-tool-call events are linked via `model_call_id`

Disadvantages:
* Unstructured format: events are embedded in 50MB+ log files mixed with debug output
* No workspace-scoping logic (solved by `COPILOT_HOME`, but still requires parsing)
* No query surface: raw log files require a custom parser
* No task normalization: cannot compute tokens-per-task without linking to backlogit
* No cross-MCP-server attribution out of the box
* Schema is undocumented and can change without notice

Assessment: Necessary as a data source but insufficient as a solution.

### Option B: Build self-reporting telemetry into backlogit MCP tools

Instruct agents to call `backlogit_log_telemetry` with usage data after each interaction.

Advantages:
* Full control over schema and storage
* Data is workspace-scoped by definition
* Queryable via existing `backlogit_query_sql`

Disadvantages:
* backlogit cannot see token data at runtime (MCP protocol limitation)
* Agent self-reporting is unreliable: agents do not have access to their own token counts
* Only covers backlogit tools, not engram, autoharness, or graphtor-docs
* Self-reporting calls themselves consume tokens (double-counting risk)

Assessment: Insufficient as a data source. The plumbing is useful as an output target.

### Option C: Standalone telemetry harvester tool

Build a separate Go binary that parses `.copilot/` data and writes structured output.

Advantages:
* Clean separation of concerns
* Reusable across workspaces

Disadvantages:
* Tokens-per-task computation requires importing backlogit's event parser, artifact model, SQL schema, and query gate
* The "standalone" tool becomes a de facto backlogit dependency
* Duplicates infrastructure backlogit already provides (JSONL writer, SQLite rehydration, SQL query surface)
* Cannot provide mid-session self-diagnostic feedback through MCP

Assessment: Architecturally isomorphic to building it inside backlogit, but with more moving parts.

### Option D: Workspace telemetry harvester as a backlogit subcommand

Add a `backlogit telemetry` subcommand family that reads `.copilot/` data, writes to `.backlogit/telemetry.jsonl`, rehydrates into `index.db`, and exposes metrics through the existing `backlogit_query_sql` MCP tool.

Advantages:
* Task normalization is native (backlogit owns the task lifecycle)
* Queryable through existing SQL surface (agents and humans use the same interface)
* Rehydration engine already handles JSONL-to-SQLite
* `TelemetryWriter` and `telemetry.jsonl` already exist
* Agents can self-diagnose efficiency mid-session via MCP
* Single binary, no additional dependencies
* Git-tracked, workspace-scoped output

Disadvantages:
* Couples backlogit to Copilot CLI's undocumented log format (mitigated by isolating the parser behind an adapter interface)
* Does not cover non-Copilot MCP hosts without additional adapters

Assessment: Strongest fit, given that the headline metrics depend on backlogit's task model.

### Option E: MCP protocol extension (future)

Wait for the MCP spec to include a `usage` notification from host to server.

Assessment: Does not exist. MCP is not on a trajectory to add this. Indeterminate timeline.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option D: Build telemetry harvesting as a `backlogit telemetry` subcommand family.

Rationale: The dependency chain makes this the natural home.
1. Tokens-per-task (the headline metric) requires knowing which tasks completed during which sessions: that data lives in backlogit's `events.jsonl`
2. Task-type grouping (apples-to-apples comparison) requires artifact type metadata from backlogit
3. Configuration tagging (which agent/skill drove the session) is tracked in backlogit's shipment metadata
4. Queryable output needs the SQL surface backlogit already provides
5. Structured JSONL output uses the `TelemetryWriter` backlogit already has

The `.copilot/` log parser is isolated behind an adapter interface so that future support for Claude Code, Cursor, or other MCP hosts can be added without changing the core metrics pipeline.

### Data sources

Three Copilot CLI data sources per workspace (all under `.copilot/` via `COPILOT_HOME`):

1. `.copilot/logs/process-*.log`: `cli.model_call` events with `prompt_tokens`, `completion_tokens`, `total_tokens`, `cached_tokens`, `duration_ms`, `model`, `session_id`, `request_id`. Also `cli.tool_call` events with `tool_name`, `result_type`, `duration_ms`, `model_call_id`, `session_id`.
2. `.copilot/session-state/*/events.jsonl`: `assistant.message` with `outputTokens` and `requestId`; `tool.execution_complete` with `toolCallId` and `model`; `session.compaction_complete` with `preCompactionTokens` and `compactionTokensUsed.{input,output,cachedInput}`.
3. `.copilot/session-store.db`: SQLite with `sessions` (id, cwd, repo, branch, summary, timestamps) and `turns` (session_id, turn_index, user_message, assistant_response) tables.

### Correlation keys

* `session_id` links process log events to session-state events
* `requestId` links `assistant.message` (session events, has `outputTokens`) to `cli.model_call` (process logs, has `prompt_tokens` + `completion_tokens`)
* `toolCallId` links `tool.execution_complete` to `assistant.message.toolRequests[]` entries
* `model_call_id` in `cli.tool_call` links back to the `cli.model_call` that spawned the tool call

### Tool attribution

Map tool names to MCP servers via prefix matching or a registry:

* `backlogit_*` -> backlogit
* `engram_*`, `unified_search`, `map_code`, `list_symbols`, `impact_analysis` -> engram
* `autoharness_*` -> autoharness
* `graphtor_*` -> graphtor-docs
* `view`, `edit`, `bash`, `glob`, `grep`, `report_intent` -> copilot_builtin

### Metrics framework

Tier 1 (primary efficiency metrics, the ones users tune against):
* Tokens per task: `sum(prompt_tokens + completion_tokens)` for all model calls in session / tasks completed in session
* Context yield ratio: `completion_tokens / prompt_tokens`
* Cache efficiency: `cached_tokens / prompt_tokens`
* Compaction rate: `compaction_events / assistant_turns`
* Compaction cost ratio: `compactionTokensUsed.input / preCompactionTokens`

Tier 2 (diagnostic metrics):
* Turns per task
* Tool calls per turn
* Tool success rate
* Per-server token share
* Retry rate (repeated calls to same target)
* Peak context utilization (`max(prompt_tokens) / max_prompt_tokens`)

Tier 3 (comparative metrics):
* Efficiency delta: `tokens_per_task(config_A) / tokens_per_task(config_B)`
* Context lifespan: turns before first compaction
* Overhead ratio: `(tool_infrastructure_tokens + compaction_tokens) / total_tokens`
* Model efficiency: `tokens_per_task` grouped by model

### Pipeline stages

1. Extract: parse `.copilot/logs/process-*.log` and `.copilot/session-state/*/events.jsonl`; query `.copilot/session-store.db`
2. Correlate: join via `session_id`, `requestId`, `toolCallId`, `model_call_id`
3. Attribute: map tool names to MCP servers via prefix registry
4. Normalize: link to backlogit task completions via `.backlogit/events.jsonl` status-change events; compute tokens-per-task
5. Report: output normalized metrics per session, per server, per model, per time period

### CLI surface

```
backlogit telemetry harvest [--session <id>] [--since <date>]
backlogit telemetry report [--session <id>] [--by tool|server|session|model]
backlogit telemetry compare --baseline <session-id> --candidate <session-id>
backlogit telemetry trend --metric tokens-per-task --window 7d
```

### MCP surface

* `backlogit_telemetry_harvest`: trigger harvest from agent context
* Queryable via existing `backlogit_query_sql` against telemetry tables in `index.db`

## Open Questions

<!-- BEGIN:open-questions -->
1. Process log format stability: Copilot CLI's `cli.model_call` and `cli.tool_call` telemetry events are undocumented. What is the maintenance cost when the format changes? Mitigation: isolate the parser behind an adapter interface with contract tests against known log samples.

2. VS Code Copilot coverage: The current analysis is based on Copilot CLI process logs. VS Code Copilot Chat writes to a different log format (`GitHub Copilot Chat.log` with `ccreq` lines that have latency and model ID but no token counts). Can the VS Code extension's session telemetry be harvested? This needs a spike once the CLI harvester is working.

3. Per-tool token attribution granularity: A single model turn may invoke multiple tools. Tokens are reported per model turn, not per tool call. How should token cost be attributed when one turn calls tools from multiple MCP servers? Options: attribute to primary (first) tool call, split proportionally by tool count, or split proportionally by response size.

4. Task completion attribution: When a session spans multiple tasks, how are session-level token costs allocated? Options: divide evenly across tasks completed in the session, attribute to the task that was active at each turn (requires turn-level task tracking), or report only at the session level and normalize by task count.

5. Historical log retention: `.copilot/logs/` files accumulate and grow large (50MB+ per process). What is the retention policy? Should `backlogit telemetry harvest` mark processed log regions to avoid re-parsing?

6. BS Buster complementarity: BS Buster (github.com/All-The-Vibes/bs-buster) provides qualitative harness evaluation (47 pass/fail checks across five pillars). Its Copilot observer reads VS Code's `GitHub Copilot Chat.log` but captures no token counts. Should backlogit's telemetry reports include qualitative harness quality indicators alongside quantitative efficiency metrics? This is a future consideration, not a launch requirement.
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
### Evidence base

This deliberation was grounded in direct inspection of Copilot CLI telemetry data from this workspace:

* `.copilot/logs/process-*.log` (31 log files): confirmed `cli.model_call` events contain `prompt_tokens_count`, `completion_tokens_count`, `total_tokens_count`, `cached_tokens_count`, `duration_ms`, `model`, `session_id`, `request_id`
* `.copilot/session-state/*/events.jsonl` (23 sessions): confirmed `assistant.message` events contain `outputTokens` and `requestId`; `session.compaction_complete` events contain `preCompactionTokens` and `compactionTokensUsed.{input,output,cachedInput}`
* `.copilot/session-store.db`: confirmed SQLite schema with `sessions` and `turns` tables, indexed by `cwd` and `repository`
* Session `2bda33d2`: 40,572 output tokens across 67 assistant turns and 84 tool executions; compaction event at 136,804 pre-compaction tokens

### cpstart.ps1 pattern

The `COPILOT_HOME=.\.copilot` pattern (via `cpstart.ps1` at each workspace root) is what makes workspace-scoped telemetry possible. Without it, Copilot CLI stores data in the user's global home directory, making per-workspace attribution impossible. This pattern should be documented as a prerequisite for telemetry harvesting.

### Existing backlogit telemetry infrastructure

* `internal/events/telemetry.go`: `TelemetryEntry{Timestamp, EventType, Payload}` struct with `TelemetryWriter` (goroutine-safe JSONL append)
* `internal/mcp/tools.go`: `backlogit_log_telemetry` MCP tool (accepts arbitrary `event_type` + payload)
* `internal/mcp/server.go`: telemetry writer initialized at `.backlogit/telemetry.jsonl`

These provide the output plumbing. The harvester adds the input pipeline (Copilot log parsing, correlation, attribution) and the metrics computation layer.

### BS Buster analysis

BS Buster (github.com/All-The-Vibes/bs-buster) is a TypeScript/Node CLI for evaluating AI agent harnesses. It runs 47 deterministic checks across five pillars: Context Assembly, Tool Integrity, Loop Discipline, Policy Enforcement, and Context Lifecycle. Its Copilot observer parses VS Code's `GitHub Copilot Chat.log` for `ccreq` lines (model name, latency, status) but captures no token counts. The README itself notes "no token tracking" for the Copilot target. BS Buster answers "is this harness well-designed?" (qualitative), while this feature answers "how efficient is this tool combination?" (quantitative). The two are complementary but not overlapping.

### Design principle: reliable relative measurement

Three factors make relative measurement reliable:
1. Consistent work units: always normalize by completed tasks (backlogit provides this)
2. Configuration tagging: each session tagged with active MCP servers, model, and agent/skill combination
3. Apples-to-apples comparison: group by task type before computing efficiency deltas
