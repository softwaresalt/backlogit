The current generic paths demonstrably DROP unknown top-level fields: models.ArtifactFromFrontmatter maps only an enumerated set of known keys into the Artifact struct (id/title/status/artifact_type/parent_id/sprint/priority/custom_fields/timestamps/level/hierarchy_path/assigned_to/owner/commit/labels/dependencies/links/references), so any unknown TOP-LEVEL key has NO carrier and is dropped on read, and core.WriteArtifactFile re-serializes only struct-backed fields (custom_fields survives because it is captured as a nested map; a top-level size/size_source/size_ruleset_version does not). This task must IDENTIFY the exact LOSS POINTS (the enumerated-key mapping in models.ArtifactFromFrontmatter with no top-level extension carrier; the struct-only re-emit in core.WriteArtifactFile) and PROPOSE CONCRETE BRIDGE OPTIONS (for example: add a top-level extension carrier field to the Artifact model captured in FromFrontmatter and re-emitted by WriteArtifactFile; OR store size provenance under the already-preserved nested custom_fields; OR a YAML-node/raw passthrough design) as decision-input. This is EVIDENCE ONLY: it records classification, loss points, and bridge options and asserts NO preservation success condition and NO implementation - the bridge SELECTION is made in 109.004-T. Preservation, where the GENERIC rebuild route provides it (for example a surviving nested custom_fields), is described honestly as SEMANTIC/deep-value equivalence of the top-level extension key/value graph plus canonical, LF-normalized body equivalence and idempotent backlog read/modify/write. On this path the generic reader models.ParseFrontmatter normalizes CRLF to LF across the WHOLE document before ArtifactFromFrontmatter/WriteArtifactFile run, so a CRLF body is canonicalized to LF and its raw bytes are NOT preserved; core.WriteArtifactFile then re-serializes the frontmatter via models.SerializeFrontmatter/yaml.Marshal (which may canonicalize key ordering/quotes/scalar spelling and drops comments/anchors) and writes the already-LF-normalized body through. That LF-normalization and top-level-key drop is specific to the GENERIC rebuild route (models.ParseFrontmatter -> ArtifactFromFrontmatter -> WriteArtifactFile). The size-mutation seam core.SetArtifactSize is the OTHER backlog-writer path and behaves oppositely: it decodes/encodes through internal/mdfront directly (mdfront normalizes CRLF only inside the frontmatter block and never touches the body), so it preserves EXACT body bytes and the FULL frontmatter map including unknown top-level keys, deliberately bypassing the generic rebuild route to avoid the drop (internal/core/artifact_size.go). So mdfront IS on a backlog-writer path (the size seam), and the canonical LF-normalized body-equivalence description above applies ONLY to the generic rebuild route, NOT to SetArtifactSize. Neither path preserves the frontmatter block as raw lexical bytes (both re-emit YAML); only the generic route LF-normalizes the body and drops unknown top-level keys, while SetArtifactSize is exact-body-byte preserving unless a future YAML-node/raw-byte frontmatter design is explicitly chosen.
