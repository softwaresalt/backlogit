Runner-bootstrap PREREQUISITE of the entire baseline-convergence feature `175-F`. This is the STRICT PREDECESSOR of `175.001-T` (U1) and, transitively, of every baseline-remediation member `175.001-T`..`175.098-T`. Single-domain (test/harness authoring plus PowerShell runner scaffolding — one skill domain: verification tooling).

## Why this task exists (bootstrap resolution, PR #449 cycle 2)

Every baseline-remediation member's `<!-- BEGIN:task-lint-contract -->` block invokes the canonical short runner `scripts/verify-task-lint.ps1`, and the feature additionally requires the intermediate-wave runner `scripts/verify-baseline-lint.ps1` and the terminal runner `scripts/verify-terminal-lint.ps1`. None of those three scripts exists on this branch, and no `175.*` remediation member owned creating them. Without an owner, the first replacement shipment `157-S` (U1) would have no executable task-lint command, and folding the runners into `157-S` would exceed that shipment's declared single-task ownership. This task closes that gap by OWNING creation of the three shared runner scripts, and it is chained ahead of the replacement baseline sequence via `176-S -> 157-S` (shipment edge) and `175.099-T -> 175.001-T` (task edge).

## Owned deliverable surface (created by Ship during execution; NOT implemented in this planning PR)

- `scripts/verify-task-lint.ps1` — the canonical short per-task runner invoked by all 98 remediation members' `task_lint_cmd` (`-TaskId <id> -FeatureId 175-F`, with `-Phase Schema|PreCommit|PostCommit` lifecycle screens).
- `scripts/verify-baseline-lint.ps1` — the intermediate-wave monotonicity runner (`-Inventory ... -InventorySha256 ... -Shipment <replacement-shipment-id> -FeatureId 175-F -TerminalTask 175.012-T`).
- `scripts/verify-terminal-lint.ps1` — the terminal zero-warning global runner (`-FeatureId 175-F`), screening BOTH supported GOOS surfaces (`windows`, `linux`) via an in-process `GOOS` override on a single host and emitting the deterministic success marker `TERMINAL-LINT-OK:175-F` only after both surfaces prove zero residual warnings.

These are the ONLY three implementation files this task may create. It creates NO Go source, NO workflow, and modifies NO existing script; the three runners are net-new files under `scripts/`.

## Bootstrap harness (non-vacuous; behavioral, fixture-driven)

BOOTSTRAP INVARIANT (honest, non-vacuous): the task-lint GATE for this member is the owned Go harness `tests/runner_bootstrap_175_099_test.go` invoked as `go test ./tests -run ^TestU175_099_`, NOT a direct invocation of `scripts/verify-task-lint.ps1` — using the runner this task CREATES as its own gate would be a circular self-dependency. The gate MUST COMPILE, and its targeted test MUST EXECUTE, under existing main-branch tooling BEFORE the three runners exist. Compilation and test-outcome are distinct: with the runners absent the harness COMPILES cleanly (the Go build/test binary is unaffected) but its assertions FAIL when the test RUNS, so `go test ./tests -run ^TestU175_099_` reports a test failure and exits NONZERO — this is the expected RED phase, a genuine failing assertion over the missing runner behavior. Only after the three runners are implemented correctly does the same targeted test pass GREEN (exit 0). The pre-implementation `go test` command therefore never reports success; compile success never implies test success. The task-lint command depends on none of the runners pre-existing. This task EXCLUSIVELY OWNS the one deterministic Go harness path `tests/runner_bootstrap_175_099_test.go` (exactly-one-owner; no other member may create it), declaring a single task-scoped Go test function `TestU175_099_RunnerBootstrap` (deterministic `TestU175_099_` unit token).

BEHAVIORAL, NON-VACUOUS COVERAGE (PR #449 cycle 3): existence + AST-parse + param-surface proofs ALONE are vacuous — a no-op script that merely parses and declares the right `param(...)` block would pass them. The harness therefore, AFTER the three runners exist, EXERCISES each runner as a controlled behavioral test subject against harness-authored deterministic fixture workspaces/inputs, asserting deterministic red/green scenarios a no-op implementation cannot satisfy. The harness proves, using ONLY existing main-branch tooling (`go test` + the built-in PowerShell 7 AST parser and fixture-driven runner invocation), the following.

BEHAVIORAL layer (per-runner red/green proof; GREEN only when the runner honors its contract). For EACH runner the harness drives at least these deterministic scenarios against controlled fixtures and asserts the discriminating exit codes/markers:

- `verify-task-lint.ps1` (`-TaskId <id> -FeatureId 175-F`, `-Phase Schema|PreCommit|PostCommit`):
  - IDENTITY-MODEL CONSTRAINT (line-stable): ownership matching MUST use the
    `line-stable-group-multiset/v1` model recorded in the governed inventory — group each
    live golangci-lint issue by the stable key `(path, linter, normalized_message)`
    (fingerprint `sha256(json([path,linter,normalized_message]))`, `normalized_message` =
    NFC + trim + internal-whitespace collapse), count the residual occurrences per owned
    `group_fingerprint`, and require observed residual to EQUAL each owned group's
    `expected_group_residual_after_task`. Matching MUST NOT key on `line`/`column` (those
    are diagnostic only), so a multiline edit that shifts a still-owned occurrence cannot
    make it disappear, and multiplicity is enforced for interchangeable duplicates.
  - GREEN success: a fixture workspace representing a compliant owned target for `<id>` → native exit 0 and the runner's success marker.
  - RED failure propagation: a fixture representing a non-compliant target (a retained owned lint finding / missing required contract element) → native NONZERO exit, no success marker.
  - RED shift-safety (line-stable): a fixture where a compliant edit shifts a still-owned
    occurrence of an owned group to a different line (owned residual stays above
    `expected_group_residual_after_task`) → native NONZERO exit, no success marker; the
    same fixture keyed by exact line would falsely pass, so this scenario proves the
    matcher is line-independent.
  - RED interchangeable-duplicate isolation: a split-group fixture where the target
    resolves a strictly-later slice's occupancy instead of its own (owned residual falls
    BELOW `expected_group_residual_after_task`) → native NONZERO exit.
  - Malformed/missing-input fail-closed: invocation with a missing/empty `-TaskId`, an unknown task id, or a missing `-FeatureId` → native NONZERO exit.
  - Non-vacuity evidence: the GREEN and RED fixtures MUST yield DIFFERENT exit codes (0 vs nonzero); an always-0 or always-nonzero no-op fails at least one scenario.
- `verify-baseline-lint.ps1` (`-Inventory <path> -InventorySha256 <hash> -Shipment <id> -FeatureId 175-F -TerminalTask 175.012-T`):
  - IDENTITY-MODEL CONSTRAINT (line-stable): remaining-baseline monotonicity MUST be
    evaluated as an expected residual multiset per stable `group_fingerprint` — expected
    residual after the completed tasks = each group's `group_multiplicity` minus the summed
    `owned_count` of its completed owners — rejecting missing (owned occurrence resolved by
    no completed owner), extra (a completed owner's occurrence still present, including a
    shifted one), new-fingerprint, and reordered-across-distinguishable-groups findings.
    It MUST NOT compare exact `line`/`column`.
  - GREEN success: a fixture inventory whose actual SHA-256 equals `-InventorySha256` and whose remaining baseline is monotone → native exit 0.
  - RED integrity fail-closed: a fixture inventory whose actual content hash does NOT match `-InventorySha256` (tampered) → native NONZERO exit.
  - RED shifted-descendant (line-stable): a fixture where a completed-owner occurrence was
    shifted to a new line but not resolved (group residual exceeds expected) → native
    NONZERO exit, proving the shift is caught by fingerprint+multiplicity rather than
    silently absorbed.
  - Malformed/missing-input fail-closed: a missing inventory file or malformed inventory content → native NONZERO exit.
  - Non-vacuity evidence: matched-hash vs tampered-hash fixtures MUST yield DIFFERENT exit codes.
- `verify-terminal-lint.ps1` (`-FeatureId 175-F`; internally screens BOTH supported GOOS surfaces `windows` and `linux` via an in-process `GOOS` override on a single host):
  - GREEN success: a fixture workspace with zero residual warnings on BOTH the `windows` and `linux` surfaces → native exit 0 AND the deterministic success marker `TERMINAL-LINT-OK:175-F`.
  - RED windows-surface fail-closed: a fixture carrying an injected residual warning present ONLY under `GOOS=windows` (e.g. on a `_windows.go` path) → native NONZERO exit, no success marker — proving the `windows` surface is independently analyzed.
  - RED linux-surface fail-closed: a fixture carrying an injected residual warning present ONLY under `GOOS=linux` (e.g. on a `_unix.go` path) → native NONZERO exit, no success marker — proving the `linux` surface is independently analyzed.
  - Malformed/missing-input fail-closed: a missing `-FeatureId` or a missing required precondition input → native NONZERO exit.
  - Success-marker assertion: ONLY the both-surfaces-clean GREEN case emits `TERMINAL-LINT-OK:175-F`; no failing case emits it.
  - Non-vacuity evidence: the both-surfaces-clean fixture and EACH single-surface residual-warning fixture MUST yield DIFFERENT exit codes, so a host-only implementation that analyzes just one surface fails at least one RED single-surface scenario.
