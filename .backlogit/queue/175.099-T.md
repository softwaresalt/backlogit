## Why this task exists (bootstrap resolution, PR #449 cycle 2)

Every baseline-remediation member's `<!-- BEGIN:task-lint-contract -->` block invokes the canonical short runner `scripts/verify-task-lint.ps1`, and the feature additionally requires the intermediate-wave runner `scripts/verify-baseline-lint.ps1` and the terminal runner `scripts/verify-terminal-lint.ps1`. None of those three scripts exists on this branch, and no `175.*` remediation member owned creating them. Without an owner, the first replacement shipment `157-S` (U1) would have no executable task-lint command, and folding the runners into `157-S` would exceed that shipment's declared single-task ownership. This task closes that gap by OWNING creation of the three shared runner scripts, and it is chained ahead of the replacement baseline sequence via `176-S -> 157-S` (shipment edge) and `175.099-T -> 175.001-T` (task edge).

## Owned deliverable surface (created by Ship during execution; NOT implemented in this planning PR)

- `scripts/verify-task-lint.ps1` — the canonical short per-task runner invoked by all 98 remediation members' `task_lint_cmd` (`-TaskId <id> -FeatureId 175-F`, with `-Phase Schema|PreCommit|PostCommit` lifecycle screens).
- `scripts/verify-baseline-lint.ps1` — the intermediate-wave monotonicity runner (`-Inventory ... -InventorySha256 ... -Shipment <replacement-shipment-id> -FeatureId 175-F -TerminalTask 175.012-T`).
- `scripts/verify-terminal-lint.ps1` — the terminal zero-warning global runner (`-FeatureId 175-F`).

These are the ONLY three implementation files this task may create. It creates NO Go source, NO workflow, and modifies NO existing script; the three runners are net-new files under `scripts/`.

## Bootstrap harness (non-vacuous; behavioral, fixture-driven)

BOOTSTRAP INVARIANT (honest, non-vacuous): the task-lint GATE for this member is the owned Go harness `tests/runner_bootstrap_175_099_test.go` invoked as `go test ./tests -run ^TestU175_099_`, NOT a direct invocation of `scripts/verify-task-lint.ps1` — using the runner this task CREATES as its own gate would be a circular self-dependency. The gate MUST be buildable and runnable under existing main-branch tooling BEFORE the three runners exist: with the runners absent the harness fails RED (its assertions fail; the Go build itself is unaffected), and with the runners present and behaviorally correct it passes GREEN. The task-lint command therefore never depends on the runners pre-existing. This task EXCLUSIVELY OWNS the one deterministic Go harness path `tests/runner_bootstrap_175_099_test.go` (exactly-one-owner; no other member may create it), declaring a single task-scoped Go test function `TestU175_099_RunnerBootstrap` (deterministic `TestU175_099_` unit token).

BEHAVIORAL, NON-VACUOUS COVERAGE (PR #449 cycle 3): existence + AST-parse + param-surface proofs ALONE are vacuous — a no-op script that merely parses and declares the right `param(...)` block would pass them. The harness therefore, AFTER the three runners exist, EXERCISES each runner as a controlled behavioral test subject against harness-authored deterministic fixture workspaces/inputs, asserting deterministic red/green scenarios a no-op implementation cannot satisfy. It uses ONLY existing main-branch tooling (`go test` + PowerShell 7), constructs every fixture itself in temporary directories, and invokes each runner via a fixed argument vector (Go `exec.Command`-style — no shell string, no interpolation of untrusted content) so NO arbitrary/untrusted shell input is ever executed.

The harness proves, using ONLY existing main-branch tooling (`go test` + the built-in PowerShell 7 AST parser and fixture-driven runner invocation), the following.

STATIC layer (files-present proof; RED before the runners are created):

1. Each of the three runner scripts exists as a tracked, non-ignored, non-empty file under `scripts/`.
2. Each runner script PARSES CLEANLY under the built-in PowerShell AST parser (`[System.Management.Automation.Language.Parser]::ParseFile`) with zero parse errors.
3. Each runner declares its required parameter surface in its `param(...)` block (AST param-block inspection): `verify-task-lint.ps1` declares `TaskId` and `FeatureId`; `verify-baseline-lint.ps1` declares `Inventory`, `InventorySha256`, `Shipment`, `FeatureId`, `TerminalTask`; `verify-terminal-lint.ps1` declares `FeatureId`.

BEHAVIORAL layer (per-runner red/green proof; GREEN only when the runner honors its contract). For EACH runner the harness drives at least these deterministic scenarios against controlled fixtures and asserts the discriminating exit codes/markers:

- `verify-task-lint.ps1` (`-TaskId <id> -FeatureId 175-F`, `-Phase Schema|PreCommit|PostCommit`):
  - GREEN success: a fixture workspace representing a compliant owned target for `<id>` → native exit 0 and the runner's success marker.
  - RED failure propagation: a fixture representing a non-compliant target (a retained owned lint finding / missing required contract element) → native NONZERO exit, no success marker.
  - Malformed/missing-input fail-closed: invocation with a missing/empty `-TaskId`, an unknown task id, or a missing `-FeatureId` → native NONZERO exit.
  - Non-vacuity evidence: the GREEN and RED fixtures MUST yield DIFFERENT exit codes (0 vs nonzero); an always-0 or always-nonzero no-op fails at least one scenario.
- `verify-baseline-lint.ps1` (`-Inventory <path> -InventorySha256 <hash> -Shipment <id> -FeatureId 175-F -TerminalTask 175.012-T`):
  - GREEN success: a fixture inventory whose actual SHA-256 equals `-InventorySha256` and whose remaining baseline is monotone → native exit 0.
  - RED integrity fail-closed: a fixture inventory whose actual content hash does NOT match `-InventorySha256` (tampered) → native NONZERO exit.
  - Malformed/missing-input fail-closed: a missing inventory file or malformed inventory content → native NONZERO exit.
  - Non-vacuity evidence: matched-hash vs tampered-hash fixtures MUST yield DIFFERENT exit codes.
- `verify-terminal-lint.ps1` (`-FeatureId 175-F`):
  - GREEN success: a fixture workspace with zero residual warnings → native exit 0.
  - RED fail-closed: a fixture workspace carrying an injected residual warning → native NONZERO exit.
  - Malformed/missing-input fail-closed: a missing required precondition input → native NONZERO exit.
  - Non-vacuity evidence: zero-warning vs residual-warning fixtures MUST yield DIFFERENT exit codes.

FIXTURE-INJECTABILITY REQUIREMENT (design constraint on the owned runners): each runner MUST accept its inputs via its declared parameter surface and an execution working directory so the harness can drive it against controlled fixtures without mutating live repository state. No fixture content is sourced from outside the harness; all fixtures are deterministic and harness-authored.

RED/GREEN DISCRIMINATOR: before the three scripts are created the harness fails RED at the static existence layer; after creation it passes GREEN ONLY when every runner satisfies BOTH its success and its failure/fail-closed scenarios. Because the harness exercises the runners only as fixture-driven subjects (never as the gate mechanism, and never `scripts/verify-task-lint.ps1` as this task's own lint), it remains independently buildable and runnable under existing tooling at every point and never requires a missing script to pre-exist.
