        CreateCheckpoint accepts malformed JSON and writes a corrupt checkpoint file while returning success.

        Defect (verified at current HEAD b07729386a316384d1d740ac77d60ff7e0ea9a36): in internal/events/memory.go, CreateCheckpoint decides whether an incoming state_dump is a V1 checkpoint by probing with json.Unmarshal(data, &probe) == nil && probe.SchemaVersion == 1. That single condition conflates two different questions: "is this syntactically valid JSON?" and "is this a V1 checkpoint?". When state_dump is malformed or truncated JSON, the probe unmarshal fails, so the condition is false and the V1 branch is skipped entirely - ParseCheckpoint, checkClosedSchemaNamespace, ValidateCheckpoint, Context.Keys() and the re-marshal never run. Control falls through to the legacy path, which hands the raw unvalidated bytes straight to syncWriteFileAtomic. This happens even when the payload plainly begins with {"schema_version":1,... and was obviously intended as a V1 checkpoint: the truncation is exactly what makes the probe fail, so the more V1-shaped-but-broken the input is, the more silently it is treated as legacy.

        Impact: the call returns a success-shaped CreateCheckpointResult (path plus best-effort legacy context keys) and leaves a corrupt checkpoint file on disk. The damage surfaces later and elsewhere: subsequent checkpoint enumeration and recovery correctly fail closed on the malformed record, which under the agent recovery protocols can halt Stage or Ship startup and force operator handoff. The write is reported as good at the moment it happens and only proves bad at the moment an agent needs it.

        Not the defect: the atomic file writer is behaving correctly. syncWriteFileAtomic faithfully and durably persists the bytes it is given; those bytes were already malformed when they arrived. Please do not describe or fix this as backlogit truncating or corrupting a valid payload - the corruption is inherited from the caller-supplied input and the bug is that nothing rejects it.

        Required behavior contract:
        - Establish that state_dump is syntactically valid JSON FIRST, as a separate step, and only then classify it as V1 or legacy. Validity and schema selection must stop being one combined test.
        - Reject unparseable/malformed JSON using this workspace's established typed/structured error behavior, consistently on the core, CLI, and MCP surfaces.
        - On rejection, return no success-shaped result and leave no checkpoint file behind (no partial, no temp remnant). Same "fail before the write" ordering discipline already pinned for the Keys()-before-write case.
        - Preserve legitimate legacy compatibility: input that is valid JSON but lacks schema_version: 1 must keep flowing through the existing legacy path with unchanged behavior. This fix must not turn legacy dumps into rejections.
        - Preserve current V1 behavior for valid V1 payloads: the existing parse, closed-schema-namespace validation, context-key reporting, and atomic persistence must all be unchanged.
        - Add focused regression coverage: a truncated V1-shaped payload that asserts BOTH a typed error is returned AND no checkpoint file exists afterward. Add transport parity coverage only to the extent needed to pin the same contract on CLI and MCP.

        Explicit non-goals and scope boundaries:
        - No generic checkpoint refactor. This is a narrow input-validation ordering fix.
        - No payload size limit. A size cap is not required to close this defect and should only be considered if a later, independent deliberation justifies it on its own merits.
        - No changes to quarantine/abandon disposition behavior (136-F), recovery policy, checkpoint retention, agent templates, or unrelated checkpoint context handling.
        - Do NOT reopen or duplicate the sibling work already shipped under 146-F: 3C7AAC71 (context-key preservation) and 90F2A9F8 (docs-lint continuation). In particular, task 146.011-T added the closed unknown-schema-namespace rejection that runs only AFTER the probe has already succeeded, so it does not and cannot catch this malformed-input fallthrough - the malformed case never reaches it.
