## Findings

### P2-001 — Stale DB entry on cascade-delete failure (`merge_sync.go`)

**File:** `internal/db/merge_sync.go:152-168`

`result.Deleted` is always populated from `diff.Deleted` regardless of whether `DeleteItemCascade` succeeded. When a non-ErrNotFound delete failure occurs, the function logs a warning, then returns `current` as the new manifest. The deleted file is absent from `current`, so future MergeSync calls will not see it in the diff and will never retry the delete. The SQLite index retains the stale entry until a full Rehydrate is manually triggered.

**Recommended fix:** Track which deletes succeeded; only include those in `result.Deleted` and only replace manifest entries for successful deletes. Alternatively, on delete failure, retain the old manifest entry so the next sync detects and retries the delete.

---

### P2-002 — Concurrent calls can overwrite newer manifest with staler snapshot (`tools.go`)

**File:** `internal/mcp/tools.go:746-759`

Two concurrent `handleMergeSync` calls both read `oldManifest = s.manifest` under RLock, then race to write `s.manifest = newManifest` under Lock. If G2 (processing filesystem state at t2 > t1) writes first, G1 (processing t1) can overwrite it with an older snapshot. Subsequent syncs will reprocess G2's changes, causing unnecessary DB upserts. No data corruption (upserts are idempotent via ON CONFLICT REPLACE); correctness is preserved by eventual fallback.

**Recommended fix:** Compare-and-swap via a version counter or timestamp: only update `s.manifest` if the manifest captured during the call is still current.

---

### P3-001 — Double file read per artifact during incremental sync

`extractItemIDFromFrontmatter` opens each artifact in `BuildManifest`. The same file is opened again by `parseMarkdownArtifact` in the upsert loop. Two reads per changed artifact per sync. Low impact for typical workspace sizes.

---

### P3-002 — Delete operations not batched in a transaction

Each `DeleteItemCascade` call is a separate DB operation, producing N round-trips for N deleted artifacts. With WAL mode and RetryWrite, this is safe but suboptimal for large delete batches.
