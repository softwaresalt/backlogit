Plan unit **U6d**. Make a quarantine candidate filter-exempt, matching the shipped parse-failure precedent.

Files: `internal/events/checkpoint_lifecycle.go`, `internal/events/checkpoint_lifecycle_test.go`.

147.011-T computes the conformance verdict before the filter block, but the summary then falls through into `Agent` / `Status` / `ShipmentID` / `FeatureID` / `MaxAge` like any other row, so a non-conforming document is still dropped by a caller filtering on `status: "active"` — and its own `status` field is exactly the untrusted data the feature refuses to rely on. The remediation surface would then be invisible to precisely the query an agent runs at session start.

`ListCheckpoints` already treats one class this way: a document that fails `ParseCheckpoint` is appended and `continue`d **before** the filter block (`internal/events/checkpoint_lifecycle.go:~46-57`). Extend that same exemption to `NeedsQuarantine` summaries rather than inventing a second, narrower rule: **any summary with `NeedsQuarantine: true` bypasses the whole filter block**, exactly as a parse failure does today.

This is deliberately a blanket exemption, not a per-field one. Splitting filters into "lifecycle" and "identity" tiers would require trusting `Agent`, `ShipmentID`, and `FeatureID` read out of a document already judged unsafe to round-trip, and would leave a schema-invalid file with an empty `agent` silently dropped by an agent filter.

**The exemption is a published contract, not silent behaviour** (PR #377 Copilot review cycle 4). A caller that filters on `Status`, `Agent`, `ShipmentID`, `FeatureID`, or `MaxAge` now receives rows that do not match the filter it passed, and today's `ListCheckpoints` doc comment promises the opposite. Update that exported doc comment in the same file and the same commit to state that a summary with `NeedsQuarantine: true` bypasses every optional filter, exactly as a parse failure does, so the contract is legible at the exported boundary rather than only inside this task. The agent-facing `list_checkpoints` MCP description carries the same statement and is owned by 147.014-T (U7b), which now depends on this unit so a published description cannot promise behaviour that has not landed.

`ListCheckpoints` stays strictly read-only.
