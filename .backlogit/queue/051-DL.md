# CLI/MCP command parity phase-2: build the deferred CLI fallbacks worth building

## Problem Frame

<!-- BEGIN:problem-frame -->
Phase-1 (078-F) made the .autoharness fallback map honest and marked a set of tools mcp_only:true. Phase-2 evaluates each deferred tool for genuine CLI value vs intentional-permanent MCP-only, and builds the worthwhile fallbacks over their existing shared core paths, guarded by the U2 drift test.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
- Option A: fill every deferred surface incl. merge_sync + export-command-map enhancement (rejected: folds write-by-default merge_sync + an open binary-vs-registry design question into an additive gap-fill).
- Option B (CHOSEN): value-tiered — build link/hooks/memory/comment/metadata-discovery over clean core paths, flip their registry rows guarded by the drift test, defer merge_sync + the export-map enhancement, keep log_telemetry permanent MCP-only.
- Option C: link-group only (rejected: under-delivers; leaves cheap honest wins undone).
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Option B. Seven tasks: U1 link CLI group; U2 hooks poll/ack; U3 memory save; U4 comment add (+core.AppendComment extraction); U5 metadata types/wit/templates; U6 registry flip + drift-test green (depends U1-U5); U7 discoverability docs update (depends U6). Each code unit is test-first with output-shape parity. Requires plan hardening: no.
<!-- END:chosen-direction -->

## Open Questions
