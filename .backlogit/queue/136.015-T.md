Follow-up hardening identified during 122-S PR review (Copilot, review-fix cycle 5, accepted as
backlog per the 3-cycle review-fix limit rather than blocking merge).

moveNoReplace discards the error from its unwind os.Remove(dst) call when os.Remove(src) fails
after a successful os.Link. If both the source removal AND the unwind removal fail, both src and
dst now exist, but the caller only sees the source-removal error, not the unwind failure. A
subsequent retry then hits ErrCheckpointDestinationOccupied without any signal that this is an
unwind-failure state requiring manual cleanup, rather than a normal occupied-destination case.

Fix: join/return both errors when the unwind also fails, and have QuarantineCheckpoint classify
that combined failure as indeterminate (do not blindly retry) rather than a plain not-applied error.

Files likely touched: internal/core/checkpoint_disposition.go (moveNoReplace).
