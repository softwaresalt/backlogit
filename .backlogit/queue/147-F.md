Checkpoint `abandon` and `resolve` parse a stored checkpoint, mutate the decoded struct, and re-marshal it. Any top-level JSON key that is not modeled on `CheckpointV1` is silently dropped by that round trip. Nested `context` preservation already shipped in 146-F; the top level did not.

Deliberation `docs/decisions/2026-08-24-checkpoint-toplevel-key-disposition-deliberation.md` decided **Option B — refuse to mutate** rather than preserve, and widened the decision on two grounds discovered empirically:

* `ResolveCheckpoint` has **no validity gate at all**. On a legacy document it replaces the whole file with a fabricated skeleton (`schema_version: 0`, empty `agent`, zero `created_at`, empty `context`), destroying every byte of evidence. Both Stage and Ship session-start recovery call it. This is the higher-severity half of the defect.
* A naive refusal would deadlock: `QuarantineCheckpoint` refuses any target that parses and validates, so a valid-but-non-conforming file would have no disposition path at all. Quarantine classification must widen in the same change.

Plan: `docs/exec-plans/2026-08-24-checkpoint-toplevel-key-disposition-plan.md`.
