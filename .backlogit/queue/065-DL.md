# Split crypto-authenticity vs authenticated-authorization into isolated trust-boundary features (#423 follow-up)

## Problem Frame

<!-- BEGIN:problem-frame -->
866FDC8C bundles TWO deferred #423 residuals that both require an EXTERNAL trust anchor backlogit lacks: (1) cryptographic authenticity of delivery evidence (a workspace writer can forge frontmatter+event), closable by verifying a CI/release-system SIGNED delivery attestation; (2) authenticated per-invocation operator AUTHORIZATION (an autonomous caller self-supplies --confirm/TTY), closable by an operator-issued per-invocation credential the agent cannot mint. Preserving these as ONE broad feature conflates THREE distinct trust boundaries (key/anchor lifecycle, evidence-authenticity verification, invocation authorization) with different threat models, blast radii, and independent value.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
(a) Keep as ONE broad security feature (rejected: conflates 3 trust boundaries, wide blast radius, cannot ship incrementally). (b) TWO features split crypto-vs-authz (rejected: both still embed their own key/anchor bootstrap, duplicating trust-anchor lifecycle and creating two divergent verification cores). (c) THREE isolated features: A=external trust-anchor/verification-key lifecycle (bootstrap/store/rotate/revoke, the shared foundation), B=signed delivery-evidence attestation verification (closes residual 1, depends on A), C=authenticated per-invocation operator approval (closes residual 2, depends on A, independent of B).
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
(c) THREE isolated trust-boundary features with A as the shared foundation. Dependency ordering: B depends on A, C depends on A; B and C are mutually independent and may ship in parallel after A. Each is an independently valuable, independently shippable capability with a single clean responsibility, matching the operator directive to favor highly decomposed features with clean trust-boundary separation. This also keeps residual (1) (non-gating, crypto authenticity) and residual (2) (the 167.015-T ratification gate on authenticated authorization) on separate delivery tracks.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
Attestation/signature format and tooling (cosign/sigstore vs minisign vs in-toto) — to be settled in feature-B planning; verification-key storage & rotation model for feature A (workspace config vs external keyring); operator-credential channel for feature C (signed authorization token vs out-of-band approval vs hardware-backed key); whether feature A should expose a general 'trusted verification key' primitive reusable beyond reconcile.
<!-- END:open-questions -->
