DEFERRED follow-up from spike 120-F (conclusion: proceed). Implement a repo-wide, opt-in fsync durability protocol for backlogit's two shared write primitives — atomicfile.WriteFileAtomic and events.EventWriter.AppendEvent — so the whole write path is durable against OS-crash/power-loss, not just process-crash. This is a SEPARATE later release unit and is explicitly NOT part of v1.7.0.

Design (from findings): add a repo-wide fsync durability sequence to the two shared primitives. Reuse internal/events/fsutil.go's file-content fsync patterns ONLY where their documented constraints hold; do NOT reuse syncWriteFileAtomic verbatim for canonical artifacts — its Windows path pre-removes the destination before rename (internal/events/fsutil.go:63-68, comment: "acceptable for regenerable files"), so a crash in that removal window could DELETE a canonical file. Canonical writes need a real Windows atomic-replace / fail-closed strategy (e.g. ReplaceFile semantics or a write-then-swap that never leaves the destination missing), not the regenerable-file pre-remove.

Scope requirements:
1. WriteFileAtomic: sync temp file, then (POSIX) fsync the parent directory AFTER rename so the rename itself is durable; gate directory fsync on runtime.GOOS != "windows" (Windows FlushFileBuffers has no directory-handle support).
2. AppendEvent first-create durability: AppendEvent runs os.MkdirAll(logsDir) and opens each per-item log with O_CREATE (internal/events/stream.go:56-60), so the FIRST append to a new log creates a new directory entry (and possibly the logs/ dir). On POSIX, when a per-item log is first created the protocol MUST fsync the containing logs/ directory (and any parent directory MkdirAll just created) BEFORE reporting success — a file-only fsync does NOT persist the new dirent. Subsequent appends need only the file fsync. Windows first-create dirent durability is explicitly best-effort (file-content durability only).
3. Canonical-write Windows strategy: for canonical artifacts do NOT use the fsutil pre-remove; implement/verify a Windows atomic-replace that is fail-closed and never deletes the destination before the replacement is in place.
4. Opt-in `durable_writes` mode (default off) so bulk paths keep current performance. Fail-closed on critical single-item mutations (size seam, status transitions), best-effort on bulk regeneration.
5. Document the platform-asymmetric guarantee (full POSIX power-loss durability including new-file dirents; Windows file-content durability with best-effort dirent). Add regression harnesses mirroring the 040-F/041-S pattern, including a Windows directory-fsync skip assertion and a first-create dirent-durability test.
