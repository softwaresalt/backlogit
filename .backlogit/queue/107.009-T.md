EXECUTABLE production-contract task (<=2h, width-isolated to internal/docline normalization + serialization seam; corrected for PR #241). Test-first: this task is GATED behind the RED integration regression 107.010-T (tests/integration/docline_extension_compat_test.go), which must be observed FAILING first; this production change turns it GREEN. The current production seam CONTRADICTS the authoritative base/extension contract in TWO places, both of which this task must change: (1) internal/docline/normalize.go folds every non-contract top-level key into the docline namespace (foldUnderDocline), driven by the CLOSED contractFields set in internal/docline/policy.go; and (2) internal/docline/frontmatter.go serializes through BaseFrontmatter.ToMap(), which emits ONLY the base-contract fields plus the docline namespace, so even after the fold is removed, unknown top-level extension keys are DROPPED on serialization because BaseFrontmatter has no carrier for them. Honest scope correction: preserving unknown top-level extension keys REQUIRES a change to internal/docline/frontmatter.go (capture non-contract, non-docline top-level keys in FromMap into a carrier field on BaseFrontmatter and re-emit them unchanged at the top level in ToMap), IN ADDITION to stopping the fold in internal/docline/normalize.go. Per the authoritative contract, docline owns only the base Markdown/frontmatter contract and MUST preserve unknown top-level extension properties (e.g. the backlogit-owned size, size_source, size_ruleset_version) unchanged IN PLACE at the top level, validating/normalizing only its own base fields, and MUST NOT relocate extension fields under docline. Update the contradictory existing unit tests in internal/docline/normalize_test.go (TestNormalize_ContractSurfaceHoldsOnlyContractKeys and TestNormalize_FoldsLegacyTypeUnderDocline, which currently assert every top-level key is a contract field / that non-contract keys are folded away) to assert top-level pass-through. internal/docline/policy_test.go is NOT changed: TestIsContractField remains valid against current HEAD because the closed contract set still governs which base fields docline normalizes and no longer governs relocation of unknown keys. The size-extension regression proof (size/size_source/size_ruleset_version stay top-level and semantically/deep-value equivalent, with unchanged document body bytes and idempotent normalization, never validated/defaulted/emitted, surviving a lint/migration round-trip) lives in the RED task 107.010-T and is out of this task changed-file set. Body bytes and idempotency (Normalize(Normalize(x)) == Normalize(x)) preserved. Scope stays Go-only: this task changes internal/docline/normalize.go, internal/docline/frontmatter.go, and internal/docline/normalize_test.go plus their in-file comments/docs, and makes NO JSON-schema or authoring-guide edits; the correlated non-Go corrections are separate width-isolated sibling tasks in shipment 095-S: 107.011-T opens the docline base JSON schema (schemas/docline/base-frontmatter-v1.schema.json) for declared producer-owned top-level extension fields, and 107.012-T rewrites docs/docline-frontmatter-authoring-guide.md to the inheritance model. No CLI-distribution changes. Ownership stays explicit: top-level pass-through is DOCLINE base-contract behavior; size semantics (validation, defaults, provenance, composition) remain BACKLOGIT-owned and are out of scope here. Codec responsibility here is strictly LOSSLESS SEMANTIC PRESERVATION: docline retains unknown top-level keys as a SEMANTICALLY/deep-value equivalent key/value graph in place at the top level without interpreting, relocating, dropping, or SCHEMA-SANCTIONING them - preserving a key does NOT make it schema-valid. Because the frontmatter codec (mdfront.Encode) reserializes YAML and MAY canonicalize key ordering/quotes/scalar spelling/comments/anchors, this is deep-value equivalence plus unchanged document body bytes and idempotent normalization, NOT raw frontmatter byte/lexical preservation unless a future YAML-node/raw-byte design is explicitly chosen. Schema validity of DECLARED producer extensions is the SEPARATE responsibility of the sibling schema task 107.011-T; preserved-but-undeclared legacy unknown keys stay losslessly preserved but are NOT thereby sanctioned or valid. Preservation (codec) and validation (schema) are intentionally separate responsibilities - there is no missing selective codec migration.
