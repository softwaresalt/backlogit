Documentation task (<=2h, width-isolated to docs/docline-frontmatter-authoring-guide.md; introduced for the PR #241 correction). Depends on the codec pass-through task 107.009-T and the schema task 107.011-T because the guide must describe the FINAL codec + schema behavior, not the current contradictory state. The guide currently says every non-contract key belongs under docline and that migration moves every unknown key there (move, never drop), contradicting the open base/extension contract. Rewrite the ownership model as an INHERITANCE model: docline owns and validates ONLY the base Markdown/frontmatter fields; derived producers such as backlogit OWN top-level extension fields (size, size_source, size_ruleset_version); docline PRESERVES top-level extensions in place but never interprets, defaults, aggregates, validates, or emits them. Explicitly DISTINGUISH declared producer extensions (sanctioned top-level keys per the opened schema 107.011-T) from legacy arbitrary keys, and describe the normalization/migration behavior for each: declared producer extensions stay TOP-LEVEL and byte-unchanged AND are schema-VALID; preserved-but-undeclared legacy arbitrary keys are LOSSLESSLY PRESERVED in place by the codec (107.009-T) - never silently relocated under docline or dropped - but are NOT thereby schema-valid or sanctioned, and lint MAY surface them as undeclared/unsanctioned top-level keys. Document that lossless codec preservation (107.009-T) and schema validation (107.011-T) are intentionally SEPARATE responsibilities, so the guide must not claim that all preserved unknown keys automatically validate, and there is no missing selective codec migration. Name the canonical derived-key location explicitly: TOP-LEVEL. Keep the guide body-preserving and docline-lint-clean. No production code or schema changes in this task.
