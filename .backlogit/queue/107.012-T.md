Documentation task (<=2h, width-isolated to docs/docline-frontmatter-authoring-guide.md; introduced for the PR #241 correction, revised for PR #242 cycle 2 to the authoritative base/derived model). Depends on the codec pass-through task 107.009-T and the schema task 107.011-T because the guide must describe the FINAL codec + schema behavior, not the current contradictory state. The guide currently says every non-contract key belongs under docline and that migration moves every unknown key there (move, never drop), contradicting the open base/extension contract. Rewrite the ownership model as an INHERITANCE model with a clean base/derived split: docline is the BASE contract and owns and validates ONLY the base Markdown/frontmatter fields; docline ACCEPTS additional top-level extension properties (its open base schema no longer rejects them) and PRESERVES them in place through its codec, re-emitting/serializing caller-provided extension properties at the top level when present, but never interprets, defaults, aggregates, validates, or synthesizes them. Derived producers such as backlogit INHERIT/EXTEND the base contract and OWN their extension fields (size, size_source, size_ruleset_version) at the TOP LEVEL; validation of those extension semantics belongs to backlogit's future DERIVED contract, not to docline. The guide must explain the two distinct responsibilities plainly: (1) EXTENSION ACCEPTANCE/PRESERVATION - the base schema accepts extension properties and the codec preserves them at the top level as a semantically/deep-value equivalent key/value graph with unchanged document body bytes and idempotent normalization (the frontmatter codec reserializes YAML and may canonicalize ordering/quotes/scalar spelling/comments/anchors, so this is NOT raw frontmatter byte/lexical preservation); and (2) PRODUCER-OWNED VALIDATION - extension semantics are validated only by the owning producer's derived contract, never by docline. Do NOT introduce a base-layer distinction between declared/sanctioned producer extensions and arbitrary legacy unknown keys, and do NOT imply docline validates extension semantics: the base contract simply accepts and preserves extension properties uniformly. Describe LEGACY MIGRATION honestly and forward-only: the new codec (107.009-T) stops folding NEW unknown top-level keys and preserves them in place, but it does NOT unfold or auto-relocate values already nested under the docline namespace; generic automatic relocation is IMPOSSIBLE because, once nested, docline-owned metadata and previously-folded producer values are indistinguishable. Any known formerly-folded producer keys would therefore require an explicit, MANUAL, bounded migration (re-authored at the TOP LEVEL), never a generic automatic unfold; the tracked corpus has ZERO folded producer keys (docline.size*), so the contract is forward-only with no back-migration required in practice. Migration synthesizes nothing under docline and drops nothing. Name the canonical derived-key location explicitly: TOP-LEVEL. Keep the guide body-preserving and docline-lint-clean. No production code or schema changes in this task.
