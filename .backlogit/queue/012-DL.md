# Core Data Integrity & CQRS Compliance

## Problem Frame

<!-- BEGIN:problem-frame -->
The backlogit system promises a CQRS architecture where Markdown files are the authoritative source of truth and the SQLite database is a disposable, rebuildable cache. Four high-priority stash entries expose that this contract is broken in multiple places:

1. **Semantic links live only in SQLite** (DF8FDB7B) — `item_links` rows are written only to the ephemeral database and explicitly preserved across rehydrate (rehydration.go:47-48), meaning deleting the cache loses link data. This directly violates the disposable-DB promise.

2. **Update and move paths diverge file/DB state** (847DCF02) — `UpdateArtifact` silently skips the Markdown write when `FindArtifactPath` fails but still upserts SQLite (artifacts.go:408-420). `BulkUpdateStatus` commits the DB before best-effort Markdown sync (queue.go:225-230), admitting in comments that it is "DB-authoritative for now." These flows can leave file and DB state diverged until the next rehydrate overwrites one side.

3. **SQLite PRAGMAs applied to one pooled connection** (AE9DB2B6) — `db.Open` sets `foreign_keys=ON` and `busy_timeout=5000` via `db.Exec` on a single pooled connection (connection.go:14-28). New connections may come up with defaults, so foreign keys and busy timeouts are not reliably enforced.

4. **MCP consistency gaps across handler contracts** (C710BEDB) — ErrNotFound surfaces as internal error in some handlers, `handleListShipments` returns a different `custom_fields.items` shape than `get_shipment`, `ensureWorkspace` lazily initializes without synchronization (server.go:101-116), `DeleteAllItemLogs` runs outside the main rehydrate transaction (logs.go:90-98), and item deletion leaves orphaned rows in `item_deps` and `item_links`.

These are not four independent problems — they share code surfaces in `internal/core`, `internal/db`, and `internal/mcp`, and they collectively undermine the reliability of every read and write operation in the system.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: Fix each stash entry independently with targeted patches.**
Pro: Lowest coordination overhead. Each fix ships when ready.
Con: Misses shared surfaces — e.g., fixing links persistence affects rehydration which affects the MCP rehydration contract, so uncoordinated patches risk regressions. Does not establish the Markdown-first write pattern once for reuse.

**Option B: Coordinated body of work fixing all four as a single shipment.**
Fix the foundation layer first (DB connection pragmas, AE9DB2B6), then the persistence model (links durability, DF8FDB7B), then the write-path invariants (Markdown-first, 847DCF02), then the MCP contract cleanup (C710BEDB). This ordering means each layer builds on the fixed layer below it.
Pro: Proper layering — PRAGMA fixes make FK constraints reliable, FK reliability is needed for orphan cleanup in MCP, Markdown-first patterns are needed for links persistence. Shared surfaces are touched once.
Con: Larger change surface per shipment. Requires careful sequencing.

**Option C: Two-phase approach — foundation fixes first, then contract fixes.**
Phase 1 ships AE9DB2B6 (PRAGMAs) and DF8FDB7B (links durability) as foundational. Phase 2 ships 847DCF02 (Markdown-first) and C710BEDB (MCP consistency) once the foundation is stable.
Pro: Smaller blast radius per phase.
Con: Two shipments add pipeline overhead for tightly coupled work. Phase 2 may need to revisit Phase 1 surfaces anyway.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option B: Coordinated single shipment** with bottom-up layering.

Rationale: These four items share code surfaces (`internal/db/connection.go`, `internal/db/rehydration.go`, `internal/core/artifacts.go`, `internal/mcp/tools.go`) and fixing them independently risks regressions on shared paths. The bottom-up ordering resolves real dependencies:

1. **Layer 0: DB connection reliability** (AE9DB2B6) — Constrain the connection pool or apply PRAGMAs per-connection/DSN so that `foreign_keys=ON` and `busy_timeout` are reliably enforced. This must land first because orphan cleanup in Layer 3 depends on FK enforcement.

2. **Layer 1: Links persistence** (DF8FDB7B) — Add a durable representation of typed links (in Markdown frontmatter or a JSONL sidecar), rebuild them during rehydration, and remove the rehydration carve-out that preserves `item_links`. This makes the DB fully disposable for links.

3. **Layer 2: Markdown-first write invariants** (847DCF02) — Make `UpdateArtifact` fail visibly (or create the missing file) instead of silently skipping Markdown. Flip `BulkUpdateStatus` to Markdown-first ordering. Ensure `backlogit_move_item` relocates files when registry routing requires it.

4. **Layer 3: MCP contract hardening** (C710BEDB) — Standardize ErrNotFound mapping, normalize shipment response shapes, add synchronization to `ensureWorkspace`, wrap `DeleteAllItemLogs` in the rehydration transaction, and cascade-delete orphaned rows on item deletion.

This ordering means each layer can rely on the fix below it being present.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. **Links durable format**: Should links be stored in Markdown frontmatter (`links:` YAML key) or in a JSONL sidecar (`.backlogit/item_links.jsonl`)? Frontmatter keeps everything in one file; JSONL avoids modifying existing artifact format.
2. **BulkUpdateStatus rollback**: When Markdown-first write fails partway through a batch, should the entire batch roll back, or should successfully-written items persist while failures are reported?
3. **ensureWorkspace synchronization**: Is `sync.Once` sufficient, or does the workspace need a full mutex for concurrent MCP requests?
4. **PRAGMA enforcement approach**: Should we constrain pool to `SetMaxOpenConns(1)`, apply PRAGMAs via DSN query string (`_pragma=foreign_keys(1)`), or use a `ConnInitHook`?
<!-- END:open-questions -->
