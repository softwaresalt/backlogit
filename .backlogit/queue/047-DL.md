<!-- BEGIN:Problem Frame -->
Agents interacting with backlogit through the MCP surface face a schema discoverability gap. Two related problems exist:

**1. SQL schema not in metadata catalog (ACDF8C2D)**
The backlogit_get_metadata_catalog tool returns workspace config, artifact types, templates, stash config, and MCP tool inventory but does not include the SQLite schema. Agents using backlogit_query_sql must rely on instruction files for schema knowledge. New agents without pre-loaded instructions cannot construct correct queries. Adding a sql_schema section to the catalog response makes the tool surface self-describing.

**2. Telemetry schema not discoverable (1D5578B5)**
The telemetry subsystem harvests data into three JSONL fact tables (tool-calls.jsonl, session-facts.jsonl, telemetry-sessions.jsonl) with typed Go structs. Operators and agents have no CLI-accessible reference for these schemas. A backlogit telemetry schema subcommand would print field names, types, and descriptions for each fact table in text, json, or markdown format.

Both problems share the same root cause: schema metadata lives only in source code and instruction files rather than being programmatically accessible.
<!-- END:Problem Frame -->

<!-- BEGIN:Options -->
**Option A: Catalog-only approach**
Add sql_schema section to MetadataCatalog with SQLite table definitions. Telemetry schema included as additional tables. CLI gets no new subcommand.
- Pro: Single source of schema truth via existing MCP tool
- Con: CLI users have no offline schema reference; telemetry JSONL schemas are not SQLite tables

**Option B: Dual-surface approach (recommended)**
1. Add sql_schema section to MetadataCatalog for SQLite tables
2. Add backlogit telemetry schema CLI subcommand for JSONL fact table schemas
3. Optionally add MCP tool backlogit_telemetry_schema for agent access
- Pro: Each schema surface gets its natural discovery path
- Con: Two implementation units instead of one

**Option C: Schema subcommand only**
Add backlogit schema command that prints both SQLite and telemetry schemas. No catalog changes.
- Pro: Unified CLI experience
- Con: Agents still lack programmatic schema access via MCP
<!-- END:Options -->

<!-- BEGIN:Chosen Direction -->
**Option B: Dual-surface approach.** Each schema surface gets its natural discovery channel:

1. **SQL schema in metadata catalog**: Add a sql_schema section to MetadataCatalog containing table names, columns (name, type, nullable), indexes, and FTS virtual tables. Schema extracted from backlogit.db at runtime using PRAGMA table_info and PRAGMA index_list. Catalog always reflects the actual database schema.

2. **Telemetry schema CLI subcommand**: Add backlogit telemetry schema that prints a human-readable reference of each JSONL fact table. Schema metadata derived from Go struct tags on ToolCallFact, SessionFact, and SessionSummaryRecord. Output formats: text (default), json, markdown.

**Scope:**
- In: SQL schema in catalog, telemetry schema CLI
- Out: MCP telemetry schema tool, schema validation, schema migration tooling

**Success criteria:**
- backlogit_get_metadata_catalog response includes sql_schema with all tables
- backlogit telemetry schema prints fact table definitions in text/json/markdown
- Both surfaces are tested with contract and unit tests
- Agent instruction file backlogit-sql-schema.instructions.md references the catalog as primary source
<!-- END:Chosen Direction -->

<!-- BEGIN:Open Questions -->
- Should the SQL schema section include example queries or just table definitions? Recommendation: table definitions only; example queries belong in instruction files.
- Should telemetry schema also cover SQLite telemetry tables (telemetry_sessions, telemetry_tool_usage)? Recommendation: yes, include as a separate sqlite_tables section.
<!-- END:Open Questions -->
