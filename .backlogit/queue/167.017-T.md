Stable item-log lock identity for the reconcile transaction C lock. LockItemLogCrossProcess (stream.go:210) recomputes the sidecar PATHNAME and opens it through the CURRENT logs directory (stream.go:172-180), so after a logs-dir RECONFIGURATION/replacement two lockers open DIFFERENT inodes and do NOT mutually exclude. Give C a STABLE, NON-SWAPPABLE lock IDENTITY so reconcile (and any co-acquirer on the same shipment item) reliably mutually excludes: (a) the itemID is ENCODED into a SINGLE safe filename component (as artifactMutationLockPath does - reject/encode path separators so no traversal/symlink escape via a contained multi-component id); (b) the lock helper opens the sidecar HANDLE-BOUND through a validated .backlogit/.locks/itemlog directory HANDLE with no-follow/reparse-safe semantics (NOT by pathname); (c) the sidecar lives under a DISTINCT item-log-lock NAMESPACE (.backlogit/.locks/itemlog/<encoded-itemID>) so it does NOT ALIAS the membership lock A (.backlogit/.locks/<shipmentID> -> .<shipmentID>.lock; a shipment item has itemID==shipmentID, so a shared root would collapse the A/C distinction). C MUST be a resource DISTINCT from membership lock A, and NOT relative to the swappable logs directory. SCOPE BOUND (PR #424 review, thread ft-pC): the guarantee is stability across logs-directory RECONFIGURATION/replacement (the input that actually varies at runtime). Defending against an adversarial rename of the .backlogit/.locks ROOT itself is EXPLICITLY OUT OF SCOPE - no existing lock in the codebase defends that (membership lock A and artifact lock B open their roots by path too, task_lock.go:50-72); it is the same repository-wide threat-model boundary, not a reconcile-specific gap. TDD: a test proves two lockers mutually exclude on the same item INCLUDING after a logs-dir swap. Single domain (lock-identity). Domain: code (concurrency). Blocks 167.019/167.011. ROLLING-UPGRADE / MIGRATION SAFETY (PR #424 review): the lock-identity migration cannot be transparently bridged across BOTH a mixed old/new process fleet AND a logs-directory replacement - an old process is inode-bound to the legacy sidecar in the OLD directory, so after a directory replacement a new process opening the legacy sidecar in the NEW directory shares no lock with it (a dual-lock bridge only helps WITHIN the SAME logs directory). Therefore the migration REQUIRES OPERATIONAL QUIESCENCE: the lock-identity switch (and any logs-directory replacement) MUST be performed only when NO old-version process is running (drain/quiesce the CLI+MCP fleet), enforced by a version-compatibility gate. Within a single-version fleet the stable handle-bound identity holds; a logs-directory RECONFIGURATION (config value change with no concurrent old-version process) is safe because all processes resolve the same stable identity. A concurrent directory replacement during mixed-version operation is EXPLICITLY out of scope and MUST be prevented by the quiescence gate, not by a lock bridge. A runtime point-in-time check (e.g. "is an old-identity lock currently held") is INSUFFICIENT to enforce quiescence: an IDLE old-version process passes the check then acquires the legacy lock immediately after. Because legacy binaries predate this change they CANNOT be retrofitted to honor a new lease/gate, so the legacy->stable lock-identity migration REQUIRES full-fleet SHUTDOWN of all old-version processes as an EXTERNALLY-VERIFIED DEPLOYMENT PRECONDITION (stop-the-world operational step enforced by the deployment process + operator runbook, NOT by runtime code). The NEW code writes a durable version marker so a FUTURE new->newer migration (where both sides honor a lease) can use a runtime lease. TDD/docs: the operator runbook documents the stop-the-world precondition; a test asserts the new code writes the version marker and that, within a single (new) version, the stable identity mutually excludes across a logs-dir reconfiguration.
