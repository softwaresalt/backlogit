Stable item-log lock identity for the reconcile transaction C lock. LockItemLogCrossProcess (stream.go:210) recomputes the sidecar PATHNAME and opens it through the CURRENT logs directory (stream.go:172-180), so after a logs-dir RECONFIGURATION/replacement two lockers open DIFFERENT inodes and do NOT mutually exclude. Give C a STABLE, NON-SWAPPABLE lock IDENTITY so reconcile (and any co-acquirer on the same shipment item) reliably mutually excludes: (a) the itemID is ENCODED into a SINGLE safe filename component (as artifactMutationLockPath does - reject/encode path separators so no traversal/symlink escape via a contained multi-component id); (b) the lock helper opens the sidecar HANDLE-BOUND through a validated .backlogit/.locks/itemlog directory HANDLE with no-follow/reparse-safe semantics (NOT by pathname); (c) the sidecar lives under a DISTINCT item-log-lock NAMESPACE (.backlogit/.locks/itemlog/<encoded-itemID>) so it does NOT ALIAS the membership lock A (.backlogit/.locks/<shipmentID> -> .<shipmentID>.lock; a shipment item has itemID==shipmentID, so a shared root would collapse the A/C distinction). C MUST be a resource DISTINCT from membership lock A, and NOT relative to the swappable logs directory. SCOPE BOUND (PR #424 review, thread ft-pC): the guarantee is stability across logs-directory RECONFIGURATION/replacement (the input that actually varies at runtime). Defending against an adversarial rename of the .backlogit/.locks ROOT itself is EXPLICITLY OUT OF SCOPE - no existing lock in the codebase defends that (membership lock A and artifact lock B open their roots by path too, task_lock.go:50-72); it is the same repository-wide threat-model boundary, not a reconcile-specific gap. TDD: a test proves two lockers mutually exclude on the same item INCLUDING after a logs-dir swap. Single domain (lock-identity). Domain: code (concurrency). Blocks 167.019/167.011.
 ROLLING-UPGRADE TRANSITION (PR #424 review): migrating writers from the log-adjacent sidecar (logs/.<id>.jsonl.lock) to the new .backlogit/.locks/itemlog identity creates TWO independent lock domains while an OLDER backlogit/MCP process is still running (old locks the legacy sidecar, new locks the new sidecar -> concurrent mutation of the same JSONL). REQUIRED transition protocol: during the migration window every writer DUAL-LOCKS BOTH the legacy log-adjacent sidecar AND the new stable-identity lock in a FIXED order (legacy sidecar FIRST, then the new identity) so a mixed old/new process fleet still mutually excludes via the legacy lock while new processes also gain the stable identity. Retiring the legacy lock is a FUTURE cleanup gated on full-fleet upgrade (documented, not done here). TDD: a mixed-identity test proves an old-style locker and a new-style locker still mutually exclude on the same item.
