Plan unit **U8b**. Cross-surface parity from one stored state.

Files: `internal/cli/checkpoint_parity_test.go` (new). **No production change.**

U6/U6b/U6c/U7/U7b/U8/U8c each assert their own surface in isolation. Nothing yet asserts that CLI, MCP, and the `events` read layer answer the **same** question about the **same** bytes. Governed-operation parity is an explicit repo contract (`docs/design-docs/governed-operation-parity.md`), and the failure mode this feature exists to prevent is precisely surfaces disagreeing about one file.

Use the plan's **three-row** shared fixture table. For each state, one **canonical fixture** is defined and written into the scratch workspace; each **mutating** test case gets a **fresh copy** of the canonical fixture so the canonical bytes remain available for subsequent assertions. Non-mutating paths (refused mutations on rows 1 and 2) exercise the canonical fixture directly and may assert byte-identity. The `conforming-active` row's `abandon` acceptance mutates the checkpoint; that row asserts the intended rewrite/archive outcome, **not** byte identity — byte-identity cannot hold on the canonical fixture AND be the same file an accepted `abandon` rewrites.

| Row | Stored shape | Expected agreement |
|---|---|---|
| `legacy-shaped` | schema-invalid **and** non-conforming | every surface refuses `resolve` and routes to quarantine (MCP `code: checkpoint_use_quarantine` via 147.025-T); `get` returns the **validation-class** refusal on all three — `events.ErrCheckpointInvalid`, MCP `code: validation_failed`, CLI non-zero exit — **not** a success payload |
| `valid-but-non-conforming` | parses and validates, carries unmodeled top-level keys | `events.GetCheckpointResult` → `conforming: false`; MCP `get_checkpoint` → `conforming: false`; CLI `checkpoint get` → the same; `resolve` and `abandon` refuse with `checkpoint_non_conforming` |
| `conforming-active` | conforming, `status: active` | every surface accepts `abandon`; `get` reports `conforming: true` |

The `valid-but-non-conforming` row's CLI `checkpoint get` expectation is implemented by **147.027-T** (U8c), which is why this unit depends on it: before cycle 4 no task projected `conforming` on the CLI read surface, so this row asserted behaviour nothing produced.

A schema-invalid document never reaches a conformance verdict, so the `conforming: false` assertions belong to the `valid-but-non-conforming` row only. Asserting them on the `legacy-shaped` row would assert an outcome the read path cannot produce. For the same reason the `legacy-shaped` `get` expectation is the **validation-class** refusal, not a disposition code: `GetCheckpointResult` returns `ErrCheckpointInvalid` unwrapped (147.012-T) and the MCP read handler maps it through `domainError` to `validation_failed` (147.022-T). `checkpoint_use_quarantine` belongs to the `resolve` column, where 147.025-T routes it.

**Batch-harness posture (cycle-8 correction under P-004):** U8b's harness lands during the batch harness generation phase, when its dep tasks (147.014-T / U7b, 147.015-T / U8, 147.022-T / U6c, 147.024-T / U7c, 147.027-T / U8c, and their upstream 147.012-T / U6b) have their **declaration stubs** but not yet their implementations. Against that state, U8b's parity assertions target projections and refusal shapes that the declaration stubs do not yet produce. The batch-harness model is what makes the assertions runnable while the deps' implementations are still pending: the test file compiles against the declaration stubs, and the assertions fail because the stubs do not yet exhibit the parity U8b is written to pin. Once every dep's implementation lands in dep order, the assertions turn green and U8b becomes the parity contract / regression guard it has always been intended to be.

**Expected red** (against declaration stubs / current handlers, per fixture row):

- `legacy-shaped` row — `events.GetCheckpoint` currently returns a success payload for a schema-invalid document because the 147.012-T / U6b validity gate is not yet in the declaration stub; assertion `errors.Is(err, ErrCheckpointInvalid)` **fails**. MCP `get_checkpoint(filename)` currently returns a success payload before 147.022-T / U6c's domainError mapping stub is filled in; assertion `code == "validation_failed"` **fails**. CLI `checkpoint get filename` currently prints hardcoded `"valid": true` and exits 0 (see cycle-4 finding on `newCheckpointGetCmd` at `internal/cli/checkpoint.go:180-210`) before 147.027-T / U8c reprojects it; assertion `exit_code != 0` **fails**. `resolve` currently succeeds and rewrites the file with a fabricated skeleton before 147.006-T / U3's validity gate and 147.025-T / U7d's route-through-disposition-shape stub complete; assertion that resolve is refused with `checkpoint_use_quarantine` **fails**.
- `valid-but-non-conforming` row — `events.GetCheckpointResult` — the 147.012-T / U6b declaration stub returns a zero-value result before its implementation populates the projection fields; the harness asserts **at least one required positive projected field alongside `Conforming == false`** to prove ListCheckpoints populated the projection rather than returning an unset stub: `Valid == true` (the document parses and validates), `NeedsQuarantine == true` (a non-conforming document requires quarantine), and `RemediationCommand != ""` (the operation-aware remediation string is present and non-empty). Against the declaration stub's zero-value result, `Valid == true` **fails** (zero bool is false), `NeedsQuarantine == true` **fails**, and `RemediationCommand != ""` **fails** — any of these three suffice to prove the stub was not populated, so the red gate is not dependent on the ambiguous `Conforming == false` zero-value alone. MCP `get_checkpoint` — before 147.022-T / U6c's projection stub is filled in, the response has no `conforming` field; assertion that `conforming: false` appears in the payload **fails**. CLI `checkpoint get` — before 147.027-T / U8c reprojects `newCheckpointGetCmd` from `events.GetCheckpointResult`, the CLI prints hardcoded `"valid": true` with no conformance field; assertion that `conforming: false` appears in stdout **fails**. `resolve` and `abandon` — before 147.007-T / U3b's conformance gate and 147.008-T / U4's conformance gate land, both mutations succeed on a valid-but-non-conforming document; assertions of refusal with `checkpoint_non_conforming` **fail** on both surfaces.
- `conforming-active` row — every surface accepts `abandon`; this is pre-existing shipped behaviour and passes from the moment the assertion lands. The three `get` assertions (`events.GetCheckpointResult` → `conforming: true`, MCP `get_checkpoint` → `conforming: true`, CLI `checkpoint get` → `conforming: true`) are **RED** until U6b/U6c/U8c land: `GetCheckpointResult` begins as a zero-value declaration stub (`Conforming: false`), the MCP payload lacks a `conforming` field before 147.022-T / U6c, and the CLI prints hardcoded `"valid": true` with no conformance field before 147.027-T / U8c. Only accepted `abandon` is an already-green regression guard.
- Byte-identity postcondition — **refused mutation paths only** (rows 1 and 2's non-mutation surfaces) assert byte-identity against the canonical fixture; the `conforming-active` row's accepted `abandon` asserts the intended rewrite/archive outcome (archive file created, active file removed or rewritten) instead of byte identity

Rows 1, 2, and the `conforming-active` row's three `get` assertions together carry the batch-harness red gate; only the `conforming-active` row's `abandon` acceptance is an already-green regression guard. This unit no longer claims an all-guards exemption — cases 1, 2, and the `conforming-active` `get` assertions each produce concrete assertion failures against the pre-implementation state, and P-004 is satisfied by their aggregate red load. Once all dep implementations land in dep order, every assertion turns green and U8b takes on its intended parity-contract / regression-guard role: pin the agreement so a future regression in any one surface (a stale MCP projection, a CLI hardcode, an events-layer default) surfaces as a failing test instead of a silent drift.
