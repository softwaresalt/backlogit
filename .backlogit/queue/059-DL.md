# Shipment shipped-event audit-log completeness

## Problem Frame

<!-- BEGIN:problem-frame -->
A shipment can persist archived_status: shipped while its append-only JSONL log omits the shipment_status_changed: shipped event. Verified against the clean origin/main baseline 3ec95ee3: moveShipmentStatusWithHeadGuard (internal/core/shipment.go:205) persists the shipment status through persistArtifactWithGuard (line 200) and then emits the audit event through the BEST-EFFORT appendItemEvent (internal/core/shipment.go:660), which warns and returns on lock or append failure. ShipShipment (internal/core/shipment_lifecycle.go:509 -> 524) then proceeds to archiveItems regardless, yielding archived_status: shipped with no shipped event. Confirmed absent on the same baseline: there is NO shipment-scoped ws.shipmentEventAppend seam and NO shipmentEventAppendError classification anywhere in internal/, cmd/, or tests/. The only error-returning appender that exists is appendItemEventErr (internal/core/gate_evidence.go:40), reached through the gate-evidence-only seam ws.gateEvidenceAppend (gate_evidence.go:81). Observed in the field from autoharness stash 84D8E6AB / shipment 114-S.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
A: Wrap the whole status-to-archival path in the existing core.MutationEnvelope (internal/core/mutation_envelope.go). Rejected: very high blast radius across the hardened ShipShipment locked closure, its membership lock, the head-drift guard, and the 133-F covering-feature restore.
B (chosen): Create a shipment-scoped, error-returning append seam and route ONLY the active -> shipped transition through appendItemEventErr, classified per the established two-class durable-write contract (ErrWriteNotApplied compensates through the existing snapshot rollback; ErrWriteIndeterminate and untagged errors never roll back and surface a MutationPartialError), and add a report-only doctor audit that detects historical residue without ever rewriting JSONL.
C: Swap the emission to an error-returning appender and always roll back. Rejected: violates the two-class contract documented in docs/compound/2026-07-28-durable-writes-two-class-contract-commit-then-surface.md, because rolling back an indeterminate write can destroy an applied append.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Take Option B. Sequencing is test-first and non-negotiable: a RED harness lands first against the clean baseline and must fail before any production change exists, then the production seam plus class-aware rollback, then integration and regression coverage. Detection (report-only doctor audit) ships inside this feature because historical residue already exists and cannot be repaired by the forward fix. PREVENTION of non-ShipShipment paths that can also produce the residue is explicitly deferred to stash 47B48DB0 so this release unit keeps the audit-log-completeness bug boundary. The doctor audit reports two DISTINCT and separately named findings rather than one conflated finding: missing_shipped_event (archived with archived_status: shipped and no shipped event in the item JSONL) and shipped_unarchived_residue (status: shipped but not archived, the indeterminate residue), because the two states have different causes and different operator responses.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
- Whether the RED harness can inject an ErrWriteNotApplied-classified failure without a production seam. Resolved: yes, through real filesystem injection at the item log path and lock path, which is why the harness task carries no production file.
- Whether the shipped-transition change can regress claim (queued -> active) or abandon semantics. Mitigation: the routing is gated on newStatus == ShipmentShipped and the other transitions keep best-effort semantics, asserted explicitly.
- Whether a doctor finding can fire transiently during an in-flight ship. Mitigation: carry the same verify-actual-history caveat that FindingOverArchivedCoveringFeature already uses (internal/core/doctor.go:545).
<!-- END:open-questions -->
