title: Concurrent handleMergeSync calls can regress manifest to staler snapshot
updated_at: 2026-04-21T10:22:32.4145351-07:00
---

In `internal/mcp/tools.go` (lines 746–759), two concurrent calls to `handleMergeSync` both read `oldManifest = s.manifest` under RLock, then race to write `s.manifest = newManifest` under a Write Lock.\n\nIf G2 (processing filesystem state at t2 > t1) writes first, G1 (processing t1) can overwrite it with an older snapshot. No data corruption (upserts are idempotent), but the manifest regresses to a staler state causing unnecessary re-processing on the next call.\n\n**Fix direction:** Add a `manifestVersion uint64` counter to Server. Increment on each write. Read version under RLock before calling MergeSync; only update manifest+version under Lock when the current version matches what was read. Skip the write if the version has advanced.\n\n**References:** `internal/mcp/tools.go:746-759`, review `037.001-R`
