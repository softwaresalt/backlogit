Plan unit **U6b**. Make `GetCheckpoint` agree with `ListCheckpoints`.

Files: `internal/events/checkpoint_lifecycle.go`, `internal/events/checkpoint_lifecycle_test.go`.

`GetCheckpoint` (`:108`) currently reports `valid: true` for any document that parses and validates. After U4/U5 that is actively misleading: an agent running the canonical `list` → `get` → choose-verb sequence would read `needs_quarantine: true` from list and `valid: true` from get, then pick the verb this feature just closed.

**There is no get-result type today.** `GetCheckpoint` returns `(*CheckpointV1, error)`, and `NeedsQuarantine` / `RemediationCommand` exist only on `CheckpointSummary` (`internal/events/checkpoint_schema.go:371`), so this task must declare the carrier before it can populate it:

* declare exported `CheckpointReadResult{Checkpoint *CheckpointV1; Valid, Conforming, NeedsQuarantine bool; RemediationCommand string}`
* add `GetCheckpointResult(ctx, checkpointDir, filename) (*CheckpointReadResult, error)` which runs `CheckConformingTopLevelNamespace` after `ValidateCheckpoint`
* retain `GetCheckpoint` as a thin wrapper returning `res.Checkpoint` so every existing caller compiles unchanged

`valid` retains its existing meaning (schema-valid) and is **not** repurposed; conformance is reported as a distinct field so no existing consumer's contract silently changes. Schema-invalid documents still return `ErrCheckpointInvalid` — this task adds conformance reporting for **valid-but-non-conforming** documents only.

That sentinel is returned **unwrapped**: `GetCheckpointResult` does not wrap it in `ErrCheckpointUseQuarantine`, because a read is not a rewrite and there is nothing to refuse. Downstream surfaces must therefore expect the pre-existing validation-class refusal on `get`, not a disposition code — this is the contract 147.022-T and 147.016-T project.

The MCP `get_checkpoint` projection (which hardcodes `"valid": true` at `internal/mcp/tools.go:1194-1212`) is **not** part of this task — it is a different surface and is tracked as **147.022-T**. The CLI `checkpoint get` projection is owned by **147.027-T (U8c)**, added in PR #377 Copilot review cycle 4 because U8 (147.015-T) already carried three refusal scenarios and a fourth CLI read projection would have breached the four-scenario limit. This task must not change either projection surface; 147.022-T and 147.027-T are its two consumers.

- A conforming file returns `conforming: true`
- The file is byte-unchanged after get
- `GetCheckpoint` keeps its current signature and every existing caller compiles unchanged
