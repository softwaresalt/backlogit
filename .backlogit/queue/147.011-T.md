Plan unit **U6**. Surface non-conforming files through `ListCheckpoints`.

Files: `internal/events/checkpoint_lifecycle.go`, `internal/events/checkpoint_lifecycle_test.go`.

After the existing `ValidateCheckpoint` branch, run `CheckConformingTopLevelNamespace(data)`; on failure set `NeedsQuarantine = true` and `RemediationCommand`, and **append** to `ValidationErr` rather than overwriting it — a file can fail both validation and conformance and the operator needs both reasons.

`RemediationCommand` must be **POSIX-safe** — paste-runnable verbatim in `bash`, `sh`, or `zsh` (single-quote-and-escape idiom on the filename and the `<reason>` placeholder). This is the contract the shipped implementation and `TestListCheckpoints_RemediationCommandIsShellSafe` already assert. It is **not** claimed PowerShell-safe for arbitrary accepted filenames: the POSIX `'\''` escape idiom is not a valid PowerShell literal, and no single command string can be paste-runnable in both shells for a filename containing a single quote. Windows-first workspace note: `CreateCheckpoint` (`internal/events/memory.go:59`) only ever writes filenames of the form `checkpoint-YYYYMMDD-HHMMSS.json` (digits, hyphens, fixed extension), so the natural corpus contains no shell-special characters and the emitted command is therefore also literally paste-safe in `pwsh` for every backlogit-generated file. The POSIX-safe form only differs from a hypothetical PowerShell-safe form for filenames containing single quotes, spaces, or other shell metacharacters, which the generator does not produce. For such out-of-band files an operator on Windows recovers via Git Bash / WSL / `bash -c`, hand-adapts the `'\''` escape to PowerShell's doubled `''`, or renames the file to the generator's shape before invoking the command. The prior "PowerShell-safe" wording is corrected here and in plan units U6, U6b, U8, U8b, U9, U10, and their runtime-verification row; no code or exposed API change is required because the shipped implementation already meets the corrected contract.

`ListCheckpoints` stays strictly read-only. The conformance branch must run **before** the filter block, so the verdict is computed for every parsed document rather than only for documents the caller's filter happens to select.

**Ordering is not exemption.** Computing the verdict early does **not** stop the filter block from dropping the summary afterwards: only the `ParseCheckpoint` failure path is filter-exempt today (`internal/events/checkpoint_lifecycle.go:~46-57` appends and `continue`s before the filter block), while the `valErr` branch falls through into the `Agent` / `Status` / `ShipmentID` / `FeatureID` / `MaxAge` checks like any other summary. Whether a quarantine candidate also becomes filter-exempt is a **separate behavioural change** and is owned by **147.023-T** (U6d). This task must not claim a drop-through guarantee it does not implement.

- A valid-but-non-conforming file lists with `NeedsQuarantine: true` and a POSIX-safe remediation command
- A file failing **both** validation and conformance reports both reasons in `ValidationErr`
- The conformance verdict is computed before the filter block, asserted by a case whose filter matches the document
- The files on disk are byte-unchanged after listing
- Expected red: cases 1 and 2 fail
