Root cause (R-C, MEDIUM/P1 2/3): readShipmentOperationJournalFile/writeShipmentOperationJournalFile/removeShipmentOperationJournalTempFile discard the validated directory handle (`_ *os.File`) and re-resolve filepath.Join(opsRoot,name) absolute paths; validateShipmentOpsWindowsFileHandle re-checks only the FINAL path string, so a same-canonical-path directory OBJECT swap (rename a different real dir into opsRoot) between validation and use is not defeated -> directory-replacement TOCTOU. Correct fix (per correctness+security review): object-bound handle-relative ops anchored to the validated directory handle - RootDirectory-relative NtCreateFile/NtOpenFile (no-follow) for read/create-temp/remove, and SetFileInformationByHandle FILE_RENAME_INFO with RootDirectory for the atomic rename (Windows renameat) - REPLACING MoveFileEx. This achieves parity with the existing Unix shipment_ops_unix.go (Openat/Renameat/unlinkat, O_NOFOLLOW). Post-hoc re-open+identity-compare is NOT sufficient (still check-after-use).
Scope decision: the sibling shipment_reconcile_fs_windows.go previously DECLINED NT-native APIs; this task explicitly authorizes the minimal RootDirectory-relative primitives because they are the only true closure of the same-canonical-path rename window and satisfy the operator's "fail closed on directory replacement" requirement.
