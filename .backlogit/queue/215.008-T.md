## Objective

Extend cross-branch and multi-session artifact ID sequence counter reservation, leaf allocator locking (`id_allocator.lock`), and handle-relative `.locks/id-sequences.json` rollback/recovery to `AdoptItemWithOptions` (`internal/core/shipment_lifecycle.go`) and `ReconstituteShipments` (`internal/core/shipment_reconstitute_exec.go`) (`3083FC1A` / `091-DL` / Unit U5b).

## Implementation Details

1. In `internal/core/shipment_lifecycle.go` (`adoptItem`, lines 1295-1525), when `!opts.KeepID` and `ws.Config != nil && ws.Config.QueueLayout != nil`:
   * Acquire the leaf allocator lock (`<storage_root>/.locks/id_allocator.lock` + in-process allocator mutex via the pinned `.locks` `*os.Root` handle from `215.006-T`, re-entrantly if already held in `ctx`) strictly *after* `FirePre(ctx, hooks.HookAdoptItem, hookCtx)` and *before* calling `allocateTypedHierarchicalID(ctx, ws, newParentID, ...)` so concurrent `AdoptItem` and `CreateArtifact` calls under the same parent serialize their read-allocate-persist critical sections and can never select the same next child ordinal.
   * Ensure durable outer-operation ownership (`opts.BeforeRename(ctx, oldID, newID)`, which journals `state.Adoptions[oldID] = newID` to the `reconstitute` intent journal on disk at line 1330) runs **before** publishing `newID` to `<storage_root>/.locks/id-sequences.json`. Capture the preimage of `<storage_root>/.locks/id-sequences.json` before applying the adoption mutation, persist the newly allocated `newID` into `<storage_root>/.locks/id-sequences.json` via the pinned `.locks` `*os.Root` handle (`atomicfile.ReplaceTempFileInRoot`) as part of the adoption commit envelope (before `tx.Commit()` finalizes), and if `.md` write/rename, cross-reference rewrite, log rename, `id-sequences.json` persistence, or `tx.Commit()` fails, roll back `.md`/`.jsonl`/cross-ref/DB changes AND restore `<storage_root>/.locks/id-sequences.json` to its exact preimage via the pinned `.locks` handle before releasing `id_allocator.lock` (prior to `FirePost`).
2. In `internal/core/shipment_reconstitute_exec.go` (`executeReconstitution`, `applyReconstitution`, `rollbackReconstitute`, and `removeReconstituteCreated`, lines 585-650, 820-935, 1240-1265, 1371-1396):
   * **Durable operation ownership before reservation publication**: Wire `recordCreated` into `opCtx` via the pre-create ownership callback (`shipmentOperationBeforeCreateContextKey`, invoked inside `CreateArtifact` after `artifactID` is allocated under `id_allocator.lock` and **before** `MutationEnvelope` publishes the `.md` file or `id-sequences.json` reservation, mirroring `AdoptItemOptions.BeforeRename` for `recordAdoption`) AND tag reservations written under `shipmentOperationContextKey` with `correlationID` in `id-sequences.json` so neither `CreateArtifact` (`shipment_reconstitute_exec.go:832`) nor `CreateShipment` (`shipment_reconstitute_exec.go:920`) can ever publish a reservation to `id-sequences.json` before `state.CreatedIDs` / `correlationID` durably owns that ID on disk.
   * Update `rollbackReconstitute` (invoked both on in-process `applyReconstitution` failure and on crash-recovery reconciliation of an uncommitted `Phase == "intent"` `reconstitute` journal) to call `unreserveIDSequences(ws, journal.CorrelationID, ours)` via the pinned `.locks` `*os.Root` handle so all rolled-back created and adopted IDs in `ours` (and any reservation tagged with `journal.CorrelationID`) are removed from `<storage_root>/.locks/id-sequences.json` (and `id-sequences.json` is removed via `locksRoot.Remove` when its reserved set becomes empty, preserving byte-identical workspace rollback in `midway_failure_restores_byte_identical_workspace`).
