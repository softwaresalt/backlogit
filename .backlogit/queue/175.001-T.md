Scope: `.gitattributes` line-ending hardening + a path-scoped `git add --renormalize` of the tracked `*.go`/`*.json` set. Single-domain (config/line-ending migration).

2-HOUR RULE vs FILE-COUNT HEURISTIC: this is ONE homogeneous, purely MECHANICAL line-ending migration whose PRIMARY bound — human-equivalent effort well under 2 hours — is met by a single path-scoped command (`.gitattributes` edit + one `git add --renormalize` + one scoped working-tree refresh + verification). The `<3 files` guideline is a HEURISTIC PROXY for effort, and it is DELIBERATELY exceeded here because a byte-only EOL migration touches all 518 tracked `*.go`/`*.json` files with ZERO semantic change. This is NOT a waiver of the 2-hour rule and NOT a harness/granularity waiver; it is a documented case where the file-count heuristic diverges from the true effort bound. Evidence: the 518 gofmt-listed Go files are EXACTLY the 518 tracked Go files checked out CRLF (`gofmtNotCRLF=0`, `crlfGoNotGofmt=0`), captured read-only in the baseline inventory.

APPROVAL GATE (blocking): MANDATORY, explicitly-recorded OPERATOR-ONLY approval of the renormalization, recorded BEFORE any `git add --renormalize` staging or any working-tree refresh (NOT merely before the commit). CLEAN-TREE PRECONDITION (blocking): before staging anything, assert the working tree and index carry NO unrelated changes (`git status --porcelain` empty except the intended `.gitattributes` edit); FAIL closed and halt if any unrelated index/worktree change exists, so renormalization cannot sweep in unrelated edits. Ship may prepare and present the proposed `.gitattributes` rules, the enumerated affected-path set, and its verification evidence but CANNOT authorize the renormalization; authorization is the operator's alone.

Changes:
- Add explicit `eol=lf` rules for `*.go` and `*.json`.
- For the byte-exact golden fixture, FIRST normalize its committed bytes to LF (rewrite the working-tree fixture to LF and stage it) BEFORE applying any `-text` treatment, OR prefer a `eol=lf` attribute that preserves LF rather than `-text`. Do NOT stage CRLF golden bytes under `-text` (that would freeze CRLF as the canonical bytes).
- Pin true binaries (`*.exe`, `*.db`, images, intentionally-binary fixtures) as `-text`.
- ONLY AFTER recorded operator approval and with the clean-tree precondition satisfied, run `git add --renormalize .` (index-only, non-destructive, reversible via `git reset`). Because `--renormalize` refreshes the INDEX but does NOT rewrite working-tree `.go`/`.json` files, EXPLICITLY refresh the affected paths AFTER the index renormalization and BEFORE asserting `w/lf`. Derive the affected-path set as the UNION of (a) the paths the renormalize staged (`git diff --cached --name-only`) AND (b) EVERY tracked path governed by a new `eol=lf` attribute whose WORKING-TREE EOL is still `w/crlf` or `w/mixed` (enumerate via `git ls-files --eol` restricted to the `eol=lf`-governed set). Deriving from the staged-diff names ALONE is INSUFFICIENT: if the index is already LF (e.g., a prior renormalize) while the working tree is CRLF, `git add --renormalize` stages nothing, so the staged-diff list is empty even though CRLF working-tree files still need refresh. Re-checkout exactly that union set (`git checkout -- <affected paths>`). Do NOT use a forced whole-tree refresh (`git checkout-index -f -a`) or whole-tree removal/re-checkout — scope the refresh strictly to the enumerated `eol=lf`-governed affected-path set.
- The durable CI line-ending guard is SPLIT into U14 (`175.014-T`), which owns ONLY the NEW dedicated `.github/workflows/line-endings.yml`. U1 changes NO workflow content and `.github/workflows/ci.yml` remains BYTE-IDENTICAL (no earlier claim that U14 or U1 edits `ci.yml` content stands — that text is stale and removed). U1 adds NO workflow content.

Safety checks (corrected):
- Assert `git ls-files --eol` shows `w/lf` for tracked `.go`/`.json` ONLY AFTER the working-tree refresh above; `-text` (or `w/lf` under the `eol=lf` variant) for the golden; `-text` for declared binaries.
- Content-identity (EOL-only proof): do NOT use `git diff --cached -w` — `-w` ignores ALL intra-line whitespace, not just line-ending bytes, so it would mask a genuine non-EOL whitespace edit. Instead, for each staged text path EXCLUDING `.gitattributes` and declared binaries, compare base vs index blob content after canonicalizing ONLY CRLF->LF: `B = git cat-file blob HEAD:<path>`, `I = git cat-file blob :<path>`; replace every CRLF (`\r\n`) with LF (`\n`) in each (leaving every other byte, including any bare CR, untouched); require `SHA-256(canon(B)) == SHA-256(canon(I))` for every path. Equal hashes prove ONLY line-ending bytes changed; any non-EOL byte difference fails the check. Exclude `.gitattributes` because it changes content by design.
- Binary identity: do NOT treat `git diff --cached --numstat` `-`/`-` as proof of byte-identity (`-`/`-` marks binary CLASSIFICATION, not unchanged bytes). Instead require each declared binary to be ABSENT from the staged diff, OR compare its pre/post blob hashes (`git rev-parse :<path>`) and confirm identical.
