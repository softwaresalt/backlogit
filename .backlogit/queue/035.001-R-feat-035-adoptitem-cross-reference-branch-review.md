## Findings

### internal/core/artifact_references.go

#### GQ-001/CC-001 [P2] — Context not propagated in findCrossArtifactReferences

The function signature accepts `_ context.Context` but the context is discarded entirely. `filepath.WalkDir` has no mechanism to honor cancellation mid-walk, so a user-initiated cancel (e.g. SIGINT) will not interrupt a scan of a large workspace. The context should be propagated and checked inside the walk closure on each file iteration.

**Action:** manual backlog follow-up  
**Files:** `internal/core/artifact_references.go:34–37`  
**Fix direction:** Store ctx in the closure, call `ctx.Err()` at the top of each walk callback, return the error to abort the walk.

---

#### SQ-001 [P2] — dep_type hardcoded as 'blocks'; original type not preserved

When `applyCrossArtifactRewrites` rebuilds `item_deps` rows via DELETE+INSERT it always inserts `dep_type = 'blocks'`. The original dep_type stored in the DB is not fetched and preserved. This currently matches rehydration behavior (which also hardcodes `'blocks'`), so there is no bug today, but it establishes a pattern that will silently lose type information when additional dep_type values are introduced in the future.

**Action:** manual backlog follow-up  
**Files:** `internal/core/artifact_references.go:194`  
**Fix direction:** Either (a) accept the convention as a known limitation and document it, or (b) fetch the existing dep_type from `item_deps` before deleting and reuse it on re-insert.

---

#### CC-002 [P3 advisory] — File I/O inside open tx in applyCrossArtifactRewrites

`applyCrossArtifactRewrites` calls `WriteArtifactFile` (filesystem) while holding an open `*sql.Tx` (with `_txlock=immediate`). On large workspaces with many cross-referencing artifacts, this extends the transaction hold time and may cause brief SQLITE_BUSY waits for concurrent readers. Acceptable in single-agent mode but worth documenting as a known scalability concern.

**Action:** advisory  
**Files:** `internal/core/artifact_references.go:170–180`

---

#### CC-003 [P3 advisory] — Commit-failure rollback uses non-atomic os.WriteFile

The commit-failure rollback block in `AdoptItem` restores cross-artifact snapshots via `os.WriteFile` directly (not atomic tmp+rename). If the process crashes mid-restore, a file could be left partially written. The risk is low because this is a rollback path triggered only when the SQLite commit fails, but using the same atomic pattern as `WriteArtifactFile` would be safer.

**Action:** advisory  
**Files:** `internal/core/shipment_lifecycle.go` (commit-failure rollback block)
