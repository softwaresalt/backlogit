## Release sequencing contract (accurate semantics)

`149-S` is gated behind the baseline-convergence terminal boundary via the
`149-S depends_on 169-S` edge (`169-S` = RS-W12, carrying U12 `175.012-T`, the
terminal sink that closes the wave-aligned replacement sequence
`157-S`..`169-S`). This edge replaced the historical `149-S depends_on 156-S`
edge under the accepted decomposition
(`docs/decisions/2026-09-19-baseline-convergence-decomposition.md`).

**This edge is an ADVISORY ordering signal — it does NOT guarantee shipped-only
readiness.** Two tool realities bound it:

- Queue filtering (`internal/core/queue.go` `filterByResolvedDependencies`)
  treats ANY no-longer-blocking terminal status of `169-S` — the 6-status cascade
  `done/accepted/archived/shipped/abandoned/rejected`, not `shipped` alone — as
  satisfying the dependency. So an `abandoned` or `rejected` `169-S` would clear
  the edge without a successful ship.
- Direct `core.ClaimShipment` (`internal/core/shipment_lifecycle.go`) transitions
  `queued -> active` with **no** dependency check at all, so a direct claim
  bypasses this edge entirely.

**Governed guarantee until core enforcement lands.** Shipped-only readiness for
`149-S` (become eligible only after `169-S` has SHIPPED successfully) is enforced
by the Orchestrator's claim-routing policy, which MUST confirm `169-S` reached
`shipped` before `149-S` is claimed. The tool-level enforcement — a shipped-only
readiness gate at the claim/queue boundaries and claim-time dependency validation
inside `ClaimShipment` — is captured as explicit prerequisite work in stash
`6434A4D7` (deferred; planning-only correction cycle, no Go changes in this PR).
The `depends_on 169-S` edge is retained as the best-effort ordering signal.
