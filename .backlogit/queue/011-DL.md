<!-- BEGIN:problem-frame -->
Stash entry 834CCDB7 captured a requirement for commit traceability in event log entries: event log JSON should be prefixed with the referenced item ID, include timestamps on filenames, and embed commit SHA and work descriptions to enable programmatic synchronization with external systems (Azure DevOps, Jira, GitHub Issues).

The existing Event struct in internal/events/stream.go already records item_id, timestamp, actor, event_type, and a freeform delta map. The LinkCommit function in internal/core/commits.go already associates commit SHAs with artifacts via a commit_links table and appends commit_tracked events to per-item JSONL logs. The gap is that standard lifecycle events (status changes, comments, archive operations) do not carry commit context, and the JSONL filenames do not include timestamps for external sorting.

This deliberation was created retroactively after the scope was harvested into 023.008-T and assembled into shipment 006-S without passing through the deliberation gate. The analysis below captures the decision reasoning that should have preceded planning.
<!-- END:problem-frame -->

<!-- BEGIN:options -->
Option A: Extend Event struct with optional CommitSHA field. Add a CommitSHA string field to the Event struct so any event can optionally carry commit context. Lifecycle operations (move, archive, ship) would populate it when a commit is available. Log filenames remain unchanged; external sorting uses the JSON timestamp field.
Pro: Minimal change, backwards-compatible, leverages existing JSONL infrastructure.
Con: Does not address filename-level timestamp sorting.

Option B: Rename JSONL log files to include ISO timestamps. Change LogPathForItem to generate filenames like {item_id}-{YYYYMMDD}.jsonl. Events accumulate per day per item.
Pro: Enables filesystem-level chronological sorting.
Con: Breaks existing log file references; rotation logic adds complexity.

Option C: Composite approach — extend Event struct (Option A) and add a separate commit-enrichment pass that decorates recent events with commit SHAs after the fact, without changing log filenames.
Pro: Clean separation of concerns. Commit enrichment is idempotent.
Con: Two-pass approach is slightly more complex than inline.
<!-- END:options -->

<!-- BEGIN:chosen-direction -->
Option A with elements of Option C. Extend the Event struct with an optional CommitSHA field so lifecycle events can carry commit context inline when available. Use the existing AutoLinkCommits scanner as the enrichment fallback for events where the commit was not known at write time. Do not rename log files — the JSON timestamp field is sufficient for programmatic sorting, and filename changes would break existing log references.

This aligns with the original stash request (include commit ID and explanation in event log entries) while respecting the existing CQRS pattern where Markdown is the source of truth and JSONL logs are append-only audit trails.
<!-- END:chosen-direction -->

<!-- BEGIN:open-questions -->
1. Should the CommitSHA field on Event be populated eagerly (at every lifecycle operation) or lazily (only when explicitly provided)? Recommendation: lazily, to avoid git dependency on every operation.
2. Should external system sync (Azure DevOps, Jira, GitHub Issues) be a separate feature or part of this scope? Decision: separate feature — this scope covers the data model, not the sync transport.
3. Should the item_id prefix in JSONL entries be a separate top-level field or remain embedded in the existing ItemID field? Decision: it is already a top-level field in the Event struct.
<!-- END:open-questions -->
