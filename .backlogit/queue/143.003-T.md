# Route the shipped transition fail-closed

## Description

<!-- BEGIN:description -->
Unit 3. In `moveShipmentStatusWithHeadGuard` (`internal/core/shipment.go`), gate on `newStatus == ShipmentShipped` and return the append error instead of only warning. Every other transition (claim, abandon) keeps the existing best-effort call and semantics. Wrap the returned failure in the `shipmentEventAppendError` boundary type declared in 143.001-T, at the call site, so the closure in 143.004-T classifies only that error. Do NOT retry the append: the `AppendEvent` contract is that a partial write or post-write fsync failure is `ErrWriteIndeterminate` and is not safe to retry blindly, and a pre-append lock failure is already tagged not-applied by 143.001-T and compensates; there is no third outcome class. Record in the doc comment that the fail-closed shipped path intentionally suppresses the `HookMoveShipmentStatus` post-hook, which today always fires because the append error is swallowed; firing a status-changed-to-shipped post-hook for a transition about to be compensated would misinform external integrations. Execution posture: test-first, depends on the 143.002-T red state.
<!-- END:description -->

<!-- BEGIN:acceptance-criteria -->
