New-workflow specification (`.github/workflows/line-endings.yml`):
- TRIGGERS: `on: { pull_request: { branches: [main] }, push: { branches: [main] } }`. Both PR and protected-branch push are covered so CRLF re-drift landing via a direct push to `main` (not only via a PR) is caught. No `paths:`/`paths-ignore:` filter at the trigger level.
- CI-SECURITY (must match current repository convention, proven against ci.yml):
  - `permissions: { contents: read }` declared at workflow level (least privilege).
  - `actions/checkout` pinned to the SAME full commit SHA the repository already uses: `actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2`, with `with: { persist-credentials: false }`.
  - `concurrency: { group: line-endings-${{ github.ref }}, cancel-in-progress: true }` (safe cancel of superseded runs on the same ref).
- JOB: a SINGLE always-run job on `runs-on: windows-latest` with NO `needs:` gate, NO changed-files/`needs.changes` condition, and NO `paths` filter anywhere. Steps: `actions/checkout` (pinned, persist-credentials:false) followed by the fail-closed guard step. Because it is a standalone workflow with no change-detection job, a docs-only or backlog-only PR — or a direct push — cannot skip it.
- GUARD STEP (fail-closed PowerShell over a FIXED tracked set): the guard operates on a FIXED, committed set of tracked `*.go` and `*.json` paths enumerated by `git ls-files -- '*.go' '*.json'` at run time (NOT a `git ls-files --eol` attribute-driven query, which would go vacuous if `.gitattributes` were deleted or narrowed). It asserts THREE properties INDEPENDENTLY, failing the job (non-zero exit) if ANY assertion fails:
  1. `.gitattributes` CONTRACT: the required `.gitattributes` rules are present and normalize `*.go`/`*.json` to `eol=lf` (or `text` with `core.eol=lf`); a missing/removed/narrowed attribute is a hard failure, so deleting attributes cannot make the guard pass.
  2. WORKING-TREE EOL: every enumerated path's on-disk bytes contain NO `\r\n` (no CRLF, no mixed) — the Windows checkout is where CRLF re-drift manifests, which is why the job runs on `windows-latest` AFTER `actions/checkout`.
  3. STORED/INDEX BLOB normalization: each enumerated path's index/committed blob is LF-normalized independently of `.gitattributes` — verified by hashing the LF-normalized bytes and comparing to the stored blob, so an LF working tree over a CRLF-committed blob still fails.
  Because the three assertions are independent, narrowing or deleting `.gitattributes` FAILS assertion 1 rather than silently disabling assertions 2 and 3. Declared binaries (`-text`) are excluded from the LF assertions exactly as in U1.

Test posture (Principle II): NORMAL harness-required task — no harness exemption is claimed (this task carries no `harness-exempt` label and no exemption contract). This unit exclusively owns and authorizes creation of a deterministic guard-regression harness under `tests/` — the reserved path `tests/lineendings_guard_175_test.go` (exactly-one-owner; no other unit may create that path). The harness:
- Builds a DISPOSABLE Git repository under `t.TempDir()` and performs ALL git operations there; it makes NO mutation to the caller/working-repository index (no `git add` against the real repo, no renormalize of the real tree).
- EXTRACTS the committed guard run-script from `.github/workflows/line-endings.yml` (parses the workflow YAML for the guard step's `run:` body) and EXECUTES that exact script against the temp repo, so the harness proves the SHIPPED guard, not a re-implemented copy.
- RED scenarios (table-grouped to stay under 4 distinct scenarios): (a) missing workflow / guard step absent; (b) removed/narrowed `.gitattributes`; (c) CRLF or mixed working-tree blob for a tracked path; (d) LF working tree over a CRLF-committed index/blob. Each asserts the guard predicate FAILS (non-zero).
- GREEN scenario: fully LF working tree + LF index + required `.gitattributes` present asserts the guard predicate PASSES (zero). Grouped with the red rows in one table-driven test to stay within the scenario limit.
The harness file is a `*_test.go` file and is EXCLUDED from the <3 implementation-file inventory (the sole implementation file owned is the new `.github/workflows/line-endings.yml`). There is NO generic/mechanical/closure-time harness exemption for this task.
