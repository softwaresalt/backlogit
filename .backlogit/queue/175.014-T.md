Persistent CI line-ending guard, split out of U1 so U1 stays a purely content-identical (EOL-only) renormalization. This unit OWNS the one genuine content change to `.github/workflows/ci.yml` (the guard step) — an ownership that would otherwise contradict U1's "line-ending-only churn" invariant. Single-domain (CI/config). Depends on U1 (`175.001-T`): the guard is authored only after U1's renormalization has landed. Feeds the U12 terminal verification sink.

STAGE-TIME CONSTRAINT: do NOT edit `.github/workflows/ci.yml` during staging. This is a planning task that authorizes Ship to add the guard at execution time. Stage's role boundary forbids workflow edits.

Guard specification (working-tree EOL identity — resolves the persistent-guard finding):
- The CI guard MUST inspect the WORKING-TREE end-of-line state via `git ls-files --eol` and FAIL the job when any tracked `.go`/`.json` (or other `eol=lf`-declared) path reports `w/crlf` or `w/mixed`. This detects re-drift on a checkout even when the index is clean.
- The index-diff content-identity check (`git add --renormalize . && git diff --cached --exit-code`, or the EOL-only normalized-blob SHA-256 comparison) is SEPARATE, complementary content-identity evidence and is NOT a substitute for the working-tree `w/*` inspection: an index-only check can pass while the checked-out working tree carries CRLF.
- Declared binaries (`-text`) and `.gitattributes` are excluded from the `w/lf` assertion exactly as in U1.

Acceptance criteria:
- Scope (files): only `.github/workflows/ci.yml` (the guard step). No other file is owned by this unit.
- Guard present: a persistent CI step runs `git ls-files --eol` and FAILS on any `w/crlf` or `w/mixed` for tracked `eol=lf` text paths.
- Separate index-identity evidence retained: the index-diff / renormalize-exit-code check remains as distinct content-identity evidence, not merged into the working-tree assertion.
- Ownership honesty: the `.github/workflows/ci.yml` content change is owned here, so U1's EOL-only content-identity proof does NOT need to (and must not) account for it; U1 touches no workflow content.
- Depends on U1 (`175.001-T`): guard is authored after renormalization lands; feeds U12 (`175.012-T`) terminal verification.
- No behavior change beyond adding the guard step; existing CI jobs still pass.
