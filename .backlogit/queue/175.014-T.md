Persistent CI line-ending guard, split out of U1 so U1 stays a purely content-identical (EOL-only) renormalization. This unit OWNS a DEDICATED, NEW, ALWAYS-RUNNING workflow file `.github/workflows/line-endings.yml` that carries a DURABLE, NON-SKIPPABLE Windows working-tree line-ending guard. It does NOT modify the existing `.github/workflows/ci.yml` at all: ci.yml is `pull_request`-only with docs/backlog changed-file skip conditions, and adding a workflow-level `push` trigger there would (a) contradict ci.yml's documented "PR-only validation removes duplicate push-to-main runs" invariant and (b) force every existing ci.yml job to also run on push unless each were individually guarded — an unnecessarily large blast radius. Owning a separate always-running workflow file is the lowest-blast-radius coherent GitHub Actions contract: it leaves ALL existing ci.yml behavior byte-for-byte unchanged. Depends on U1 (`175.001-T`): the guard file is authored only after U1's renormalization has landed. Feeds the U12 terminal verification sink.

STAGE-TIME CONSTRAINT: do NOT create or edit any file under `.github/workflows/` during staging. This is a planning task that authorizes Ship to add the new workflow file at execution time. Stage's role boundary forbids workflow edits.

New-workflow specification (`.github/workflows/line-endings.yml` — resolves the persistent-guard + event-semantics findings):
- TRIGGERS: `on: { pull_request: { branches: [main] }, push: { branches: [main] } }`. Both PR and protected-branch push are covered so CRLF re-drift landing via a direct push to `main` (not only via a PR) is caught. No `paths:`/`paths-ignore:` filter at the trigger level.
- JOB: a SINGLE always-run job on `runs-on: windows-latest` with NO `needs:` gate, NO changed-files/`needs.changes` condition, and NO `paths` filter anywhere. Steps: `actions/checkout` followed by the working-tree EOL guard. Because it is a standalone workflow with no change-detection job, a docs-only or backlog-only PR — or a direct push — cannot skip it.
- GUARD STEP: run `git ls-files --eol` and FAIL the job when any tracked `eol=lf`-declared path (`.go`/`.json`/etc.) reports `w/crlf` or `w/mixed`. This inspects the WORKING-TREE EOL state on a Windows checkout, where CRLF re-drift actually manifests (a Linux/`ubuntu-latest` checkout keeps LF and would false-green), so the guard MUST run on `windows-latest` AFTER `actions/checkout`.
- Declared binaries (`-text`) and `.gitattributes` are excluded from the `w/lf` assertion exactly as in U1.
- The index-diff content-identity check (`git add --renormalize . && git diff --cached --exit-code`, or the EOL-only normalized-blob SHA-256 comparison) is SEPARATE, complementary content-identity evidence owned by U1's proof, NOT part of this working-tree guard, and is not duplicated here.

Test posture (Principle II): NORMAL harness-required task — no harness exemption is claimed (this task carries no `harness-exempt` label and no exemption contract). This unit exclusively owns and authorizes creation of a deterministic guard-regression harness under `tests/` — the reserved path `tests/lineendings_guard_175_test.go` — that (RED first) stages a synthetic tracked path checked out with CRLF and asserts the `git ls-files --eol` guard predicate reports `w/crlf` and fails, then goes green once the guard predicate is authored. The harness file path is reserved to this unit (exactly-one-owner; no other unit may create that path); it is a `*_test.go` file and is EXCLUDED from the <3 implementation-file inventory (the sole implementation file owned is the new `.github/workflows/line-endings.yml`). There is NO generic/mechanical/closure-time harness exemption for this task.

Acceptance criteria:
- Scope (files): implementation-file inventory is exactly ONE new file, `.github/workflows/line-endings.yml`; plus the reserved owned harness file `tests/lineendings_guard_175_test.go`. `.github/workflows/ci.yml` is NOT touched (proven by an empty diff on ci.yml). Single CI/config domain, one-implementation-file contract under the 2-hour rule.
- Existing CI preserved: `.github/workflows/ci.yml` is byte-for-byte unchanged; all existing ci.yml jobs and triggers behave exactly as before (no push trigger added to ci.yml, no job re-scoped).
- Guard present: the new workflow runs `git ls-files --eol` and FAILS on any `w/crlf`/`w/mixed` for tracked `eol=lf` text paths.
- Runner (required): the guard runs on `windows-latest` AFTER `actions/checkout` (the only place CRLF re-drift is observable; a Linux checkout would false-green).
- Runs on push (required): the new workflow triggers on protected-branch `push` (to `main`) AND `pull_request`; the EOL guard executes on a direct push to `main`. Verified by the workflow `on:` block containing both `push.branches: [main]` and `pull_request.branches: [main]`.
- Cannot be skipped by changed files (required): the guard job has no `needs: changes` gate, no `paths:`/`paths-ignore:` filter, and no changed-files skip condition, so a docs-only or backlog-only PR (or push) still performs the Windows checkout + `git ls-files --eol` guard.
- Depends on U1 (`175.001-T`): guard is authored after renormalization lands; feeds U12 (`175.012-T`) terminal verification.
- Harness (required): the reserved `tests/lineendings_guard_175_test.go` RED-first regression exists and drives the guard predicate green; no harness exemption claimed.
