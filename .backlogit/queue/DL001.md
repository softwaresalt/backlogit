# {title}

## Problem Frame

<!-- BEGIN:problem-frame -->
The current harness relies on a chain of specialized agents with manual or semi-manual handoffs between deliberation, planning, harvesting, harnessing, building, review, and closure. That model creates operational friction, makes ownership blurry, and increases the cognitive cost of moving one idea from stash to merged pull request.

We want to refactor backlogit toward a simpler operating model built around two orchestrators: one that grooms ideas into ready backlog work, and one that ships that work all the way through implementation and review. The change must preserve backlogit-native lineage, keep storage Git-friendly, and avoid introducing migration burden beyond this repository's own alpha-state data.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
1. Keep the current multi-agent topology and improve handoffs incrementally. This limits change risk but retains the coordination overhead that triggered the redesign.
2. Collapse to a single orchestrator agent with many leaf skills. This is simple conceptually, but it blends grooming and shipping responsibilities and risks an oversized control surface.
3. Split the workflow into two orchestrators with a four-stage pipeline: groomer for stash-to-backlog and shipper for backlog-to-merged shipment. This keeps ownership clear while reducing handoff count.

For bootstrapping the refactor itself, two approaches remain relevant:
- Sidecar rollout: build the new agents and supporting skills alongside the current harness, validate them, then retire the old agents.
- Ad hoc implementation: refactor manually outside the current harness, which avoids self-reference but loses dogfooding value.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
Adopt the two-agent model with a four-stage pipeline: STASH -> BACKLOG -> SHIPMENT -> SHIPPED. Use a groomer agent to transform stash entries into fully groomed backlog artifacts, and a shipper agent to take a shipment artifact from queued work through implementation, review, CI, and pull request completion.

Represent stash as JSONL, retain backlog and shipment artifacts as Markdown with YAML frontmatter inside .backlogit, and keep shipment scope 1:1 with a branch and pull request. Prefer a sidecar bootstrap strategy so the new harness can be built and validated without destabilizing the current workflow before it is ready to retire.
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
- Confirm the bootstrap strategy explicitly: sidecar first, with manual fallback only if the harness cannot self-host the migration.
- Decide how aggressively to deprecate or alias the current agent files once groomer and shipper are proven.
- Finalize the file naming refactor and determine whether it lands in the same shipment as the agent-model change or as a tightly sequenced follow-on.
- Define the exact MCP/CLI tool surface for shipment creation, listing, and lifecycle management.
<!-- END:open-questions -->

## Notes

<!-- BEGIN:notes -->
Key decisions already made in the design session:
- Shipment is a first-class artifact type with prefix S and a 1:1 relationship to branch/PR scope.
- Blocked items are removed from the active shipment manifest and returned to backlog status with an explicit blocked reason.
- The current alpha state means migration support for external users is not required; only repository-local data needs conversion.
- Existing skills such as deliberate, impl-plan, plan-review, build-feature, review, fix-ci, and compound stay as skills, while backlog-harvester, harness-architect, and pr-review are candidates for skill extraction or retirement.
<!-- END:notes -->
