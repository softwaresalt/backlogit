# {title}

## Problem Frame

<!-- BEGIN:problem-frame -->
When a feature ships and its scope gets archived, some descendant tasks may not have been included in the release. The `ShipShipment` lifecycle already returns these untouched items to `queued` status, but their IDs still encode the archived parent (e.g., `F015.T009` where F015 is shipped and archived). The `parent_id` field also still points at the archived feature. This creates a design ambiguity: the items look like they belong to a shipped feature, but they are actually available backlog work.\n\nThe core tension is that backlogit IDs are hierarchical and immutable (used as log file keys, event stream identifiers, and stash links), while the parent relationship is mutable and represents active ownership.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: Rename/reparent on return** — Clear parent_id, assign a new top-level ID, rename the file. Clean identity but breaks the ID contract for items with operational history (logs, events, stash links). Requires rename + re-index on every return. Risk of ID collision with existing top-level numbering.\n\n**Option B: Reusable drain queue** — A separate file or directory where returned items wait for adoption. Conceptually clean separation but duplicates what `status: queued` already provides. Adds complexity to rehydration with another source to scan. The existing queue is already the drain.\n\n**Option C: Status-as-authority with parent_id nulled** — Leave the ID immutable as a provenance marker. Null out `parent_id` in frontmatter to signal orphan status. `status: queued` is the authority for availability. When items get pulled into a new shipment, they can optionally get reparented under a new feature at that point. Zero migration, zero breakage, works identically for items with or without operational history.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option C: Status-as-authority with parent_id nulled.**

Rationale:
1. **ID immutability** — The F015.T009 prefix is historical provenance, not active ownership. Changing IDs would break log file references, event streams, and any external links.
2. **parent_id mutability** — Nulling parent_id on return makes orphan status explicit without breaking identity. Setting parent_id on re-adoption into a new feature preserves the mechanism.
3. **Status authority** — Queue views already filter by status, not parentage. Items with `status: queued` are available regardless of their ID prefix.
4. **Simplicity** — No new storage locations, no rename operations, no rehydration changes. The existing CQRS model handles this naturally.

Additional confirmed decisions:
- **Adopt operation**: A formal `adopt` operation sets `parent_id` to the new feature and writes `origin_feature` metadata preserving the original provenance.
- **Orphan indicator**: Queue views surface orphan status for items whose ID prefix references an archived parent.
- **Provenance ID retention**: Adopted items keep their original ID. An `origin_feature` custom field preserves lineage explicitly. Queue views group by current `parent_id` for visual clarity, not by ID prefix.

Implementation already applied:
- `returnUnreleasedFeatureItems` in `shipment_lifecycle.go` now clears `parent_id` via `clearParentID`.
- T009, T010, T011 had `parent_id` nulled as the immediate fix.
<!-- END:chosen-direction -->
