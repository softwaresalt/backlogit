Copilot review finding (106-F F1, PR #333, round 6, gateproof.go:66): the formal-gate-evidence HMAC envelope binds head_sha but not the resolved base_ref, even though base_ref defines the diff the gate reviewed. appendGateEvidence persists base_ref outside the envelope, and FormalAdmit has no verifier-supplied expected base, so editing base_ref after signing does not invalidate the proof.

Deferred from 117-S (106.003-T-106.011-T) because it is schema-affecting: gateproof.Envelope is explicitly versioned (Schema field, currently 1, 'an unknown version is rejected rather than partially trusted' per docs/design-docs/formal-gate-evidence-authenticity.md), so adding a new bound field warrants a schema v2 (or careful in-place migration reasoning) touching every signing call site (task + shipment), FormalContext, and re-validating every existing signed-evidence test.

Severity assessment: head_sha (the actual commit state the gate evaluated) is already bound and cryptographically verified, so base_ref tampering cannot change WHICH commit was authenticated as having passed -- it can only misrepresent which diff was reviewed for audit/compliance narrative purposes. Real but narrower than an admission-bypass or evidence-loss defect.

Proposed approach: bind the resolved base_ref (config.FormalGateConfig or gate.Evaluation's Base.Ref) into a new schema=2 envelope field, verified against a verifier-supplied trusted context analogous to WorkspaceID/ItemID in FormalContext, with schema=1 evidence remaining valid for its own (unextended) guarantee.
