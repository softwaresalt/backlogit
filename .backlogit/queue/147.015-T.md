Plan unit **U8**. CLI refusal surfacing.

Files: `internal/cli/checkpoint.go`, `internal/cli/checkpoint_test.go`.

**Scope note.** The `checkpoint get` conformance projection moved to **147.027-T** (U8c) during PR #377 Copilot review cycle 4. This unit owns the `resolve` / `abandon` refusal rendering and nothing else, and it must not touch `newCheckpointGetCmd`: a read projection is a different contract from a refusal rendering, and carrying it here would have made a fourth scenario, breaching the four-scenario limit. The two units share `internal/cli/checkpoint.go` but not a function, exactly as 147.022-T and 147.024-T share `internal/mcp/tools.go`.

`checkpoint resolve` (`:228`) and `checkpoint abandon` must render the refusal as an actionable operator message rather than a bare Go error string. The message names the exact remediation command, and — where one exists — the offending keys.

**The offending-key list is only available for a valid-but-non-conforming target.** A schema-invalid legacy document is refused by the U3 validity gate (`ErrCheckpointUseQuarantine`) before the conformance check ever runs, so no key list exists for it; `internal/events/checkpoint_lifecycle.go:~105-137` returns on `ValidateCheckpoint` failure without producing a conformance verdict. Demanding named keys for a legacy file would be an unsatisfiable contract. That refusal prints the validation reason and the remediation command instead.

The rendered remediation command must be **PowerShell-safe** and paste-runnable, consistent with U6.

Exit code stays non-zero on refusal; the CLI must not exit 0 for a refused mutation.
