title: Repository-ref CAS/guard for shipment completion window (post manifest-signing HEAD drift)
updated_at: 2026-08-09T08:31:40.7263694Z

Copilot review finding (106-F F1, PR #333, round 10, shipment_gate.go:590): shipmentHead is last verified stable (via the existing headDriftError pre/post bracket) BEFORE the manifest reload, digest computation, proof signing, and shipment status transition sequence. A concurrent commit landing during that LATER window lets the signed proof bind reviewed commit A while ShipShipment completes the actual status transition with the repository's real HEAD having already advanced to unreviewed commit B. The membership lock (lockShipmentMembership) only serializes concurrent backlogit membership mutations -- it cannot serialize an external git commit, since git has no first-class 'lock HEAD against external writers' primitive backlogit can take.

Severity assessment: this is narrower than the round 6/8 findings it is adjacent to. The existing headDriftError bracket already covers the SLOWEST, most externally-influenced part of the sequence (the shipment-level gate Evaluate call plus the member-evidence scan). The remaining window is bounded to fast, in-process Go operations only (manifest re-read, digest hash, HMAC sign, JSONL append, persist/relocate/DB-upsert) -- a materially narrower and harder-to-hit race than the multi-minute external build/test/lint commands the task-level head-drift fix (round 7/9) had to bracket. The signed proof's claim ('these members were verified against commit A') also remains factually true regardless of what the repository does afterward; what can drift is only the shipment's OWN declared head_sha versus the repository's live tip at the exact moment of completion, an audit-precision concern rather than an admission-bypass one.

Proposed approach (per reviewer's own suggestion): a repository-ref guard or CAS tied to the reviewed SHA at the final admission/status-transition point, so HEAD cannot silently advance out from under a completing shipment. Options to evaluate: (a) one more headSHABounded re-check immediately before the persist inside moveShipmentStatusWithTopLevel, narrowing (not eliminating) the window further; (b) a git-level advisory mechanism (e.g. a ref-lock file convention documented for CI/operator coordination) if narrowing alone is judged insufficient; (c) accepting the narrowed, audit-precision-only residual risk as a documented, monitored limitation given git itself offers no atomic 'read HEAD and complete our write' primitive. Deferred from 117-S given its narrower severity and the materially larger design surface (option b in particular) relative to the round 1-9 fixes already shipped in this PR.
