# Telemetry Pipeline Enhancements — Combined Deliberation

## Problem Frame

<!-- BEGIN:problem-frame -->
The backlogit telemetry subsystem (internal/telemetry/) was shipped in its initial form with F021 (Token Telemetry). Four enhancement requests have been stashed that collectively improve the pipeline's performance, usability, and metric coverage:

1. **Context Window Consumption Tracking** (stash DDD1F38A, orig 23884888): Measure peak context utilization, remaining capacity, and depletion rate per session. Currently ModelCall tracks prompt/completion/cached tokens but has no context window dimension — no max_context_length, utilization %, or depletion rate. CompactionEvents track pre-compaction tokens but not window efficiency.

2. **CLI Telemetry Report Subcommand** (stash AB6959FC, orig E14AB8CC): Implement `backlogit telemetry report` to surface harvested token and tool usage metrics from the terminal. Currently all three CLI subcommands (harvest, list, top) are stubs returning errors. The plan (2026-04-09) specified report with --session, --by server|model|session|tool, --format table|json flags.

3. **Incremental Harvest with Byte-Offset Checkpoints** (stash 73E63809, orig 01D115EC): Avoid full re-processing of .copilot/logs/*.log on every harvest run. Currently harvest.go line 32 comments: "Full re-harvest in v1; no incremental checkpointing (Plan Review F2)." Each run re-parses all logs and overwrites telemetry-sessions.jsonl.

4. **Date-Filtered Harvest (--since flag)** (stash 91D459D8, orig CD92F274): Allow scoping harvest to logs after a given date. No date parameters exist in HarvestTelemetry signature currently. Raw log lines contain timestamps that are parsed but not used for filtering.

All four share the code surface: internal/telemetry/, internal/cli/telemetry.go, and .backlogit/telemetry-sessions.jsonl. They have a natural dependency ordering: harvest improvements (3, 4) should land before reporting (2) can show meaningful results, and context window tracking (1) adds a new metric dimension that reporting should display.
<!-- END:problem-frame -->

## Options

<!-- BEGIN:options -->
**Option A: Sequential delivery — Harvest performance first, then reporting, then metrics**
Build incremental checkpoint + date filtering first (items 3+4), then CLI report (item 2), then context window tracking (item 1). This ensures the report subcommand is built on top of a performant harvest pipeline. Low risk but slower to show user-facing value.

**Option B: Report-first with stub data, then infrastructure**
Ship the CLI report subcommand first (item 2) on the existing full-harvest pipeline, then add incremental harvest (3+4), then context window (1). Shows user-facing value immediately but may need rework when the harvest output format changes for incremental support.

**Option C: Single cohesive feature with layered tasks**
Ship all four as a single parent feature "Telemetry Pipeline Enhancements" with ordered child tasks. Task ordering: (3) incremental checkpoint → (4) date filter → (1) context window metrics → (2) CLI report. Dependency graph ensures each task builds on the prior. This is the operator's preferred grouping.

**Option D: Two shipments — infrastructure + UI**
Split into two features: "Harvest Performance" (items 3+4) and "Telemetry Reporting" (items 1+2). Ship infrastructure first, reporting second. Clean separation but loses the cohesive narrative and may delay context window tracking unnecessarily.
<!-- END:options -->

## Chosen Direction

<!-- BEGIN:chosen-direction -->
**Option C: Single cohesive feature with layered tasks** — aligns with the operator's explicit grouping rationale and the natural dependency ordering. All four items share the same code surface and benefit from a unified implementation plan. The dependency chain (incremental checkpoint → date filter → context window metrics → CLI report) ensures each task builds on solid infrastructure.

Rationale:
- The operator explicitly grouped these as "a single cohesive group" with "natural dependency ordering"
- Incremental checkpoints (3) are foundational — they change how harvest writes and reads state
- Date filtering (4) is complementary to checkpoints — both address "don't re-process everything" and share the filtering/checkpoint data structures
- Context window tracking (1) extends the data model before the report UI is built, so the report can include all metrics from day one
- CLI report (2) is the consumer of everything above — building it last means it ships complete

Task ordering within the feature:
T1: Incremental harvest with byte-offset checkpoints (73E63809)
T2: Date-filtered harvest --since flag (91D459D8) — depends on T1 checkpoint infrastructure
T3: Context window consumption tracking (DDD1F38A) — extends data model, independent of T1/T2 but ordered after to avoid merge conflicts in types.go
T4: CLI telemetry report subcommand (AB6959FC) — depends on T1, T2, T3 being complete so report surfaces all metrics
<!-- END:chosen-direction -->

## Open Questions

<!-- BEGIN:open-questions -->
1. **Context window data availability**: Do Copilot CLI logs actually emit context window size / max context tokens? If not, can we derive utilization from prompt_tokens_count + completion_tokens_count relative to known model limits (e.g., Claude Sonnet 4 = 200k)? May need a model-to-context-limit lookup table.

2. **Checkpoint file location**: Should .telemetry-checkpoint.json live in .backlogit/ (governed by constitutional principles) or alongside .copilot/ (closer to source)? Constitutional Principle VII may require an amendment for mutable checkpoint state in .backlogit/.

3. **Incremental vs. append semantics**: When incremental harvest adds new events, should telemetry-sessions.jsonl be appended (growing file) or rewritten with merged state? Append is simpler but requires deduplication on read; rewrite is cleaner but loses the F5 "single write path" guarantee.

4. **Report output destination**: Should `backlogit telemetry report` write to stdout only, or also support --output file? The constitutional model favors stdout for CLI tools.

5. **Depletion rate calculation**: How should context depletion rate be defined — tokens consumed per minute? Per model call? Per tool call? Need a clear formula before implementation.
<!-- END:open-questions -->
