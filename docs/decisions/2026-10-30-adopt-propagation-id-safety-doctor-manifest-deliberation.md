## Problem Frame

* Active stash entries `7CE12EE6` (*backlogit ID allocator has no reservation or explicit-ID create option...*) and `40CC5C6B` (*Phase 2b follow-up from DE3E7B67: (1) declarative `shipment reconstitute --plan`; (2) `adopt` rename propagation for remaining shipment-manifest and archived-stash-provenance gaps + `--keep-id`; (3) `doctor` manifest integrity checks; (4) operator-reasoned `stash correct --reason` / `stash repoint` and non-recycling of IDs with history/provenance*) form the C1 target of the operator's Dark Factory directive (`Option 1: Run the pipeline in dark factory mode`).
* To keep every shipment bounded to 3 atomic single-domain (`code`) tasks under the 2-Hour Rule and provide clean foundational primitives before declarative multi-shipment `shipment reconstitute --plan` lands in Phase 1B (`210-S`), Phase 1A (`208-F` / `209-S`) consolidates local workspace history-based ID non-recycling and items (2), (3), and (4) of `40CC5C6B`:
  1. **`AdoptItem` rename propagation (`custom_fields.items` in shipment manifests + `harvested_artifact_id` in `.backlogit/archive/stash.jsonl` + correlated successor `ProvenanceCorrection` entries in `.backlogit/archive/provenance_corrections.jsonl`) and `adopt --keep-id`** (`docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` §3).
  2. **Local workspace history-safe non-recycling ID allocation** across SQLite history (`item_logs`, `item_log_entries` including `delta_json` `old_id`, `stash_links`) and workspace disk (`queue/`, `archive/`, `logs/*.jsonl` filenames and event records' `item_id` + `delta.old_id` on `adopted` events, `archive/stash.jsonl`, `archive/provenance_corrections.jsonl`) (`40CC5C6B` §5). Cross-branch ID collision prevention from `7CE12EE6` (reservation ledger, explicit `--id` create flag, or remote-aware allocator across open PRs/branches) is explicitly split out and tracked in follow-up stash entry `7BE3AF92`.
  3. **Operator-reasoned `CorrectStashProvenance` (`--force`) stamping the complete `source_stash_*` provenance snapshot with strict read-only preflight -> audit-before-mutation -> rollback-on-failure ordering, canonical metadata refresh during `replayProvenanceCorrections` (`applyProvenanceCorrections` in `internal/db/rehydration.go`), and CLI/MCP registry parity** (`40CC5C6B` §5).
  4. **`Doctor` shipment manifest integrity checks** (`dangling_shipment_member`, `duplicate_shipment_membership`, `split_feature_across_shipments`, `forward_shipment_dependency`, `unsequenced_queued_shipment`) (`40CC5C6B` §4).
* Item (1) of `40CC5C6B` — declarative multi-shipment `backlogit shipment reconstitute --plan <yaml> [--dry-run] [--json]` — remains active on `40CC5C6B` for **Phase 1B** (`209-F` / `210-S`), where it directly composes the hardened `AdoptItemWithOptions`, history-safe ID allocator, and `Doctor` manifest checks delivered in `209-S`. Cross-branch ID reservation / explicit `--id` / remote-aware allocation from `7CE12EE6` is tracked in follow-up stash entry `7BE3AF92`.

## Research Findings

* **`AdoptItem` & cross-reference rewrites (`internal/core/shipment_lifecycle.go:1185-1450`, `internal/core/artifact_references.go`)**:
  * `findCrossArtifactReferences` and `applyCrossArtifactRewrites` (`internal/core/artifact_references.go`) currently inspect only `a.ParentID`, `a.Dependencies`, and `a.Links`. When an item inside a shipment's `custom_fields.items` manifest is adopted under a new parent feature and receives a new ID (`oldID -> newID`), shipment manifests are not rewritten, leaving a dangling `oldID` in `custom_fields.items`. Extending `findCrossArtifactReferences` and the under-lock refresh loop in `applyCrossArtifactRewrites` to inspect `NormalizeShipmentItems(a)` when `a.ArtifactType == "shipment"` and replace `oldID` with `newID` in slice order (deduplicating if `newID` is already present and preserving a non-nil `[]string`) makes shipment manifest rewrites atomic and rollback-safe under `applyCrossArtifactRewrites`.
  * While `AdoptItem` updates `stash_links.item_id` in SQLite via `bldb.RewriteAncillaryReferences`, `.backlogit/archive/stash.jsonl` stores `"harvested_artifact_id": "<oldID>"` and `.backlogit/archive/provenance_corrections.jsonl` may store a latest correction record whose `"canonical_delivery_artifact_id"` is `"<oldID>"`. Adding an atomic helper in `AdoptItemWithOptions` that — after acquiring `lockArtifactMutations` and `lockAdoptionEventLogs` (`lockItemLogCrossProcess`) — locks `.backlogit/archive/stash.jsonl` (`lockStashFile`, establishing the canonical shared U1/U2 lock order `lockArtifactMutations` -> `lockItemLogCrossProcess` -> `lockStashFile` and refusing symlinks via `os.Lstat`), snapshots both `.backlogit/archive/stash.jsonl` and `.backlogit/archive/provenance_corrections.jsonl` file bytes for rollback on transaction failure, rewrites any `harvested_artifact_id == oldID` to `newID` in `archive/stash.jsonl`, and for any latest correction record in `archive/provenance_corrections.jsonl` whose `canonical_delivery_artifact_id == oldID` appends a correlated successor `ProvenanceCorrection` entry with `canonical_delivery_artifact_id: newID` (preserving `historical_artifact_id`, `stash_id`, and `forced`, with `actor: "backlogit"` and `reason: fmt.Sprintf("adopt rename %s -> %s", oldID, newID)`) keeps the durable JSONL archives and `SyncIndex` (`internal/db/rehydration.go:730-744`) consistent with SQLite even when the original historical artifact still carries `source_stash_id`.
  * Adding `AdoptItemOptions{KeepID bool}` and `AdoptItemWithOptions(ctx, ws, itemID, newParentID, opts)` (with `AdoptItem` delegating with `AdoptItemOptions{}`) allows callers to re-parent an item (`parent_id = newParentID`, `origin_feature` preserved) while keeping `newID == oldID` and appending an `adopted` event when `KeepID: true`.
* **History-safe ID allocation (`internal/core/hierarchy.go`, `internal/core/naming.go`, `internal/core/artifacts.go`)**:
  * `NextTypedHierarchicalID` (`internal/core/hierarchy.go:81-147`) and `NextID` (`internal/core/naming.go:47-74`) currently query only `SELECT id FROM items`. When an artifact is created and deleted before merge, unindexed on disk, or adopted under a new parent feature (`AdoptItem` renames `<oldID>.md` and `<oldID>.jsonl` to `<newID>` and U1 rewrites `harvested_artifact_id` in `.backlogit/archive/stash.jsonl`), its prior ordinal can be recycled even though `.backlogit/logs/<id>.jsonl`, event records inside `.backlogit/logs/<newID>.jsonl`, or `.backlogit/archive/stash.jsonl` (`harvested_artifact_id`) still reference `<oldID>`.
  * Extending `NextTypedHierarchicalID` and `NextID` to also advance past ordinals recorded in SQLite `item_logs`, `item_log_entries` (including `delta_json` `old_id` on `adopted` events), and `stash_links`, and adding workspace-aware `NextTypedHierarchicalIDForWorkspace` / `NextIDForWorkspace` / `MaxDiskArtifactSequence` (invoked by `CreateArtifact` and `AdoptItemWithOptions`) that scan filenames in `WorkspaceQueueRoot`, `WorkspaceArchiveRoot`, and `WorkspaceLogsRoot` (`<id>.md`, `<id>.jsonl`), event records inside `.backlogit/logs/*.jsonl` (specifically each event record's `item_id` and `delta.old_id` on `adopted` events), `.backlogit/archive/stash.jsonl` (`harvested_artifact_id`), and `.backlogit/archive/provenance_corrections.jsonl`, guarantees that no local ID with history, adoption lineage, or provenance is ever recycled (`40CC5C6B` §5). Note that U1 addresses local workspace history-based ID reuse; cross-branch/open-PR ID collision prevention from `7CE12EE6` (reservation ledger, explicit `--id` create flag, or remote-aware allocator) is tracked separately in follow-up stash entry `7BE3AF92`.
* **Operator-reasoned stash provenance correction (`internal/core/stash_provenance.go`, `internal/db/rehydration.go`, `internal/cli/stash_correct.go`, `internal/mcp/tools_reconcile.go`, `.autoharness/backlog-registry.yaml`)**:
  * `CorrectStashProvenance` (`internal/core/stash_provenance.go:63-224`) currently rejects any target artifact whose `custom_fields.source_stash_id` does not already equal `req.StashID`, and rejects a second correction for the same stash ID if it names a different canonical artifact.
  * Adding `Force bool` to `StashProvenanceCorrectionRequest` (requiring non-empty `Reason` and `Actor`) allows an operator-reasoned correction when `Force: true` to (a) enforce strict **read-only preflight -> audit-before-mutation -> rollback-on-failure** ordering under the canonical shared U1/U2 lock order (`lockArtifactMutations` -> `lockItemLogCrossProcess` -> `lockStashFile`, matching `AdoptItemWithOptions`): (1) validate inputs and containment, acquire `lockArtifactMutations(ctx, ws, []string{req.CanonicalDeliveryArtifactID})` (and `events.LockItemLogCrossProcess` for `req.CanonicalDeliveryArtifactID`) **BEFORE** `lockStashFile` (holding `lockArtifactMutations` before loading or snapshotting the target artifact and through persistence and rollback), and perform all read-only validations (`readProvenanceCorrections`, `resolveArchivedStashSnapshot` from `.backlogit/archive/stash.jsonl` / `stash_entries` when `Force: true`, and target artifact load) BEFORE any write; (2) snapshot `provenance_corrections.jsonl` and the target artifact's `.md` file bytes, then preserve the existing event-first ordering in `internal/core/stash_provenance.go:191-199` by appending the `stash_provenance_corrected` event to the target item's event log **BEFORE** appending the `ProvenanceCorrection` entry to `provenance_corrections.jsonl` (so an item-event append failure returns an error before any correction-ledger or target `.md` write occurs, and both audit writes complete fail-closed before mutating the target artifact's Markdown/SQLite state); and (3) stamp the **complete provenance snapshot** onto `target.CustomFields` — `source_stash_id`, `source_stash_priority`, `source_stash_kind`, `source_stash_text`, `source_stash_path` (defaulting to `"stash.jsonl"` when empty), and setting `source_deliberation_id` from the archived entry's `deliberation_id` when non-empty or deleting any pre-existing `source_deliberation_id` key when empty — and persist the target artifact's updated Markdown frontmatter and SQLite `items`/`stash_entries`/`stash_links` rows, restoring the `provenance_corrections.jsonl` and `.md` byte snapshots if the target Markdown or SQLite persist fails; (b) supersede an earlier conflicting correction in `provenance_corrections.jsonl` (`readProvenanceCorrections` returns the last matching `CanonicalDeliveryArtifactID`) and record `"forced": true` on the `ProvenanceCorrection` JSONL entry, the `stash_provenance_corrected` item-log event, and `StashProvenanceCorrectionResult`; and (c) update `replayProvenanceCorrections` (`applyProvenanceCorrections` in `internal/db/rehydration.go`) so that when replaying corrections it treats the **final canonical delivery artifact's** `source_stash_*` snapshot values — including an empty/absent `source_deliberation_id` (clearing `stash_entries.deliberation_id` to `""`) and default values — as authoritative when refreshing the `stash_entries` row's `priority`, `kind`, `text`, `source_path`, and `deliberation_id`, preventing a later historical artifact carrying bare/stale `source_stash_id` or a stale `source_deliberation_id` in filesystem traversal order from overwriting or leaving stale metadata on the canonical delivery's `stash_entries` row during `SyncIndex` (`Rehydrate`).
  * `internal/cli/stash_correct.go` already defines `backlogit stash correct --stash-id <id> --canonical-delivery <id> --reason <r> --actor <a>`. Extending `newStashCorrectCommand` to add `--force`, accept optional positional `[stash-id]` and `--artifact` (alias for `--canonical-delivery`), wiring `force` on MCP `backlogit_correct_stash_provenance`, and replacing `mcp_only: true` on `correct_stash_provenance` in `.autoharness/backlog-registry.yaml` with `cli_command: "backlogit stash correct --stash-id {{stash_id}} --canonical-delivery {{canonical_delivery_artifact_id}} --reason {{reason}} --actor {{actor}}"` achieves full CLI/MCP registry parity.
* **`Doctor` shipment manifest integrity checks (`internal/core/doctor.go`)**:
  * Extending `Doctor` (`internal/core/doctor.go`) with `detectShipmentManifestFindings(refs, ids)` over non-terminal shipments (`status` in `queued`, `active`, `blocked` and located outside `archive/`) detects all 5 manifest anomalies from `40CC5C6B` §4:
    1. `FindingDanglingShipmentMember` (`"dangling_shipment_member"`, error severity): manifest item ID not present in `refs` (`queue/` or `archive/`).
    2. `FindingDuplicateShipmentMembership` (`"duplicate_shipment_membership"`, error severity): item ID present in `custom_fields.items` of more than one non-terminal shipment.
    3. `FindingSplitFeatureAcrossShipments` (`"split_feature_across_shipments"`, error severity): resolves the **owning feature ancestry** for every explicit manifest member in a non-terminal shipment — a `feature` member's own ID, a `task` member's `parent_id` feature, and a `subtask` member's ancestor feature (via `parent_id` chain) — and flags when members belonging to the same feature are distributed across more than one non-terminal shipment (covering feature-in-S1 + task-in-S2, task-in-S1 + task-in-S2, and task-in-S1 + subtask-in-S2, with regression assertions for both feature+task and task+subtask splits).
    4. `FindingForwardShipmentDependency` (`"forward_shipment_dependency"`, error severity): an item in non-terminal shipment `S1` has a `blocks` dependency on an item in non-terminal shipment `S2` where `S2` depends on `S1` (directly or transitively in the shipment `blocks` DAG, meaning `S1` is scheduled before `S2`).
    5. `FindingUnsequencedQueuedShipment` (`"unsequenced_queued_shipment"`, advisory severity — does not set `DoctorSeverityError`): when more than 1 `queued` shipment exists, a `queued` shipment has no `blocks` dependency on another shipment and does not carry the `dag-root` label.

## Options Evaluated

### Option A: Stage Slice A (`AdoptItem` propagation + `--keep-id`, history-safe ID allocation, `stash correct --force`, and `Doctor` manifest checks) in `208-F` / `209-S`, and Stage Declarative `shipment reconstitute --plan` in Phase 1B (`210-S`) — Chosen

* **Description**: Deliver the four foundational integrity and provenance capabilities (`40CC5C6B` items 2, 3, 4 + local workspace history-based ID non-recycling) in feature `208-F` and shipment `209-S` across 3 sequential single-domain (`code`) tasks (`208.001-T` -> `208.002-T` -> `208.003-T`), while keeping `40CC5C6B` active for Phase 1B (`209-F` / `210-S`: declarative `backlogit shipment reconstitute --plan`) and tracking the cross-branch ID reservation / explicit `--id` / remote-aware allocator scope from `7CE12EE6` in follow-up stash entry `7BE3AF92`.
* **Pros**:
  * Respects the 2-Hour Rule (3 focused `code` tasks touching 2–4 files each).
  * Ensures `AdoptItem` manifest/stash propagation, history-safe ID allocation, and `Doctor` manifest checks are already in place when `shipment reconstitute --plan` is built in Phase 1B (`210-S`).
  * Fully resolves local workspace history-based ID non-recycling (`40CC5C6B` §5, preventing ID recycling across deleted, logged, archived, and adopted-away items) and items (2), (3), and (4) of `40CC5C6B`, while preserving the cross-branch/open-PR ID reservation scope of `7CE12EE6` in active stash entry `7BE3AF92`.
* **Cons**:
  * Splits `40CC5C6B` across two consecutive shipments (`209-S` and `210-S`), mitigated by immediate sequential execution in the same Dark Factory run.

### Option B: Bundle Declarative `shipment reconstitute --plan` into `208-F` / `209-S` — Rejected

* **Description**: Combine all 4 items of `40CC5C6B` plus `7CE12EE6` into a single 5–6 task shipment.
* **Cons**:
  * Exceeds the 3-task single-concern scope for `209-S` and couples YAML plan parsing/transaction orchestration with foundational `AdoptItem`, ID-allocator, `stash correct`, and `Doctor` primitives.

## Decision

Adopt **Option A**: promote local history-based ID non-recycling and `40CC5C6B` items (2), (3), and (4) to implementation plan `docs/exec-plans/2026-10-30-adopt-propagation-id-safety-doctor-manifest-plan.md` under covering feature `208-F` and shipment `209-S`, track the remaining cross-branch ID reservation / explicit `--id` / remote-aware allocator scope from `7CE12EE6` in follow-up stash entry `7BE3AF92`, and update `40CC5C6B` in place so item (1) (`backlogit shipment reconstitute --plan`) proceeds immediately in Phase 1B (`210-S`).
