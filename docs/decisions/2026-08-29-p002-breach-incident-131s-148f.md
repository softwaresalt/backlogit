## Factual Record

### What happened

All five tasks in feature 148-F were implemented in a single production
commit `0b97483d`. This commit introduced simultaneously:

1. Production code for U1 (malformed JSON gate), U2 (context duplicate
   detection), U3 (syncWriteFileAtomicHook seam), U4 (symlink/TOCTOU
   hardening), and U5 (Extra validation)
2. All five test harnesses: `checkpoint_u1_harness_test.go`,
   `checkpoint_u2_harness_test.go`, `checkpoint_u3_harness_test.go`,
   `checkpoint_nofollow_test.go` (U4), `checkpoint_u5_harness_test.go`
3. Backlog status updates

Parent commit `323c5247` contains none of these artifacts. No immutable
separate red-harness commits exist anywhere in the git history for any of
the five U-tasks. Every harness passed immediately upon introduction.

**Verification**: `git log --all --diff-filter=A` for each harness file
returns only `0b97483d` as the introduction commit. The `--stat` output
of `0b97483d` confirms 18 files changed with all five test and production
files landing atomically.

### What P-002 requires

P-002 requires that every task be harness-satisfied before implementation
begins. The red phase requires:

* A test harness committed in a state where it compiles and all tests fail
* The failing state observed and recorded before implementation code lands
* A separate commit capturing the red phase that precedes the green phase

### What actually occurred

The red and green phases for all five U-tasks were collapsed into a single
commit (`0b97483d`). No separate red-harness commit exists for any task.
The test-first execution record is invalid for the entire 148-F feature.
This is a genuine P-002 violation across all five tasks, not a single-task
anomaly.

### What is NOT violated

* **Behavioural correctness**: The implementation code in `0b97483d` passed
  all quality gates (tests, vet, lint, format) at merge time and continues
  to pass. The harnesses exercise the correct behavior
* **Review gates**: PR #383 passed Copilot review, adversarial review, and
  CI. PR #384 (closure) passed all readiness checks

## Governed Decision

### Posture: Acknowledged breach with forward control

This decision **acknowledges** the P-002 breach as a genuine NON-NEGOTIABLE
policy violation affecting all five tasks in 148-F. It does NOT:

* **Accept** the breach — P-002 violations cannot be accepted or normalized
* **Waive** the red phase — retroactive waivers would undermine the policy
* **Erase** history — 131-S archive remains immutable
* **Claim cure** — adding a green regression test does not satisfy P-002's
  requirement that the red phase precede implementation
* **Revert** the security hardening — the code is behaviourally correct and
  reverting would reintroduce the security gaps 148-F was designed to close

### Risk assessment

| Factor | Assessment |
|---|---|
| Behavioural correctness | CONFIRMED — all tests pass, adversarial review found no logic gaps |
| Regression coverage | PRESENT — all five harness files test the correct behavior |
| Security impact of revert | NEGATIVE — reverting would reopen security gaps |
| Blast radius of the violation | PROCEDURAL — the violation is in execution discipline, not in code safety |
| Forward risk | HIGH — without controls, collapsed red/green phases could recur |

### Decision

**The breach is recorded as a permanent procedural incident against 131-S.**
Shipping may resume for remaining dark-factory groups under amended forward
controls (see below). The historic 148-F red phase is NOT considered cured.

The return-from-shipped posture is: **CONDITIONAL RESUME** — the P-002
halt condition is satisfied by this formal incident record, the forward
control amendment, and the causal risk recording, without requiring code
revert or archive mutation.

## Causal Risk: Untracked P1 Data-Loss Window

The P-002 audit revealed a pre-existing P1 data-loss risk:

**`syncWriteFileAtomic` Windows pre-Remove data-loss risk** (stash `CB71B412`):
On Windows, `internal/events/fsutil.go` `syncWriteFileAtomic` calls
`os.Remove(dst)` before `os.Rename(tmp, dst)`. If the process crashes between
Remove and Rename, checkpoint data at `dst` is destroyed with no replacement
in place.

**Provenance**: This gap was pre-existing and was already production-reachable
before 148-F — `CreateCheckpoint` called `syncWriteFileAtomic` directly in
parent commit `323c5247`. U3's change replaced the direct call with a hook
seam; subsequent PR fix commits (`18d77d02`, `3820564f`) routed the
`CreateCheckpoint` path through `atomicfile.WriteFileAtomic`. However,
`syncWriteFileAtomic` remains reachable through other callers (e.g.,
`hook_checkpoint.go`). The P-002 audit of U3 surfaced this risk. Unix
`rename(2)` is atomic and does not require pre-Remove, so this is
Windows-only.

This P1 risk is tracked as stash `CB71B412` (bug, high). It is a follow-up
obligation from the 131-S audit. It MUST be addressed no later than the
final dark-factory group, regardless of whether intervening groups modify
the affected files.

## Forward Control Amendment

The following controls are MANDATORY for all remaining dark-factory groups
(Groups 2, 3, 4) and for any future Ship release unit until the operator
explicitly relaxes them:

### FC-1: Separate Red-Harness Commits Required

Every task that carries `harness-ready` MUST have its red-harness committed
in a **separate commit** that precedes the implementation commit. The Ship
agent MUST verify that the red-harness commit exists as a distinct ancestor
of the implementation commit before claiming the task is harness-satisfied.

### FC-2: Ship Preflight Source/History Check

Before any Ship agent claims a `harness-ready` task from a wave, it MUST
run a preflight check that verifies:

1. The `*_harness_test.go` file (or equivalent) for the task exists in a
   commit that is an ancestor of the current branch HEAD
2. That ancestor commit does NOT contain the corresponding production code
   changes
3. The red-harness commit compiles: `go test -run=^$ -count=1 ./...`
4. The task's tests fail at the red-harness commit:
   `go test -run=<task-specific-pattern> -count=1 ./<package>/...`
   must exit non-zero

If this preflight check fails, the task MUST NOT be claimed. A P-002
violation report MUST be emitted.

**Harness-exempt exception**: Tasks carrying `harness-exempt` with a valid
P-002.1 exemption class (`docs-only`, `verification-only`, `covered-by`)
are exempt from this source/history check. The Ship agent MUST instead
verify the P-002.1 static and claim-time conditions for the declared
exemption class, including `harness_owner` predecessor evidence for
`covered-by` tasks.

### FC-3: Release Decision Audit Trail

Every shipment closure MUST include a P-002 compliance section that
explicitly states:

* For each `harness-ready` task: the separate red-harness commit SHA
* For each `harness-ready` task: confirmation the red phase was observed to fail
* For each `harness-exempt` task: the exemption class and validation evidence
* For the shipment: whether any P-002 exceptions or deviations occurred
* Reference to this incident decision (INC-P002-131S-148F) for provenance

### FC-4: Causal P1 Sequencing Constraint

Stash `CB71B412` (syncWriteFileAtomic Windows pre-Remove data-loss) MUST
ship no later than the final dark-factory group (Group 4). It MUST NOT be
deferred past the dark-factory activation scope. If any Group modifies
`internal/events/fsutil.go`, `internal/events/memory.go`, or any caller of
`syncWriteFileAtomic`, `CB71B412` MUST be included in that Group or an
earlier one.
