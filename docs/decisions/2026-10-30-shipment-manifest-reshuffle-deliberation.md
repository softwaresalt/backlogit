## Problem Frame

* Active stash entry `DE3E7B67` (*FEATURE REQUEST: Shipment manifest reshuffle and reconstitution*, full specification in `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md`, folded with `8CCB29CF` per `docs/decisions/2026-10-08-stage-foldins-and-dispositions.md` F4) is the Phase 2 target of the operator's Dark Factory directive (`2026-10-30T05:55:05Z`: *"Phase 1: Consistent CLI and MCP errors; Phase 2: Replan shipments without hand-editing manifests; Phase 3: Trustworthy metadata for cheaper model routing. Run pipeline in Dark Factory mode."*).
* In backlogit today (`internal/core/shipment.go`, `internal/cli/shipment.go`, `internal/mcp/tools.go`), shipment manifest membership only supports `AddItemToShipment` (`backlogit shipment add` / `backlogit_add_to_shipment`) and active-shipment `ReturnBlockedItem` (`backlogit shipment return-blocked` / `backlogit_return_blocked`).
* When a queued shipment needs replanning after review (splitting oversized shipments, removing descoped tasks, moving tasks to a sibling shipment, or restoring covering-feature-first and `blocks`-topological manifest order), operators and agents have no governed primitive to remove, move, or reorder `custom_fields.items`. Hand-editing `.backlogit/queue/<id>-S.md` bypasses core validation (`validateShipmentItemIDs`, one-shipment-per-item invariants, status guards), leaves no JSONL audit trail in `.backlogit/logs/`, and risks SQLite index drift.
* The full design document (`docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md`) spans five capabilities:
  1. **Primitive manifest operations (`remove`, `move`, `reorder`)** on queued shipments by default, with `--auto` topological ordering, `--dry-run`, `--force` + `--reason` override on non-queued shipments, audited JSONL events, and full CLI/MCP parity.
  2. **Declarative multi-shipment reconstitution (`shipment reconstitute --plan <yaml>`)** composing primitive manifest operations, feature creation, and `adopt`.
  3. **`adopt` rename propagation** for remaining shipment-manifest and archived-stash-provenance gaps.
  4. **`doctor` manifest integrity checks** (dangling/renamed manifest IDs, multi-manifest items, feature split across shipments, forward `blocks` edges, unsequenced queued shipments).
  5. **Stash provenance correction (`stash correct --reason` / `stash repoint`)** and ID-reuse prevention.

## Research Findings

* **Core shipment concurrency, recovery, and persistence (`internal/core/shipment.go`, `internal/core/shipment_ops.go`, `internal/core/shipment_recovery.go`)**:
  * `AddItemToShipment` (`internal/core/shipment.go:1553-1648`) establishes the canonical lock and persistence pattern: acquire `lockShipmentLifecycleGlobal(ctx, ws)`, run `recoverPendingShipmentOperations(ctx, ws)`, acquire `lockShipmentMembership(ctx, ws, shipmentID)`, normalize manifest items with `NormalizeShipmentItems(shipment)` (which never returns `nil`, preserving the `[]` JSON wire-shape invariant from `docs/compound/go-patterns/f015-shipment-stash-patterns.md` and `docs/compound/2026-07-03-cli-mcp-honest-fallback-map-and-registry-drift-test.md`), and execute `MutationEnvelope` with `"frontmatter-update"` (`persistArtifact(ctx, ws, shipment, false)` + rollback compensation via `cloneArtifact`) and `"jsonl-append"` (`NewWorkspaceEventWriter` + `bldb.IndexEvent`).
  * `persistArtifact` (`internal/core/shipment.go:2062-2069`) and `guardBlockedShipmentMembershipMutation` (`internal/core/artifacts.go:1042-1053`) unconditionally reject manifest changes while a stored shipment has `status == "blocked"` (`blerrors.ErrShipmentConflict` / `ErrShipmentBlockedManifestSealed` / `ErrInvalidStatus`). Therefore, `blocked` shipments must be unconditionally refused even when `--force` is supplied — both in live execution and in `--dry-run` preview — requiring governed `UnblockShipment` first; `--force` with non-empty `--reason` overrides only `active` (and terminal `shipped`/`abandoned`) non-`queued` shipments.
  * When `RemoveFromShipment` removes a member: for a `queued` shipment, the member remains in `.backlogit/queue/` unassigned from the shipment manifest with `status: "queued"`; when force-removing an `active` member from an `active` shipment (`--force` + non-empty `--reason`), `RemoveFromShipment` verifies the member is an eligible unstarted claim-assigned member (`custom_fields.scheduler_baseline_claim == shipmentID` and no `WORK_STARTED:` comment in its item log for the current claim epoch; refusing forced removal of an already-started `active` member or one lacking the shipment's claim marker with `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`), and transitions the member's `status` from `active` back to `queued` while clearing `custom_fields.scheduler_baseline_claim` (and appending a correlated `status_changed` `active -> queued` event to the member's item log) under the same durable shipment-operation recovery journal mechanism (`Operation: "remove_item"`, `RecoveryPolicy: "rollback"`, `ShipmentID: shipmentID`, `Target: itemID`, `Preimage.Shipment` + `Preimage.Members` containing the removed item's full preimage including `status: "active"` and `custom_fields.scheduler_baseline_claim`) in `internal/core/shipment_ops.go` and `internal/core/shipment_recovery.go` as `MoveShipmentItem` (`Operation: "move_item"`). Likewise, when `MoveShipmentItem` force-moves an `active` member from an `active` source shipment (`Force: true` + non-empty `Reason`), it verifies the member is an eligible unstarted claim-assigned member of `fromShipmentID` (`custom_fields.scheduler_baseline_claim == fromShipmentID` and no `WORK_STARTED:` comment in the current claim epoch; otherwise refusing with `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`); if `toShipment` is `queued`, it transitions the member's `status` from `active` back to `queued` and clears `custom_fields.scheduler_baseline_claim` (and appends a correlated `status_changed` `active -> queued` event to the member's log) inside the `move_item` journaled mutation so `ClaimShipment(toShipment)` will later activate the `queued` member and stamp `scheduler_baseline_claim: toShipmentID` (and if `toShipment` is `active`, it keeps `status: "active"` and updates `scheduler_baseline_claim = toShipmentID`). Because `MutationEnvelope` keeps compensation only in memory and skips it on `ErrWriteIndeterminate` (`internal/core/mutation_envelope.go:23-41`), and `cleanupShipmentOperationJournal` logs a warning without failing if journal removal fails after commit, both `RemoveFromShipment` and `MoveShipmentItem` persist a durable `Phase: "intent"` journal before mutating the member or manifest(s), durably update the on-disk journal to `Phase: "committed"` (`writeShipmentOperationJournal` with `Phase: shipmentOperationPhaseCommitted`) immediately after all member/manifest writes and `phase: "committed"` audit event appends succeed and before calling `cleanupShipmentOperationJournal` or returning success, teach `validateShipmentLifecycleJournalRecord` (`internal/core/shipment_ops.go`) and `reconcileShipmentLifecycleIntent` / the recovery evidence reader (`internal/core/shipment_recovery.go`) that a `remove_item` or `move_item` journal with `Phase == "committed"` (or matching `phase: "committed"` `shipment_item_removed` / `shipment_item_moved` event(s) in the shipment log(s)) is already committed and must be finalized/cleaned up without rolling back preimages, skip in-memory compensation and retain the `Phase: "intent"` journal on disk for `lockShipmentLifecycleGlobal` barrier rollback recovery on `ErrWriteIndeterminate` or a crash before commit, and roll back in-memory from the preimages and remove the journal on `ErrWriteNotApplied`.
  * Because `lockShipmentLifecycleGlobal` creates lock files and runs recovery, and `GetShipment` populates SQLite on a cache miss, `--dry-run` preview paths must use a dedicated read-only preview path that checks for unfinished recovery journals read-only (refusing if pending recovery exists) and loads shipment/member artifacts via a read-only Markdown file loader (`readArtifactFromDiskReadOnly`) with zero writes to SQLite, lock files, or JSONL logs.
  * For cross-shipment `MoveShipmentItem(ctx, ws, itemID, fromShipmentID, toShipmentID, opts)`, holding `lockShipmentLifecycleGlobal`, acquiring `lockShipmentMembership` on `fromShipmentID` and `toShipmentID` in canonical lexicographical order (`docs/compound/2026-10-19-lock-held-side-effect-ordering.md`), updating `validateShipmentLifecycleJournalRecord` / `loadShipmentOperationJournals` in `internal/core/shipment_ops.go` to accept both `Operation == "remove_item"` and `Operation == "move_item"` (across both `Phase == "intent"` and `Phase == "committed"`), and persisting a durable `move_item` recovery journal (`internal/core/shipment_ops.go` + `internal/core/shipment_recovery.go`) that captures and restores both shipment manifest preimages AND the moved member artifact's full preimage (including `status` and `custom_fields.scheduler_baseline_claim`), transitions to `Phase: "committed"` before journal cleanup, and emits correlated `intent` / `committed` / `aborted` events prevents lock-order deadlocks, journal-validator rejections at the lifecycle barrier, accidental rollback of completed operations on journal-cleanup failure, and torn manifest, member-status, claim-marker, or audit state across crashes, `ErrWriteIndeterminate`, or failure after the first audit append.
* **Covering-feature and topological ordering (`internal/core/shipment_covering.go`, `internal/db/dependencies.go`)**:
  * `isRootCoveringFeature(item)` (`internal/core/shipment_covering.go:114-122`) identifies a root covering feature (`item.ArtifactType == "feature" && !strings.Contains(item.ID, ".")`).
  * `ReorderShipment` with `--auto` deterministically emits only root covering feature(s) (`isRootCoveringFeature`) in the leading prefix, then topologically orders **every remaining manifest member not already emitted in the root-feature prefix** — including nested/sub-epic dotted features (`100.001-F`), tasks (`task`), and subtasks (`subtask`) — as vertices in the Kahn graph `G` constructed in two phases: (1) first add all hard intra-manifest `blocks` prerequisite edges `B -> A` (`A depends_on B`, `dep.Type == "" || dep.Type == "blocks"`), rejecting any cycle among hard `blocks` edges with `ErrDependencyCycle` / `blerrors.ErrValidation`; (2) second, iterate over candidate default parent-before-child edges `P -> C` (for each non-root member `C` whose `parent_id` `P` is also in the non-root graph) in deterministic manifest order (by `C`'s original manifest index) and admit `P -> C` into `G` **if and only if** `P` is not reachable from `C` in the current graph `G` (which already contains all hard `blocks` edges plus all previously admitted `P -> C` parent edges, preventing cross-parent dependencies such as `A depends_on b` and `B depends_on a` from forming a false cycle `a -> B -> b -> A -> a`), using priority-queue tie-breaking that groups ready children immediately after their emitted parent while honoring all edges in `G`, and using the exact same two-phase graph `G` rule for `--items` explicit-order validation.
* **CLI/MCP parity and CI gates (`.autoharness/backlog-registry.yaml`, `internal/cli/registry_parity_test.go`, `.github/workflows/ci.yml`)**:
  * `.autoharness/backlog-registry.yaml` is listed in `.autoharness/drift-ignore` and is the single authoritative operation registry consumed by both agents and `internal/cli/registry_parity_test.go` (see commit `a86b8065`). Updating `.autoharness/backlog-registry.yaml` directly in U3 (`206.003-T`) with `remove_from_shipment`, `move_shipment_item`, and `reorder_shipment` ensures `TestRegistryParity_EveryMCPToolMappedOrDeferred`, `TestRegistryParity_EveryCLICommandResolves`, `TestRegistryParity_NoOrphanMCPTool`, `TestRegistryParity_DiscoverabilityConsistency`, and `TestRegistryParity_FlagAndPositionalParity` validate the authoritative registry without test-only workarounds.
  * `.github/workflows/ci.yml` runs `go run ./cmd/gen-docs docs/cli-reference` and `git diff --exit-code docs/cli-reference/` in the `CLI Reference Drift` job (`docs/compound/workflow-issues/cli-reference-drift-check-manual-edits-bypass-gen-docs-2026-04-25.md`). Adding Cobra subcommands `shipment remove`, `shipment move`, and `shipment reorder` requires regenerating `docs/cli-reference/` in the same unit.

## Options Evaluated

### Option A: Stage Primitive Manifest Replanning Operations (`remove`, `move`, `reorder`) in `206-F` / `207-S` and Capture Phase 2b Extensions as Follow-Up Stash — Chosen

* **Description**:
  1. **U1 (`206.001-T`, `code`)**: Implement `ShipmentManifestOptions`, `RemoveFromShipmentResult`, `MoveShipmentItemResult`, `RemoveFromShipment`, `MoveShipmentItem`, and `remove_item` + `move_item` journal validation in `internal/core/shipment_ops.go` (and recovery journal handling in `internal/core/shipment_recovery.go`) with unit tests `TestU1_RemoveFromShipment_QueuedAndForceGuards` and `TestU1_MoveShipmentItem_AtomicTransferAndGuards` in `internal/core/shipment_manifest_test.go`. Enforce `queued`-only default with `--force` + non-empty `--reason` override for `active` (and terminal `shipped`/`abandoned`) non-`queued` shipments while unconditionally refusing `blocked` shipments (preserving the blocked-manifest seal in both live and `--dry-run` modes until governed `UnblockShipment`), governed requeue (`active -> queued` + clearing `custom_fields.scheduler_baseline_claim` + `status_changed` event) when force-removing an eligible unstarted claim-assigned `active` member (`scheduler_baseline_claim == shipmentID` and no `WORK_STARTED:` comment in the current claim epoch; refusing already-started or un-claimed active members) or force-moving an eligible unstarted claim-assigned `active` member from an `active` source shipment to a `queued` target shipment (so `ClaimShipment(target)` can later activate and stamp `scheduler_baseline_claim: targetShipmentID`), a zero-write read-only `--dry-run` preview path (refusing pending recovery journals and avoiding SQLite cache-miss writes), durable `remove_item` and `move_item` recovery journal protocols that transition the on-disk journal to `Phase: "committed"` immediately after all writes and `phase: "committed"` audit events succeed and before calling `cleanupShipmentOperationJournal` (preventing rollback if journal cleanup fails), covering crash-between-writes recovery and left-behind `Phase: "committed"` journal finalization through the real `lockShipmentLifecycleGlobal` lifecycle barrier (`reconcileShipmentLifecycleIntent`), `ErrWriteIndeterminate` journal retention (skipping in-memory compensation), `ErrWriteNotApplied` in-memory preimage rollback + journal removal, and partial audit-write rollback/aborted-event compensation (restoring the shipment manifest(s) AND the removed/moved member artifact's full preimage including `status` and `custom_fields.scheduler_baseline_claim` in Markdown and SQLite), and `shipment_item_removed` / `shipment_item_moved` JSONL + SQLite-indexed events.
  2. **U2 (`206.002-T`, `code`, blocked by `206.001-T`)**: Implement `ReorderShipmentResult` and `ReorderShipment` in `internal/core/shipment_manifest.go` supporting both explicit `--items` permutation validation and `--auto` topological sorting over the two-phase dependency graph `G` (emitting only root covering feature(s) `isRootCoveringFeature` in the leading prefix, including **every remaining manifest member not already emitted as a root covering feature** — nested/sub-epic dotted features `100.001-F`, tasks, and subtasks — as vertices in `G`, first adding all hard intra-manifest `blocks` edges `B -> A` with cycle detection, and then iterating candidate default `P -> C` parent-before-child edges in deterministic manifest order and admitting `P -> C` into `G` if and only if `P` is not reachable from `C` in the current graph `G` containing all hard `blocks` edges plus previously admitted parent edges), zero-write read-only `--dry-run` preview (refusing pending recovery and avoiding SQLite cache-miss writes), `--force` + `--reason` guard on non-`queued` shipments that unconditionally refuses `blocked` shipments, and `shipment_reordered` events, with unit tests `TestU2_ReorderShipment_*` (including nested-feature `[100-F, T, 100.001-F]` -> `[100-F, 100.001-F, T]`, absent-parent subtask `[T, S]` -> `[S, T]`, and cross-parent `[F, A, B, a, b]` with `A depends_on b` and `B depends_on a` -> `[F, b, A, a, B]` regression cases).
  3. **U3 (`206.003-T`, `code`, blocked by `206.002-T`)**: Wire CLI subcommands `backlogit shipment remove`, `backlogit shipment move`, and `backlogit shipment reorder` in `internal/cli/shipment.go` and MCP tools `backlogit_remove_from_shipment`, `backlogit_move_shipment_item`, and `backlogit_reorder_shipment` in `internal/mcp/tools.go`; register `remove_from_shipment`, `move_shipment_item`, and `reorder_shipment` directly in `.autoharness/backlog-registry.yaml` and add `TestU3_ShipmentManifestCLIAndMCP_*` tests in `internal/cli/registry_parity_test.go`; and regenerate `docs/cli-reference/` via `go run ./cmd/gen-docs docs/cli-reference`.
  4. **Follow-up stash (Phase 2b)**: Capture declarative `shipment reconstitute --plan`, `adopt` manifest/stash-provenance rename propagation, `doctor` manifest integrity checks, and `stash correct --reason` / `stash repoint` in a linked follow-up stash entry referencing `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` and `206-F` / `207-S`.
* **Pros**:
  * Delivers the complete foundational capability to replan queued shipment manifests without hand-editing Markdown files (`remove`, `move`, `reorder --items|--auto`, `--dry-run`, `--force --reason`) in 3 right-sized, test-first tasks that strictly obey the 2-Hour Rule and width isolation.
  * Provides the exact core building blocks that declarative `reconstitute --plan` will compose in Phase 2b.
  * Updates the authoritative `.autoharness/backlog-registry.yaml` (which is drift-ignored in `.autoharness/drift-ignore`) while satisfying both `registry_parity_test.go` and CI's `CLI Reference Drift` check.
* **Cons**:
  * Multi-shipment YAML plan execution (`reconstitute --plan`), `adopt` manifest propagation, `doctor` manifest checks, and `stash repoint` are staged for a subsequent shipment rather than bundled into `207-S`.
* **Effort estimate**: Medium (3 atomic tasks, ~6 hours human-equivalent).

### Option B: Monolithic 5-Subsystem Shipment (`remove`/`move`/`reorder` + `reconstitute --plan` + `adopt` propagation + `doctor` + `stash repoint`)

* **Description**:
  * Stage all five sections of `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` across `internal/core`, `internal/stash`, `internal/db`, `internal/cli`, and `internal/mcp` in a single shipment `207-S`.
* **Pros**:
  * Implements every section of the design doc in one PR.
* **Cons**:
  * Violates the 2-Hour Rule and width isolation (requires 12–15 tasks across 5 distinct subsystems, recreating the exact oversized-shipment problem described in the `201-S` scenario of the design doc itself).
  * High blast radius across shipment lifecycle, `adopt` ID renumbering, `doctor` diagnostics, and stash provenance logs.
* **Effort estimate**: Very High (12+ tasks).

## Trade-off Comparison

| Criterion | Option A (Foundational Primitive Ops in `207-S` + Phase 2b Follow-Up Stash) | Option B (Monolithic 5-Subsystem Shipment) |
|---|---|---|
| Solves hand-editing of shipment manifests | Yes (`remove`, `move`, `reorder --items\|--auto` via CLI and MCP) | Yes |
| 2-Hour Rule & Width Isolation | Pass (3 focused `code` tasks) | Fail (12+ tasks across 5 subsystems) |
| Atomic rollback & audit trail | Durable `remove_item` & `move_item` recovery journals + `MutationEnvelope` + JSONL/SQLite event parity | Complex multi-subsystem transaction surface |
| CI & harness safety | Updates authoritative `.autoharness/backlog-registry.yaml` (drift-ignored) and satisfies `docs/cli-reference/` drift gate | High risk of cross-package conflict |

## Decision

Adopt **Option A**: promote primitive shipment manifest replanning operations (`remove`, `move`, `reorder`) to implementation plan `docs/exec-plans/2026-10-30-shipment-manifest-reshuffle-plan.md` under feature `206-F` and shipment `207-S`, and record a linked follow-up stash entry for Phase 2b (`shipment reconstitute --plan`, `adopt` manifest/stash rename propagation, `doctor` manifest integrity checks, and `stash correct --reason` / `stash repoint`).

## Rejected Alternatives

* **Option B (Monolithic 5-Subsystem Shipment)**: Rejected because bundling all five subsystems into a single shipment violates the 2-Hour Rule and width isolation, whereas landing the primitive manifest operations first delivers immediate replanning value and establishes a clean foundation for Phase 2b.

## Unresolved Questions

* None. All core lock helpers, sentinel errors, event schemas, CLI flags, MCP parameters, and CI drift gates are verified against the current codebase.

## Risks and Mitigations

* **Risk 1 (Cross-shipment lock ordering, journal validation, committed-journal cleanup safety, and crash/indeterminate-write durability in `RemoveFromShipment` and `MoveShipmentItem`)**: Acquiring `lockShipmentMembership` in caller-supplied `(from, to)` order could deadlock if two concurrent moves run in opposite directions (`S1 -> S2` and `S2 -> S1`), leaving an `active` claimed member `active` after a forced removal or active-to-queued transfer prevents `ClaimShipment` on the target shipment from claiming it, leaving the journal at `Phase: "intent"` until `cleanupShipmentOperationJournal` allows a journal-cleanup failure to trigger a full rollback at the next lifecycle barrier, and an in-memory-only `MutationEnvelope` (which skips compensation on `ErrWriteIndeterminate`) or a journal omitted from `validateShipmentLifecycleJournalRecord` (`internal/core/shipment_ops.go`) cannot recover a crash between member mutation and manifest write in `RemoveFromShipment` or `MoveShipmentItem`, an `ErrWriteIndeterminate` outcome, a lost `scheduler_baseline_claim` marker on a claimed member, or a failure on the second audit append.
  * **Mitigation**: Always acquire `lockShipmentLifecycleGlobal` first, then acquire `lockShipmentMembership` on shipment IDs (in canonical lexicographical order `min(from, to)` then `max(from, to)` for moves); require eligible unstarted claim-assigned `active` members (`scheduler_baseline_claim == sourceShipmentID` and no `WORK_STARTED:` in the current claim epoch; refusing already-started active members) to transition `active -> queued` with `scheduler_baseline_claim` cleared when force-removed or force-moved to a `queued` shipment; update `validateShipmentLifecycleJournalRecord` / `loadShipmentOperationJournals` in `internal/core/shipment_ops.go` to accept both `Operation == "remove_item"` and `Operation == "move_item"` (in both `Phase == "intent"` and `Phase == "committed"`); persist durable `remove_item` (for `RemoveFromShipment`) and `move_item` (for `MoveShipmentItem`) recovery journals (`internal/core/shipment_ops.go` + `internal/core/shipment_recovery.go`) with exact preimages of the shipment manifest(s) (`Preimage.Shipment`, plus `Preimage.Related` for `move_item`) AND the removed/moved member artifact's full preimage (`Preimage.Members`, including `status` and `custom_fields.scheduler_baseline_claim`) before mutating the member or manifest(s); durably update the journal on disk to `Phase: "committed"` immediately after all writes and `phase: "committed"` audit event appends succeed and before calling `cleanupShipmentOperationJournal` (and teach `reconcileShipmentLifecycleIntent` / the recovery evidence reader that a `Phase == "committed"` journal or matching `phase: "committed"` `shipment_item_removed` / `shipment_item_moved` event is already committed and must be finalized/cleaned up without rolling back preimages); skip in-memory compensation and retain the `Phase: "intent"` journal on `ErrWriteIndeterminate` for `lockShipmentLifecycleGlobal` barrier rollback recovery (`reconcileShipmentLifecycleIntent`); and roll back in-memory from the preimages and remove the journal on `ErrWriteNotApplied`.
* **Risk 2 (Authoritative `.autoharness/backlog-registry.yaml` parity)**: Registering new MCP tools in `internal/mcp/tools.go` without adding their CLI fallbacks to `.autoharness/backlog-registry.yaml` fails `TestRegistryParity_EveryMCPToolMappedOrDeferred` and leaves agents without authoritative CLI fallback metadata.
  * **Mitigation**: Update `.autoharness/backlog-registry.yaml` (which is listed in `.autoharness/drift-ignore`) directly in U3 (`206.003-T`) with `remove_from_shipment`, `move_shipment_item`, and `reorder_shipment` so both agents and all five `TestRegistryParity_*` assertions consume the authoritative registry.
* **Risk 3 (`CLI Reference Drift` CI gate)**: Adding `remove`, `move`, and `reorder` under `backlogit shipment` changes the Cobra command tree checked by `go run ./cmd/gen-docs docs/cli-reference`.
  * **Mitigation**: Include `go run ./cmd/gen-docs docs/cli-reference` in U3 (`206.003-T`) so `docs/cli-reference/backlogit_shipment*.md` stays byte-identical to the generator output.
