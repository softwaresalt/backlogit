## Context

`EED25928` is a deferred follow-up from the 2026-07-02 Stage harvest docline
hardening plan
(`docs/exec-plans/2026-07-02-stage-harvest-docline-frontmatter-hardening-plan.md`,
option table row 3). It bundles two concerns:

- **(a) Direction 3 (deferred):** change how the Stage harvest commit reaches
  the Ship feature branch so that an *unrelated* Stage-artifact defect (beyond
  docline frontmatter — for example a wrong committed-file scope) cannot ride
  into a Ship PR. Options recorded: Stage pushes its harvest commit to
  `origin/main` before Ship branches, or harvest lands via a dedicated delivery
  mechanism. Deferred originally because it has larger blast radius and alters
  branch/push topology owned partly by Ship.
- **(b) Upstream template drift:** the docline frontmatter contract and the
  pre-harvest lint gate were applied to the in-repo
  `.github/skills/impl-plan/SKILL.md` and `.github/skills/harvest/SKILL.md`,
  but the generating `.tmpl` sources live in the external autoharness repo.

## Decision

### Part (a) — Direction 3: chosen option and operational realization

**Chosen option: Stage pushes its harvest/staging commit to `origin/main`
before Ship branches** (rather than a dedicated delivery mechanism).

This is **already operationally realized** by the Orchestrator's
**Step 1.5 Staging Artifact Merge Gate (NON-NEGOTIABLE)**, which commits and
merges backlog/staging artifacts to `origin/main` via a staging PR *before* any
Ship feature branch is created, and verifies the shipment manifest exists on
`origin/main`. It was practiced for every unit shipped across the
2026-07-11/12 sessions (087-S through 100-F): Ship always branched from a clean,
already-merged `main`, so an unrelated Stage-artifact defect could not ride into
a Ship feature PR through the harvest commit. Direction 3's intent is therefore
satisfied at the workflow level.

Durable codification of this topology lives in the autoharness-**generated**
orchestrator agent definition and `.github/policies/workflow-policies.md` (both
carry a `Generated by: autoharness` marker). Per **Principle IV**, this
workspace must not hand-edit generated harness artifacts as a substitute for the
upstream template, so the durable change belongs upstream (see handoff).

### Part (b) — upstream `.tmpl` drift (out-of-tree)

`.github/skills/impl-plan/SKILL.md` is confirmed generated
(`Generated by autoharness | Template: impl-plan/SKILL.md.tmpl`); the harvest
skill is part of the same generated harness surface. Their generating templates
live in the external autoharness repo. Per **Principle IV** (no out-of-tree
writes from this workspace), the fix must be applied there, not here.

## Upstream handoff (external autoharness repo)

To prevent a regeneration from overwriting the in-repo fixes, apply upstream:

- `impl-plan/SKILL.md.tmpl` and `harvest/SKILL.md.tmpl` — the docline
  frontmatter contract (`doc_type: plan` plus top-level `title`/`source`) and
  the pre-harvest docline lint gate.
- The orchestrator agent template and the `workflow-policies.md` template —
  codify the Step 1.5 Staging Artifact Merge Gate (Stage pushes the
  harvest/staging commit to `origin/main` before Ship branches) as a durable
  policy.

## Status

`EED25928` is resolved from this workspace's perspective:

- Direction 3's intent is satisfied operationally via the Step 1.5 gate.
- The durable template/policy work is an upstream autoharness-repo handoff
  (out-of-tree, Principle IV) and must not be forced into generated in-repo
  artifacts here.

The stash `EED25928` is archived with this decision as its durable trace.
