## Why This Is a P-002 Breach

### What P-002 and Constitution II require

Constitution Principle II (NON-NEGOTIABLE) requires: write test, confirm
it fails (red), implement, confirm it passes (green). Never write production
code before the corresponding test exists and has been observed to fail.

P-002 operationalizes this as the harness-satisfied precondition: tests MUST
exist and MUST be confirmed failing BEFORE any production code is written.
The red phase must be in an immutable committed state before implementation begins.

### What the breach is

Commit `87f06f62` introduced production stub functions for
`ReconcileArchivedLifecycle` and `CorrectStashProvenance` returning
`ErrNotImplemented`. These stubs are **observable production behavior**:

- They compile as production code in `internal/core/`
- They return a defined, exported sentinel error (`ErrNotImplemented`)
- They define the function signatures, parameter types, and return types
- They constitute production code that existed in the repository before any
  test was written or committed

Commit `e7276bcf` (RED harness) came AFTER `87f06f62` (production stubs).
At the point `e7276bcf` was written, production code already existed. The
tests compiled against pre-existing stubs — they did NOT drive the interface
design as P-002 intends.


### Additional P-002 deviation: 152.004-T surface commit (3b651ae8)

Post-review analysis of commit `3b651ae8` (labeled "RED surface harness" in the
session memory) reveals it also introduced production CLI and MCP code in the
same commit as the RED tests:

- `internal/cli/reconcile.go` — production CLI command with `not_implemented` stub
- `internal/mcp/tools_reconcile.go` — production MCP tool registration with `not_implemented`
- `internal/cli/reconcile_test.go` — RED CLI tests (VERIFIED FAIL)
- `internal/mcp/tools_reconcile_test.go` — RED MCP tests

This is a second distinct P-002 breach pattern within 152-F: production surface code
landed in the same commit as the RED surface tests (no separate red-only state). This
mirrors the 131-S/148-F pattern (all-in-one commit) rather than the stub-before-RED
pattern of `87f06f62`.

INC-P002-152F-134S therefore covers two breach points:
1. `87f06f62` (stubs) before `e7276bcf` (RED core tests) — stub-before-RED ordering
2. `3b651ae8` (production CLI+MCP + tests, same commit) — all-in-one surface commit
### What is NOT a cure

The feature was implemented across declaration → RED → GREEN waves. While the
commits follow that order, the declaration wave included production stub
functions, not merely type declarations. This distinction is material:

- Type-only declarations (structs, interfaces) do not constitute production
  behavior and do not by themselves violate P-002
- Stub functions returning `ErrNotImplemented` constitute observable production
  behavior and MUST follow tests, not precede them

The 152-F commit history is permanently non-compliant and non-curable as a
historical fact. Non-curability applies to the historical record only; it
does not discharge the forward-control obligation documented below.

## Forward Control Efficacy Analysis

152-F was shipped while forward controls FC-1 through FC-4, established by
INC-P002-131S-148F, were in force. The following table records how each
control performed against the stub-before-RED pattern:

| Control | Definition | Status | Finding |
|---|---|---|---|
| FC-1 | Separate committed RED phase before GREEN | SATISFIED (narrow) | `e7276bcf` precedes `4c964c21`. FC-1 is blind to production code introduced before the RED commit in an earlier task wave. |
| FC-2 | Ship preflight: for each task, the harness commit does not contain the corresponding production code | NOT EXECUTED or INEFFECTIVE | FC-2 step 2 checks the harness commit's own contents; a preceding stub commit is invisible to it. Whether FC-2 was executed or silently passed due to this scope gap cannot be determined from the ship session memory. This is a structural gap in FC-2's implementation — it cannot detect the stub-before-RED pattern. |
| FC-3 | 134-S closure includes per-task P-002 compliance table | PARTIALLY SATISFIED | Per-task deviation table in `docs/closure/2026-08-30-152f-134s-p002-incident-closure.md`. Additional breach at `3b651ae8` identified (152.004-T): CLI/MCP production code + tests landed in same commit. |
| FC-4 | Forward-control applicability check | SATISFIED | 134-S was a new shipment under FC governance from its creation. |

**Gap identified**: FC-2's step 2 check is scoped to the harness commit's own diff. A production stub committed in an earlier wave is invisible to this check. This gap is a structural defect in FC-2 implementation that permitted the stub-before-RED pattern to pass undetected.

## Forward-Control Amendment

This incident establishes the need for a new forward-control measure:

**FC-5 (stub-before-RED guard)**: For each task with a RED-phase harness commit,
no ancestor commit in the same feature branch may introduce production code
(including stub functions with non-empty bodies, even those returning only
`ErrNotImplemented`) for that same task's target symbols, unless that commit is
itself in a prior completed task wave AND was produced under an explicit
harness-exempt P-002.1 condition.

**Implementation deferral**: FC-5 is deferred to stash A2C91FE5 (deterministic
harness-wide workflow-policy enforcement engine, active, priority: high). A2C91FE5
proposes machine-enforced prerequisite graph evaluation that would structurally
prevent the stub-before-RED pattern. A2C91FE5 MUST ship before FC-5 can be
automated; until then, FC-5 is a manual Ship pre-flight obligation. FC-1 and FC-2
remain in force as partial controls during the deferral period.
