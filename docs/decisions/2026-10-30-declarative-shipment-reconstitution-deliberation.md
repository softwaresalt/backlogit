## Problem Frame

* Active stash entry `40CC5C6B` (*Phase 2b follow-up from DE3E7B67*) originally tracked four capabilities from `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` §§2–5. In Phase 1A (`208-F` / `209-S`, merged on `main` at `34e656a0b85681cca408d18b9c8cddf068db17c3`), items (2), (3), and (4) shipped:
  * `AdoptItemWithOptions` (`KeepID`, atomic rewrite of shipment `custom_fields.items`, `.backlogit/archive/stash.jsonl` `harvested_artifact_id`, and `.backlogit/archive/provenance_corrections.jsonl`),
  * History-safe ID allocation (`NextTypedHierarchicalIDForWorkspace` / `NextIDForWorkspace` in `internal/core/hierarchy.go` and `internal/core/naming.go`),
  * `CorrectStashProvenance` (`--force`) with CLI/MCP parity, and
  * `Doctor` shipment manifest integrity checks (`dangling_shipment_member`, `duplicate_shipment_membership`, `split_feature_across_shipments`, `forward_shipment_dependency`, `unsequenced_queued_shipment` in `internal/core/doctor_shipment_manifest.go`).
* **Phase 1B (this session)** delivers the remaining capability (1) of `40CC5C6B`: **declarative multi-shipment manifest reconstitution (`backlogit shipment reconstitute --plan <path.yaml> [--dry-run] [--force --reason <text>] [--json]` and MCP `backlogit_reconstitute_shipment`)** under covering feature `209-F` and shipment `210-S`.
* When a queued shipment (such as `201-S` in `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` §2) is split into `N` chained shipments with new covering features and re-parented tasks, orchestrating individual `add`, `adopt`, `shipment create`, `shipment move`, `shipment reorder`, and `dep add` commands across dozens of artifacts risks partial state on a midway error and requires manual bookkeeping of renumbered task IDs (`oldID -> newID`). Declarative reconstitution validates the entire multi-shipment plan up front, supports a zero-write `--dry-run` preview returning the full diff and ID mapping, and applies the transformation atomically with byte-identical rollback on any failure.

## Research Findings

* **Primitive manifest foundation (`internal/core/shipment_ops.go`, `internal/core/shipment_manifest.go`)**:
  * `validateShipmentManifestQueueGuard`, `ensureNoPendingShipmentRecoveryReadOnly`, `readArtifactFromDiskReadOnly`, and `readShipmentFromDiskReadOnly` (`internal/core/shipment_ops.go:602-668`) already enforce the queued-only default (unconditionally refusing `blocked` shipments via `hasBlockedShipmentSeal` / `blerrors.ErrShipmentConflict` even with `Force: true`, and requiring `Force: true` + non-empty `Reason` for `active`, `shipped`, or `abandoned` shipments) and provide a zero-write read-only inspection path for `DryRun: true`.
  * Destination-aware `planMemberDetach` and claim-marker transitions (`internal/core/shipment_ops.go`) apply to **every member moving out of an `active` source shipment (`Force: true` + `Reason`)**, not only to `unassigned_items`: first verify that each moving or unassigned active member is an eligible unstarted claim-assigned member of its `active` source shipment (`custom_fields.scheduler_baseline_claim == sourceShipmentID` and no `WORK_STARTED:` comment in the current claim epoch; otherwise refuse in both `--dry-run` and live execution with `blerrors.ErrInvalidStatus` / `blerrors.ErrShipmentConflict`, matching `RemoveFromShipment` and `MoveShipmentItem`). Second, if the member moves to a `queued` target shipment (or to `unassigned_items`), transition its `status` from `active` to `queued`, clear `custom_fields.scheduler_baseline_claim`, and emit a `status_changed` (`active -> queued`) event on its item log; if it moves to an `active` target shipment, keep `status: active` and update `custom_fields.scheduler_baseline_claim = targetShipmentID`. Both `--dry-run` (`U1`) and live execution (`U2`) project and apply these exact member `status` and `scheduler_baseline_claim` transitions.
  * `buildReorderGraph`, `autoOrder`, and `validateExplicit` (`internal/core/shipment_manifest.go:108-250`) implement the two-phase dependency graph `G` (root covering features leading, hard intra-manifest `blocks` edges first, cycle-safe parent-before-child edges second). Reusing `buildReorderGraph` inside `ReconstituteShipments` guarantees identical `--auto` and `explicit_order` semantics between `shipment reorder` and `shipment reconstitute`.
* **Adoption, ID allocation, durable `reconstitute` recovery journal, `ctx`-local post-hook buffering, `commit_links` rollback, & interoperable locking (`internal/core/shipment_lifecycle.go`, `internal/core/shipment_ops.go`, `internal/core/shipment_recovery.go`, `internal/core/hierarchy.go`, `internal/core/stash_lock.go`, `internal/hooks/hooks.go`, `internal/events/`)**:
  * `AdoptItemWithOptions` (`internal/core/shipment_lifecycle.go:1202-1515`) re-parents an item under a target feature (`KeepID: false` allocates a history-safe hierarchical ID via `allocateTypedHierarchicalID` and propagates `oldID -> newID` across `dependencies`, `links`, shipment manifests, `archive/stash.jsonl`, and `archive/provenance_corrections.jsonl`; `KeepID: true` preserves `oldID == newID`).
  * `adoptItem` acquires `lockActiveStash(ws)` (`internal/core/stash_lock.go:62`) when `!opts.KeepID && ws.DB != nil`, while `AssociateCommit` acquires an item-log lock (`events.LockItemLogCrossProcess`) before acquiring `lockShipmentLifecycleGlobal` inside `persistArtifact`. To prevent both same-goroutine deadlock on `stashMu` and lock-order inversion against `AssociateCommit`, `ReconstituteShipments` acquires outer locks in the order `lockActiveStash(ws)` (`withStashLockHeld(ctx)` so nested `adoptItem` calls skip `lockActiveStash(ws)`) -> `lockShipmentLifecycleGlobal(ctx, ws)` (which runs `recoverPendingShipmentOperations` and is re-entrant via context) -> `lockShipmentMembership(ctx, ws, id)` in sorted shipment ID order -> `lockArtifactMutations(ctx, ws, affectedArtifactIDs)` in sorted ID order, and NEVER bulk-acquires `events.LockItemLogCrossProcess` upfront under `lockShipmentLifecycleGlobal`. Instead, `events.LockItemLogCrossProcess` is acquired **only briefly per-item** during individual event appends and during operation-correlated log rollback (`restoreReconstitutedItemLogs`, following `restoreShipArtifactsDetailed` / `removeShipmentOperationEvents`).
  * To survive process crashes midway through multi-file mutations, `ReconstituteShipments` persists a durable `Operation: "reconstitute"` (`RecoveryPolicy: "rollback"`) operation journal (`internal/core/shipment_ops.go` + `internal/core/shipment_recovery.go`, matching `remove_item` and `move_item` from `207-S`) with `Phase: "intent"`, `CorrelationID`, preimage byte/struct snapshots of all touched shipment and member `.md` files, `archive/stash.jsonl` and `archive/provenance_corrections.jsonl` snapshots, `commit_links` preimages, deterministically pre-computed `CreatedArtifactIDs` / `CreatedPaths`, and `AdoptedIDMap` (`oldID -> newID`). After all mutations, `Doctor` manifest integrity check, and `shipment_reconstituted` events succeed, it durably transitions the journal on disk to `Phase: "committed"` BEFORE calling `cleanupShipmentOperationJournal` and flushing buffered post-hooks. `validateShipmentLifecycleJournalRecord` and `reconcileShipmentLifecycleIntent` handle `Operation == "reconstitute"`: finalizing and removing a `Phase == "committed"` journal without rollback, or executing idempotent rollback for `Phase == "intent"` and retaining the `intent` journal if rollback itself errors so the next `lockShipmentLifecycleGlobal` barrier retries recovery.
  * During `ReconstituteShipments` execution, post-hook buffering is strictly **operation-local via `context.Context`** (`hooks.WithBufferedPostHooks(ctx)` / `hooks.FlushBufferedPostHooks(ctx, ws.HookRunner)` in `internal/hooks/hooks.go`): `ws.HookRunner` is never nil'd, replaced, or mutated on `ws` (leaving concurrent operations on the same `Workspace` unaffected), synchronous `ws.HookRunner.FirePre(...)` runs normally on every child `CreateArtifact` and `AdoptItemWithOptions` call (so a rejecting pre-hook vetoes the operation and triggers clean rollback), and `HookRunner.FirePost(ctx, ...)` appends `(event, hookCtx)` entries to the `ctx`-local buffer instead of dispatching immediately, flushing only after the journal reaches `Phase: "committed"` (and discarding the buffer on rollback).
  * Because `bldb.Rehydrate` does not clear or rebuild `commit_links` after `AdoptItemWithOptions` renames (`oldID -> newID`), `ReconstituteShipments` records `commit_links` preimages in the journal before executing child renames and restores `commit_links` during rollback alongside `bldb.Rehydrate`. Furthermore, `restoreReconstitutedItemLogs` locks one item log at a time (`events.LockItemLogCrossProcess`), renames `<newID>.jsonl -> <oldID>.jsonl` when needed, reads the current `.jsonl` lines, filters out only events carrying `_reconstitute_operation: correlationID` while preserving any independent concurrent `AppendComment` or `AssociateCommit` events, writes the filtered log atomically, and re-indexes it in SQLite.
* **Post-apply `Doctor` manifest integrity verification (`internal/core/doctor_shipment_manifest.go`)**:
  * `detectShipmentManifestFindings` (`internal/core/doctor_shipment_manifest.go:38-145`) checks non-terminal shipments for `FindingDanglingShipmentMember`, `FindingDuplicateShipmentMembership`, `FindingSplitFeatureAcrossShipments`, `FindingForwardShipmentDependency`, and `FindingUnsequencedQueuedShipments`. Validating these invariants both in the pre-execution planner (supporting `--dry-run`) and as a post-apply gate before committing guarantees that a reconstituted workspace always leaves `backlogit doctor` clean.

## Options Evaluated

### Option A: Single-Plan Declarative Reconstitution with Read-Only `--dry-run` Planner and Full Snapshot/Restore Rollback (`209-F` / `210-S`) — Chosen

* **Description**: Implement `ReconstitutePlan` YAML parsing and validation, a zero-write read-only `--dry-run` diff planner, and atomic `ReconstituteShipments` execution in `internal/core/shipment_reconstitute.go`, wired to CLI `backlogit shipment reconstitute --plan <path.yaml> [--dry-run] [--force --reason <text>] [--json]` and MCP `backlogit_reconstitute_shipment` across 3 sequential single-domain (`code`) tasks (`209.001-T` -> `209.002-T` -> `209.003-T`):
  * **U1 (`209.001-T`)**: `ReconstitutePlan` YAML schema (with duplicate-YAML-key and unknown-field rejection, and symlink-aware real-workspace-root containment on `plan_path` resolving `filepath.EvalSymlinks(ws.RootPath)`, walking every component from `ws.RootPath` to `plan_path` with `os.Lstat` / `IsSymlinkOrReparsePoint`, and verifying `filepath.EvalSymlinks` stays inside the real workspace root so valid workspace-root plan files like `plans/reshuffle.yaml` outside `.backlogit/` succeed while intermediate symlinked directories escaping the workspace are rejected), comprehensive preflight validation (source shipment status guard, destination-aware `planMemberDetach` and `scheduler_baseline_claim` transition validation for every member moving out of an `active` source shipment as well as `unassigned_items`, complete partition + `unassigned_items` accounting, single-membership across all non-terminal shipments, no split features across shipments, acyclic shipment `blocks` DAG, no `unsequenced` queued shipments when `>1` queued shipment exists, no `forward_shipment_dependency` across shipments, and two-phase `buildReorderGraph` manifest ordering), and zero-write read-only `DryRun: true` simulation returning `ReconstituteShipmentResult` (`CreatedFeatures`, `CreatedShipments`, `AdoptedIDMap`, `BeforeManifests`, `AfterManifests`, `DependencyChanges`, projected member `status` / `scheduler_baseline_claim` transitions, and `PlanDigest`).
  * **U2 (`209.002-T`)**: Live all-or-nothing `ReconstituteShipments` execution under interoperable outer lock ordering (`lockActiveStash(ws)` outermost with `withStashLockHeld(ctx)` -> `lockShipmentLifecycleGlobal(ctx, ws)` -> `lockShipmentMembership(ctx, ws, id)` in sorted shipment ID order -> `lockArtifactMutations(ctx, ws, affectedArtifactIDs)` in sorted ID order, with `events.LockItemLogCrossProcess` acquired only briefly per-item during individual event appends and `restoreReconstitutedItemLogs`), persisting a durable `Operation: "reconstitute"` (`RecoveryPolicy: "rollback"`) operation journal (`internal/core/shipment_ops.go` + `internal/core/shipment_recovery.go`) with preimage `.md`/`stash.jsonl`/`provenance_corrections.jsonl`/`commit_links` snapshots, pre-computed `CreatedArtifactIDs`/`CreatedPaths`, and `AdoptedIDMap`, buffering post-hooks operation-locally via `context.Context` (`hooks.WithBufferedPostHooks(ctx)` / `hooks.FlushBufferedPostHooks(ctx, ws.HookRunner)` in `internal/hooks/hooks.go`) without mutating `ws.HookRunner` or bypassing `FirePre`, composing feature creation (`CreateArtifact` + `related_to` link), `AdoptItemWithOptions` re-parenting with `oldID -> newID` translation across target manifests and `blocks` edges, destination-aware `planMemberDetach` and `scheduler_baseline_claim` transitions for all reassigned/unassigned members moving out of `active` source shipments, shipment creation/update with topological ordering, `blocks_on` and `rewire` dependency edge mutations, post-apply `detectShipmentManifestFindings` verification, correlated `shipment_reconstituted` JSONL/SQLite audit events on all source and target shipments, durable journal transition to `Phase: "committed"` before cleanup and post-hook flush, and idempotent rollback via `reconcileShipmentLifecycleIntent` + `restoreReconstitutedItemLogs` on any midway failure or crash recovery.
  * **U3 (`209.003-T`)**: CLI `backlogit shipment reconstitute` (`internal/cli/shipment_manifest.go`, `internal/cli/shipment.go`), MCP `backlogit_reconstitute_shipment` (`internal/mcp/tools.go`, `internal/mcp/shipment_manifest_handlers.go`), `.autoharness/backlog-registry.yaml` (`reconstitute_shipment`), end-to-end 1-to-6 shipment split + CLI/MCP parity tests, and `docs/cli-reference/` regeneration.
* **Pros**:
  * Directly satisfies every acceptance criterion in `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` §2 and `40CC5C6B` item (1).
  * Respects the 2-Hour Rule with 3 tightly scoped `code` units.
  * Full pre-mutation byte snapshot + new-file removal + SQLite `Rehydrate` rollback guarantees byte-identical workspace state if any step fails midway.
* **Cons**:
  * Snapshot/restore rollback must track both pre-existing modified files and newly created artifact/log files; addressed explicitly in U2 with failure-injection tests.

### Option B: Best-Effort Sequential Script Without Snapshot Rollback — Rejected

* **Description**: Execute `CreateArtifact`, `AdoptItem`, and `CreateShipment` sequentially without a read-only dry-run planner or full filesystem/SQLite rollback on midway failure.
* **Cons**:
  * Violates the all-or-nothing requirement in `docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` §2 ("A failure injected midway leaves the workspace identical to its pre-command state") and cannot support a zero-write `--dry-run` preview.

## Decision

Adopt **Option A**: promote `40CC5C6B` item (1) to implementation plan `docs/exec-plans/2026-10-30-declarative-shipment-reconstitution-plan.md` under covering feature `209-F` (`209.001-T`..`209.003-T`) and shipment `210-S` (blocked by shipped `209-S`), and harvest `40CC5C6B` into `209-F` so `40CC5C6B` is archived upon harvest.
