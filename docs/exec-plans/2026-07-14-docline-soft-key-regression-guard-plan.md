# Bounded Docline Soft-key Regression Guard Implementation Plan

## Problem Frame

Docline defaults make missing `chunk_strategy` and `schema_version` invisible to current validation. The guard must persist after backfill without combining live inventory, value parsing, temporary Git repositories, and open extension-key compatibility into one oversized task. The protected untracked scratch file remains outside all mutations.

**Base-contract / extension ownership (authoritative for PR #241).** Docline owns only the base Markdown/frontmatter ingestion contract and its compatibility rules. That base contract is open/extensible: producer-specific optional properties (for example the backlogit-owned `size`, `size_source`, `size_ruleset_version`) may be added and MUST be preserved unchanged at the top level. The **current production seam contradicts this**: `internal/docline/normalize.go` folds every non-contract top-level key into the `docline` namespace (`foldUnderDocline`), and `internal/docline/policy.go` defines a **closed** `contractFields` set that drives that relocation. This plan's `107.009-T` therefore becomes an **executable production-contract task**, and the correction is honest about the full seam AND the current-HEAD behavior: at current HEAD `Normalize` **relocates** unknown top-level keys under the `docline` namespace (folded via `foldUnderDocline` and preserved as a nested map by `FromMap`/`ToMap`), so they are **not dropped today** — they simply no longer stay top-level. Because `BaseFrontmatter.ToMap()` in `internal/docline/frontmatter.go` emits **only** the base-contract fields plus the `docline` namespace, removing the fold **without** adding a `frontmatter.go` carrier would convert that relocation into a **latent top-level drop** — so both seams must change together. `107.009-T` therefore changes **both** production seams — `internal/docline/normalize.go` (stop folding non-contract top-level keys under `docline`) **and** `internal/docline/frontmatter.go` (capture unknown top-level, non-`docline` keys in `FromMap` into a carrier on `BaseFrontmatter` and re-emit them unchanged in `ToMap`) — so unknown top-level extension properties pass through **in place** (docline validates/normalizes only its own base fields and must not relocate extension fields under `docline`), and updates the contradictory normalization unit tests. The size-extension regression is split into a **RED-first integration task `107.010-T`** (`tests/integration/docline_extension_compat_test.go`), observed failing before the seam change; `107.009-T` depends on `107.010-T` and turns it GREEN. Pass-through is **docline** base-contract behavior; `size` semantics (validation, defaults, provenance, composition) remain **backlogit-owned** and are out of scope here. This plan adds no production filesystem containment, which is unrelated to the base-contract/extension boundary.

**Schema and authoring-guide correction (PR #241; base/derived model clarified PR #242 cycle 2).** The base JSON schema itself also contradicts the open base contract: `schemas/docline/base-frontmatter-v1.schema.json` declares top-level `additionalProperties: false`, which **rejects** producer-owned top-level extension keys, and the authoring guide (`docs/docline-frontmatter-authoring-guide.md`) still says every non-contract key belongs under `docline` (migration "moves every unknown key there"). These are corrected by two additional width-isolated tasks: `107.011-T` opens the base schema so it **accepts** producer-owned top-level extension properties generally (docline is the BASE contract and stays open/extensible), **without** enumerating or validating the backlogit size fields and **without** any base-schema distinction between "declared/sanctioned" and "arbitrary legacy" extension keys — the base validator intentionally validates only the docline-owned base fields and ignores extension semantics; and `107.012-T` rewrites the guide to the base/extension inheritance model. Validation of size/`size_source`/`size_ruleset_version` semantics is owned by backlogit's future **derived** contract, not the base schema. The earlier "no schema changes" framing was false at the shipment level and is corrected here: `107.009-T` (the Go codec task) makes no schema change, but this shipment **does** carry a bounded JSON-schema change in `107.011-T`.

### `107.010-T` — RED-first extension pass-through regression (test-only)

**File:** `tests/integration/docline_extension_compat_test.go`

RED-first integration regression written **before** the `107.009-T` seam change. Representative backlogit-owned extension keys (`size`, `size_source`, `size_ruleset_version`) added to an in-scope doc must:

* stay **top-level** and **semantically/deep-value equivalent** through `Normalize` — the extension key/value graph is preserved at the top level (never relocated under `docline`, never dropped on serialization) and the **document body bytes** remain unchanged. `Normalize` reserializes YAML via the frontmatter codec (`mdfront.Encode`), which MAY canonicalize key ordering, quote style, scalar spelling, comments, and anchors, so the assertion is **deep-value equivalence + top-level placement + unchanged body bytes + idempotency**, **not** raw frontmatter byte/lexical preservation (no raw-byte guarantee is made unless a future YAML-node/raw-byte design is explicitly chosen);
* be preserved and re-emitted in place by docline as a **semantically/deep-value equivalent** key/value graph but **never** defaulted, rewritten in value, synthesized, validated, or semantically interpreted;
* survive a lint/migration round-trip without body mutation; the transform stays idempotent.

These assertions **fail at current HEAD** for a reason the plan states honestly: `normalize.go` folds non-contract top-level keys under the `docline` namespace, and `BaseFrontmatter.FromMap`/`ToMap` (`frontmatter.go`) **preserve** that nested `docline` map, so the keys are **relocated** under `docline` (not top-level) and round-trip intact — they are **not dropped today**. Because `ToMap` emits only base-contract fields plus `docline`, the missing top-level carrier is a **latent** drop that would occur only if the fold were removed without adding the carrier. `107.010-T` is the dependency gate for `107.009-T`; test-only, no production change.

### `107.009-T` — Preserve unknown top-level extension keys in docline normalization (production pass-through)

**Files (production + tests):** `internal/docline/normalize.go` (stop folding non-contract keys under `docline`), `internal/docline/frontmatter.go` (`BaseFrontmatter` carrier + `FromMap`/`ToMap` re-emission of unknown top-level keys), `internal/docline/normalize_test.go` (update contradictory assertions). `internal/docline/policy_test.go` is **not** changed. The size-extension regression lives in `107.010-T`, not here.

**Production-contract correction (PR #241; current-HEAD causal correction PR #242 cycle 2):** the current seam contradicts the authoritative base/extension contract, and the correction is honest about current-HEAD behavior. At current HEAD `Normalize` folds every non-contract top-level key under the `docline` namespace via `foldUnderDocline` (`policy.go` defines the **closed** `contractFields` set that drives that relocation), and `FromMap`/`ToMap` preserve that nested `docline` map, so unknown top-level keys are **relocated** (moved off the top level) and **not dropped today**. Because `BaseFrontmatter.ToMap()` emits **only** base-contract fields plus `docline`, the absence of a top-level carrier is a **latent** drop that manifests only if the fold is removed without the carrier. The authoritative contract requires docline to preserve unknown top-level extension properties **unchanged in place** and to **never relocate** them under `docline`, validating/normalizing only its own base fields — so both the fold-stop and the carrier must land together.

This is an **executable ≤2h production-contract task**, gated behind the `107.010-T` RED:

1. **Serialization seam** — `internal/docline/frontmatter.go`: `BaseFrontmatter` gains a carrier for non-contract, non-`docline` top-level keys; `FromMap` captures them and `ToMap` re-emits them unchanged at the top level (without this, removing the fold alone would still drop the keys).
2. **Normalization seam** — `internal/docline/normalize.go`: non-contract top-level keys pass through **unchanged in place** instead of being folded under `docline`. Docline still reads/emits its own `docline` namespace and base contract fields; body bytes and idempotency (`Normalize(Normalize(x)) == Normalize(x)`) are preserved.
3. **Update contradictory tests** — `TestNormalize_ContractSurfaceHoldsOnlyContractKeys` (asserts every top-level key is a contract field) and `TestNormalize_FoldsLegacyTypeUnderDocline` (asserts non-contract keys are folded away) are updated to assert top-level pass-through. `policy_test.go` `TestIsContractField` **remains valid and unchanged** (the closed contract set still governs which base fields docline normalizes; it no longer governs relocation of unknown keys).

Ownership stays explicit: top-level pass-through is **docline** base-contract behavior; `size` validation, defaults, provenance, and composition remain **backlogit-owned** and are out of scope here. Test-first: the `107.010-T` failing assertions are observed before the seam change. This task makes no schema or CLI-distribution change (the correlated schema change is the separate `107.011-T`).

### `107.011-T` — Open the base JSON schema to accept producer-owned top-level extension properties (schema, test-first)

**File:** `schemas/docline/base-frontmatter-v1.schema.json` (plus a schema-validation test).

The base schema currently declares top-level `additionalProperties: false`, which **contradicts** the open base contract and rejects producer-owned top-level extension keys (`size`, `size_source`, `size_ruleset_version`). Open it so it **accepts** additional producer-owned top-level extension properties generally (for example `additionalProperties: true`, or an equivalently open construct), **without** enumerating `size`/`size_source`/`size_ruleset_version` as base fields and **without** encoding any distinction between "declared/sanctioned" and "arbitrary legacy" extension keys. The base schema neither enumerates nor validates backlogit size semantics; it simply stops rejecting extension properties while continuing to validate **only** the docline-owned base fields (required `title`/`source`/`ingested_at`/`doc_type`, `minLength`, closed `doc_type` vocabulary, `content_sha256` pattern) unchanged. This intentional openness means the base validator ignores extension semantics by design — no claimed lint divergence between "sanctioned" and "legacy" keys is needed at the base layer.

**Test-first:** write the failing schema-validation coverage first (representative producer extension keys `size`/`size_source`/`size_ruleset_version` validate at the top level against the base schema; base-owned field validation is unchanged and still rejects base-field violations), then change the schema to turn it green. The hand-rolled Go validator (`internal/docline/validate.go`) validates only base fields and does not enforce `additionalProperties` today, so no Go behavior regression is introduced; it stays consistent with the schema contract and continues to intentionally ignore extension semantics. Validation of size/`size_source`/`size_ruleset_version` semantics is owned by backlogit's future **derived** schema/validators, out of scope here. Width-isolated to the schema family; gated behind the `107.010-T` RED and correlated with `107.009-T` and `107.012-T` (the Schema-CLI-Docs Coupling Reviewer confirms the three stay consistent). No CLI-distribution change.

### `107.012-T` — Document the base/extension inheritance model (docs)

**File:** `docs/docline-frontmatter-authoring-guide.md`.

The guide currently states every non-contract key belongs under `docline` and that migration "moves every unknown key there (move, never drop)", contradicting the open base/extension contract. Rewrite the ownership model as an **inheritance model** with a clean base/derived split: docline is the BASE contract and owns and validates only the base fields; docline **accepts** additional top-level extension properties (its open base schema no longer rejects them) and **preserves** them in place — re-emitting/serializing caller-provided extension properties at the top level when present — but never interprets, defaults, aggregates, validates, or synthesizes them. Derived producers such as backlogit **inherit/extend** the base contract and **own** their top-level extension fields (`size`, `size_source`, `size_ruleset_version`); validation of those extension semantics belongs to backlogit's future **derived** contract, not to docline. The guide must explain the two distinct responsibilities plainly — (1) **extension acceptance/preservation** (base schema accepts, codec preserves in place as a semantically/deep-value equivalent key/value graph) and (2) **producer-owned validation** (extension semantics validated only by the owning producer's derived contract) — and must **not** introduce a base-layer distinction between "declared/sanctioned" and "arbitrary legacy" keys or imply docline validates extension semantics. Describe **legacy migration** honestly and forward-only (the new codec in `107.009-T` stops folding NEW unknown top-level keys and preserves them in place, but does **not** unfold or auto-relocate values already nested under `docline` — generic automatic relocation is **impossible** because, once nested, docline-owned metadata and previously-folded producer values are indistinguishable; known formerly-folded producer keys would need an explicit **manual** bounded migration re-authored at the top level, never a generic automatic unfold; the tracked corpus has **zero** folded producer keys (`docline.size*`), so the contract is forward-only with no back-migration required in practice; migration synthesizes nothing under `docline` and drops nothing). Name the canonical derived-key location explicitly: **top-level**. Body-preserving and docline-lint-clean; depends on `107.009-T` and `107.011-T` because the guide must describe the final codec + schema behavior. No production code or schema change in this task.
