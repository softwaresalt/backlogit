## Scope

This document describes how backlogit custodies verification keys
(trust anchors), where the root of trust lives, how keys are rotated and
revoked, and which attacks the design does and does not close. It covers the
resolver in `internal/core` and the `backlogit trust-anchor` command group.

## Public-only custody

The workspace stores only public verification material: an anchor declares
`id`, `role`, `algo`, `public_key_ref`, `fingerprint`, an optional
`not_before`/`not_after` window, and an advisory `status`. Private signing
keys are never stored in, generated by, or read from the workspace. This is
public-only custody: a workspace-write attacker learns nothing that lets them
sign, but can edit every workspace field, so workspace fields are never the
root of trust.

## External-pin root of trust

The root of trust is an external pin set provisioned outside the workspace
(an `ExternalPinSetProvider`). It is authoritative:

- An absent pin set disables trust anchors and every resolution fails closed.
- A fingerprint that is not pinned is never trusted, whatever the workspace
  `status` says. Workspace `status` is advisory: it can restrict (a revoked
  status is honored) but never grants trust, so revocation is monotonic.
- Each pin may carry a binding of the externally authoritative `role` and
  validity window. The resolver requires the workspace role to equal the bound
  role and permits the workspace window only to narrow, never widen, the
  external window (later `not_after`, earlier `not_before`, or a removed bound
  is denied). A pin with no binding cannot verify role or validity, so the
  resolver denies it (fail closed). There is no documentation-only escape
  hatch for role or validity.
- The resolved key's pinned algorithm must equal any declared algorithm, and a
  requested purpose must equal the anchor role.

The CLI provisions the pin set from environment variables that live outside the
workspace:

- `BACKLOGIT_TRUST_PINS`: comma or whitespace separated entries.
- `BACKLOGIT_TRUST_PINS_FILE`: an operator-owned file, one entry per line with
  `#` comments.

An entry is `<fingerprint>=<role>[;not_before=<RFC3339>][;not_after=<RFC3339>]`
for a bound pin. A bare `<fingerprint>` pins the fingerprint for the add gate
but cannot resolve a key because its role and validity are unverifiable. A
malformed entry fails closed as an absent pin set.

## Pin-set provenance

Pin-set provenance is the control that establishes how the authenticity of the
external pin set is established and verified. The implemented behavior is:

1. The pin set is supplied only through the injected provider; the core never
   reads it from workspace config and never writes it.
2. The CLI provider reads the environment variables above and an
   operator-owned file; the file path is operator-chosen and outside the
   workspace.
3. The core does not itself cryptographically verify the pin set. Its
   authenticity and integrity rest on the operating-system access controls of
   the environment or file that the operator provisions.

Explicit residual trust assumption: backlogit trusts whoever can set the
process environment and the operator-owned pin file. An attacker who can alter
either of those, or who controls the process launching the CLI, defeats the
root of trust. A signed or read-only pin-set authority consulted by the
provider is the intended hardening path; it is out of scope for 149-S and is
recorded here as an accepted residual rather than claimed as closed.

## Rotation

Rotation introduces a new anchor and retires the old one. `rotate` requires
operator approval evidence and a new fingerprint that is already in the
external pin set, so a workspace writer cannot introduce an unpinned key. The
old anchor is retired authoritatively: rotate records the old fingerprint
through the same `RevocationAuthority` as revoke and fails closed (denial
audit, no workspace change) when none is injected, so the shipped CLI rotate
currently fails closed with the required external operation. The workspace
status flip is only an advisory projection. Rotation never
widens a role: the new key resolves only under its externally bound role.

## Revocation

Revocation is authoritative only when it is recorded in an external authority.
`revoke` records the tombstone through an injected, non-filesystem
`RevocationAuthority` and only then writes the workspace status as a contained
projection. The resolver consults the same authority (`ApplyRevocations`), and
a tombstone overrides any pin, binding or workspace status, so flipping the
status back to active cannot restore trust.

- A revoke without an injected authority fails closed (non-success) and names
  the fingerprint that must be de-pinned or tombstoned externally. It does not
  flip workspace status and does not claim the key is revoked.
- If the authority records the tombstone but the projection or audit write
  then fails, the outcome is indeterminate and the marker stays outstanding.
- No external-path filesystem writes are authorized.

Resolution uses `ResolveVerificationKeyAuthoritative`, which always applies
the authority's tombstones (a nil authority means no tombstone source is
configured). The shipped CLI wires no concrete authority, so `backlogit trust-anchor
revoke` currently fails closed with the required external operation. Operators
revoke by removing the fingerprint from the external pin set.

## Mutation CLI

`backlogit trust-anchor add|rotate|revoke` are thin wrappers over one core
mutation path:

- `add --id --role --algo --public-key-ref --fingerprint [--not-before]
  [--not-after]` requires the fingerprint to be externally pinned.
- `rotate <id>` takes the same declaration flags plus `--approval`.
- `revoke <id> --approval` requires approval and the revocation authority.
- `--approval <file>` is a signed JSON token with `action`, `anchor_id`,
  `approver`, `expiry`, `nonce` and a base64 Ed25519 `signature`. The core
  verifies the signature, the action and anchor binding, the nonce and the
  expiry against the operator approver key. The expiry may be at most 24 hours
  ahead. For rotate the signed payload (v2) also covers the replacement
  anchor's id, fingerprint, role, algo, not_before and not_after, taken from
  the rotate flags; the token file format itself is unchanged.
- `BACKLOGIT_TRUST_APPROVER_KEY` (base64 raw Ed25519 public key) or
  `BACKLOGIT_TRUST_APPROVER_KEY_FILE` provisions the approver key outside the
  workspace.
- Every mutation, applied or denied, is written to the append-only
  `trust_anchor_audit.jsonl`. A marker file brackets the write steps so a
  partial write is reported as indeterminate rather than success.
- `verify-key` is read-only and resolves a key through the same resolver.

## Residual it does/does not close

The residual it does/does not close, stated plainly:

Closed:

- A workspace writer re-activating a de-pinned or revoked key.
- A workspace writer widening a role or extending or removing a validity
  window for a bound pin.
- An advisory-only status flip being reported as a revocation.
- Unpinned, unapproved or forged-approval add, rotate and revoke requests.

Not closed:

- Compromise of the external pin set, the environment or the approver key
  (see the pin-set provenance residual above).
- Pins without a role and validity binding are denied rather than verified, so
  they provide no usable trust.
- Revocation without an operator-provided external authority is a manual
  external operation, not an automated one.
- Compromise of a private signing key held by the operator.
