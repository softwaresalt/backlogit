## Objective

Enable operators and agents to replan queued shipment manifests without hand-editing Markdown files by delivering the primitive shipment manifest operations from `DE3E7B67` (`docs/design-docs/2026-09-29-backlogit-shipment-manifest-reshuffle-feature-request.md` §1) under feature `206-F` and shipment `207-S`:

1. **`RemoveFromShipment` (`backlogit shipment remove` / `backlogit_remove_from_shipment`)**: Remove an item from a shipment's `custom_fields.items` manifest while leaving a `queued` shipment's member in `.backlogit/queue/` with `status: "queued"`, or — when force-removing an `active` member from an `active` shipment (`Force: true` + non-empty `Reason`) — verifying the member is an eligible unstarted claim-assigned member (`custom_fields.scheduler_baseline_claim == shipmentID` and no `WORK_STARTED:` comment in its item log for the current claim epoch; refusing forced removal of an already-started `active` member or one lacking the shipment's claim marker with `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`) and transitioning the member's `status` from `active` back to `queued` while clearing `custom_fields.scheduler_baseline_claim` (and appending a correlated `status_changed` `active -> queued` event to the member's item log) under the same durable shipment-operation recovery journal mechanism (`Operation: "remove_item"`, `RecoveryPolicy: "rollback"`, `ShipmentID: shipmentID`, `Target: itemID`, `Preimage.Shipment` + `Preimage.Members` containing the removed item's full preimage including `status` and `custom_fields.scheduler_baseline_claim`) in `internal/core/shipment_ops.go` and `internal/core/shipment_recovery.go` as `MoveShipmentItem` (durably updating the on-disk journal to `Phase: "committed"` immediately after all writes and `phase: "committed"` audit event appends succeed and before calling `cleanupShipmentOperationJournal`, skipping in-memory compensation and retaining the `Phase: "intent"` journal on disk for `lockShipmentLifecycleGlobal` barrier rollback recovery on `ErrWriteIndeterminate` or a crash before commit, and rolling back in-memory from the preimages and removing the journal on `ErrWriteNotApplied`), with a zero-write read-only `--dry-run` preview, a `--force` + `--reason` guard on non-`queued` shipments that unconditionally refuses `blocked` shipments (`ErrShipmentBlockedManifestSealed` / `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`), and audited `shipment_item_removed` event logging.
2. **`MoveShipmentItem` (`backlogit shipment move` / `backlogit_move_shipment_item`)**: Atomically remove an item from a source shipment and add it to a target shipment under canonical lexicographical membership lock ordering and a durable correlated `move_item` recovery journal (`internal/core/shipment_ops.go` + `internal/core/shipment_recovery.go`) that records and restores the **moved member artifact's full preimage** (including its original `status` and `custom_fields.scheduler_baseline_claim` marker) alongside both shipment manifest preimages in both immediate rollback and durable lifecycle-barrier recovery, verifies that any `active` member being force-moved from an `active` source shipment is an eligible unstarted claim-assigned member (`custom_fields.scheduler_baseline_claim == fromShipmentID` and no `WORK_STARTED:` comment in the current claim epoch; otherwise refusing with `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`), transitions the member's `status` from `active` back to `queued` and clears `custom_fields.scheduler_baseline_claim` (with a correlated `status_changed` `active -> queued` event) when `toShipment` is `queued` so `ClaimShipment(toShipment)` will later activate the `queued` member and stamp `scheduler_baseline_claim: toShipmentID` (or keeps `status: "active"` and updates `scheduler_baseline_claim = toShipmentID` when `toShipment` is `active`), durably updates the on-disk journal to `Phase: "committed"` after all writes and `phase: "committed"` audit events succeed and before calling `cleanupShipmentOperationJournal`, and supports a zero-write read-only `--dry-run` preview, a `--force` + `--reason` guard on non-`queued` endpoints that unconditionally refuses `blocked` endpoints, and correlated `shipment_item_moved` event logging with crash, journal-cleanup-failure, `ErrWriteIndeterminate`, and partial-audit-write rollback/aborted-event recovery.
3. **`ReorderShipment` (`backlogit shipment reorder` / `backlogit_reorder_shipment`)**: Reorder a shipment's manifest either via an explicit `--items` permutation or via `--auto` topological sorting over the two-phase dependency graph `G` (emitting only root covering feature(s) `isRootCoveringFeature` in the leading prefix, including **every remaining manifest member not already emitted as a root covering feature** — nested/sub-epic dotted features `100.001-F`, tasks, and subtasks — as vertices in `G`, first adding all hard intra-manifest `blocks` dependencies `B -> A` with cycle detection, and then iterating candidate default parent-before-child edges `P -> C` in deterministic manifest order and admitting `P -> C` into `G` if and only if `P` is not reachable from `C` in the current graph `G` containing all hard `blocks` edges plus previously admitted parent edges, with deterministic tie-breaking in `--auto` and validating the exact same graph `G` edges in `--items`), with a zero-write read-only `--dry-run` preview, a `--force` + `--reason` guard on non-`queued` shipments that unconditionally refuses `blocked` shipments, and audited `shipment_reordered` event logging.

## Problem Frame

In backlogit today (`internal/core/shipment.go`, `internal/cli/shipment.go`, `internal/mcp/tools.go`), shipment manifest membership only supports `AddItemToShipment` (`backlogit shipment add` / `backlogit_add_to_shipment`) and active-shipment `ReturnBlockedItem` (`backlogit shipment return-blocked` / `backlogit_return_blocked`). Replanning a queued shipment after review — removing descoped tasks, moving tasks to another shipment, or restoring covering-feature-first and `blocks`-topological manifest ordering — forces manual edits to `.backlogit/queue/<id>-S.md`. Hand-editing bypasses core validation (`validateShipmentItemIDs`, one-shipment-per-item invariants, status guards), leaves no JSONL audit trail in `.backlogit/logs/`, and risks SQLite index drift.

## Constraints

* **2-Hour Rule and Width Isolation**: Each unit stays within the `code` domain, touches at most 2–3 core source/test files (plus `.autoharness/backlog-registry.yaml` and deterministic `go run ./cmd/gen-docs docs/cli-reference` output in U3), modifies at most 4 functions, and keeps `go test` completely green at the end of every wave.
* **Authoritative `.autoharness/backlog-registry.yaml` update**: `.autoharness/backlog-registry.yaml` is listed in `.autoharness/drift-ignore` (see commit `a86b8065`). U3 updates `.autoharness/backlog-registry.yaml` directly with `remove_from_shipment`, `move_shipment_item`, and `reorder_shipment` (no test-only `pendingInRepoRegistryOperations` workaround in `internal/cli/registry_parity_test.go`) so both agents and `TestRegistryParity_*` consume the authoritative operation registry.
* **Blocked-manifest seal preservation**: Because `persistArtifact` (`internal/core/shipment.go:2062-2069`) and `guardBlockedShipmentMembershipMutation` (`internal/core/artifacts.go:1042-1053`) unconditionally reject manifest changes while a stored shipment is `blocked`, any `blocked` shipment (`status == "blocked"` or carrying a blocked-manifest seal) is unconditionally refused (`ErrShipmentBlockedManifestSealed` / `ErrInvalidStatus` / `blerrors.ErrShipmentConflict`) even when `Force: true` — both in live execution and in `DryRun: true` preview — requiring governed `UnblockShipment` first. `Force: true` with non-empty `Reason` overrides only `active` (and terminal `shipped`/`abandoned`) non-`queued` shipments, never `blocked`.
* **Read-only zero-write preview (`DryRun: true`)**: When `opts.DryRun == true`, all three operations (`RemoveFromShipment`, `MoveShipmentItem`, `ReorderShipment`) MUST execute a dedicated read-only preview path that (a) does NOT call `lockShipmentLifecycleGlobal` (which creates lock files and runs recovery) — instead inspecting the shipment lifecycle recovery journal directory read-only and refusing with a pending-recovery error (`blerrors.ErrShipmentConflict`) if any unfinished recovery journal exists — and (b) does NOT call `GetShipment` or `loadArtifact` (which call `db.UpsertItem` on a SQLite cache miss) — instead reading the shipment and member artifacts directly from Markdown via a read-only file loader (`readArtifactFromDiskReadOnly`) that never writes to SQLite, filesystem locks, or JSONL logs.
* **Never-nil slice wire-shape invariant**: All `ItemsBefore`, `ItemsAfter`, `FromBefore`, `FromAfter`, `ToBefore`, and `ToAfter` slices on result structs and `custom_fields.items` MUST be non-nil (`[]string{}` when empty, never `nil`) so JSON marshaling on both CLI and MCP always emits `[]` rather than `null` (`docs/compound/2026-07-03-cli-mcp-honest-fallback-map-and-registry-drift-test.md` Rule 3).
* **Genuine tests-first RED -> GREEN**: Every unit specifies the exact failing test selector (`^TestU1_`, `^TestU2_`, `^TestU3_`) that compiles cleanly and is observed RED before the production implementation turns it GREEN. No `harness-exempt` tasks exist in this plan (`closed_exempt_set: []`).

## Decisions and Rationale

* **Focused file layout across `shipment_ops.go`, `shipment_recovery.go`, and `shipment_manifest.go`**: `internal/core/shipment.go` is already ~2,950 lines, while `internal/core/shipment_ops.go` (512 lines) houses `validateShipmentLifecycleJournalRecord` and `loadShipmentOperationJournals`. Placing `RemoveFromShipment`, `MoveShipmentItem`, and `remove_item` + `move_item` journal validation in `internal/core/shipment_ops.go` alongside barrier recovery in `internal/core/shipment_recovery.go` and tests in `internal/core/shipment_manifest_test.go` keeps U1 strictly within the 3-file 2-Hour Rule while ensuring the real lifecycle barrier accepts and recovers both `remove_item` and `move_item` journals; U2 then adds `ReorderShipment` in `internal/core/shipment_manifest.go` (2 files in U2).
* **Canonical lexicographical lock order, governed requeue of unstarted claimed members, and durable `remove_item` + `move_item` recovery journals (`Phase: "intent"` -> `Phase: "committed"`) with full member preimage in `RemoveFromShipment` and `MoveShipmentItem`**: Always acquiring `lockShipmentLifecycleGlobal` first, then `lockShipmentMembership` (in lexicographical order `min(fromID, toID)` then `max(fromID, toID)` for moves), transitioning eligible unstarted claim-assigned `active` members (`scheduler_baseline_claim == sourceShipmentID` and no `WORK_STARTED:` in the current claim epoch; refusing already-started active members) back to `queued` with `scheduler_baseline_claim` cleared when force-removed or force-moved to a `queued` target shipment, persisting durable `remove_item` and `move_item` recovery journals (`internal/core/shipment_ops.go` + `internal/core/shipment_recovery.go`) with exact preimages of the shipment(s) AND the removed/moved member artifact's full preimage (including `status` and `custom_fields.scheduler_baseline_claim`), and durably updating the journal on disk to `Phase: "committed"` immediately after all writes and `phase: "committed"` audit event appends succeed and before calling `cleanupShipmentOperationJournal` eliminates AB-BA deadlocks, ensures `ClaimShipment` on a destination shipment can activate and stamp moved members, prevents a journal-cleanup failure from rolling back a completed operation at the next barrier, and prevents torn manifests or uncompensated audit events.
* **Authoritative `.autoharness/backlog-registry.yaml` update**: Because `.autoharness/backlog-registry.yaml` is listed in `.autoharness/drift-ignore` (see commit `a86b8065`), updating `.autoharness/backlog-registry.yaml` directly in U3 keeps the operation registry authoritative for both agents and `internal/cli/registry_parity_test.go` without test-only mappings.

## Risks and Mitigations

* **Risk 1 (Partial state, unclaimable active residual on `active -> queued` move/remove, rollback on journal-cleanup failure, or lost `scheduler_baseline_claim` on crash/indeterminate write)**: Clearing `scheduler_baseline_claim` without transitioning an eligible unstarted `active` member back to `queued` would cause `ClaimShipment` (`internal/core/shipment_lifecycle.go:169-175`) on the destination shipment to skip the non-`queued` member and leave it without `scheduler_baseline_claim`; leaving the operation journal at `Phase: "intent"` until `cleanupShipmentOperationJournal` would allow a journal-removal warning to trigger a rollback of a completed operation at the next lifecycle barrier; and `MutationEnvelope` keeps compensation only in memory and skips it on `ErrWriteIndeterminate` (`internal/core/mutation_envelope.go:23-41`).
  * **Mitigation**: Both `RemoveFromShipment` (`Operation: "remove_item"`, `RecoveryPolicy: "rollback"`, `ShipmentID: shipmentID`, `Target: itemID`, `Preimage.Shipment` + `Preimage.Members` containing the removed item's full preimage) and `MoveShipmentItem` (`Operation: "move_item"`, `RecoveryPolicy: "rollback"`, `ShipmentID: fromShipmentID`, `Target: toShipmentID`, `Preimage.Shipment` + `Preimage.Related` + `Preimage.Members` containing the moved item's full preimage) verify that any `active` member being force-removed or force-moved is an eligible unstarted claim-assigned member (`scheduler_baseline_claim == sourceShipmentID` and no `WORK_STARTED:` comment in the current claim epoch; refusing already-started active members), transition the member from `active` to `queued` and clear `scheduler_baseline_claim` when removing or moving to a `queued` shipment, persist durable shipment-operation recovery journals accepted by `validateShipmentLifecycleJournalRecord` / `loadShipmentOperationJournals` (`internal/core/shipment_ops.go`) before mutating the member or manifest(s), **durably update the journal on disk to `Phase: "committed"` (`writeShipmentOperationJournal` with `Phase: shipmentOperationPhaseCommitted`) after all writes and `phase: "committed"` audit event appends succeed and before calling `cleanupShipmentOperationJournal`** (and teach `reconcileShipmentLifecycleIntent` / the recovery evidence reader in `internal/core/shipment_recovery.go` that a `Phase == "committed"` journal or matching `phase: "committed"` `shipment_item_removed` / `shipment_item_moved` event is already committed and must be finalized/cleaned up without rolling back preimages), skip in-memory compensation on `ErrWriteIndeterminate` and retain the `Phase: "intent"` journal on disk so the next `lockShipmentLifecycleGlobal` barrier recovers `Preimage.Shipment` (and `Preimage.Related` for `move_item`) and `Preimage.Members` (including `status` and `scheduler_baseline_claim`) in Markdown and SQLite, and roll back in-memory from the preimages and remove the journal on `ErrWriteNotApplied`.
* **Risk 2 (Topological sort cycle, cross-parent default edge cycle, omitted nested features, absent-parent subtask edges, or nondeterminism in `ReorderShipment`)**: Cyclic `blocks` dependencies among manifest members could infinite-loop, adding all default `P -> C` parent-before-child edges simultaneously when only individual `blocks` reachability is checked could create a false cycle across parents (`A depends_on b` and `B depends_on a` + `A -> a` + `B -> b` forming `a -> B -> b -> A -> a`), nested/sub-epic features (`100.001-F`, excluded by `isRootCoveringFeature`) could be dropped if the Kahn graph only included non-feature items, subtasks whose parents are absent from the manifest could have their `blocks` edges ignored, or unsequenced items could reorder nondeterministically across runs.
  * **Mitigation**: Emit only root covering feature(s) (`isRootCoveringFeature`) in the leading prefix and include **every remaining manifest member not already emitted in the root-feature prefix** (nested/sub-epic dotted features `100.001-F`, tasks, and subtasks) as vertices in the two-phase dependency graph `G`: Phase 1 adds all hard intra-manifest `blocks` edges `B -> A` (rejecting any cycle among hard `blocks` edges with `ErrDependencyCycle` / `blerrors.ErrValidation`); Phase 2 iterates candidate default `P -> C` parent-before-child edges in deterministic manifest order and admits `P -> C` into `G` **if and only if** `P` is not reachable from `C` in the current graph `G` (containing all hard `blocks` edges plus previously admitted parent edges); `--auto` breaks ties deterministically (ready children of the most-recently emitted parent first, then original manifest index), and `--items` validates against the exact same two-phase graph `G`.
